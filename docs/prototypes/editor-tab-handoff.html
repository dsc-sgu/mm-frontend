Смена пишущей вкладки редактора

Вопрос. Как вкладки одного браузера делят Review editor и редактор Course Page, чтобы смена пишущей вкладки не теряла и молча не перезаписывала Working Copy (I5, I6)?

Прототип проигрывает предлагаемый протокол. Пишет одна вкладка, остальные — живые копии только для чтения. «Продолжить здесь» меняет пишущую вкладку добровольно или силой, если та молчит. Lease один на браузер (auth session). Браузер (localStorage, Web Lock, BroadcastChannel, заморозка вкладок) и сервер смоделированы в памяти. Нажимайте кнопки в любом порядке или пройдите сценарии.

Прототип для #132, выбросить после решения. Переносимая логика — в первом блоке <script>.

Вкладки браузера

Что произошло

Что предлагает прототип

  1. Спокойное состояние. Пишущая вкладка отвечает на «Продолжить здесь» сразу и перестаёт принимать правки. Ждёт она только запросы, чей исход меняет Working Copy: пакет синхронизации Course Page, публикацию или удаление черновика, публикацию Review. Отложенная синхронизация и «Не сохранено» передаются как есть. Неподтверждённая публикация Review передаётся вместе с idempotencyKey и замороженной Working Copy, повторы продолжает новая вкладка. Загрузки картинок в реализованном редакторе нет. На будущее: смена ждёт загрузку, во второй вкладке виден прогресс и «Отменить загрузку и продолжить здесь».
  2. Силовая смена. Если пишущая вкладка молчит 3 с, вкладка с живой копией продолжает сама, без второго нажатия. Если вкладка ответила и ждёт запрос, срок — таймаут запроса плюс 3 с. Вкладка без живой копии силой не продолжает: «Та вкладка не отвечает — перейдите в неё». Порядок силовой смены: сначала счётчик в localStorage, потом steal lock'а.
  3. Закрытие пишущей вкладки. Lock переходит к первой копии в очереди, она продолжает сама и показывает уведомление. Предупреждение об уходе нужно, только если совместимой живой копии нет. Lease снимается, когда закрывается последняя вкладка редактора.
  4. Версии. Одно целое TAB_PROTOCOL_VERSION на формат сообщений и Working Copy; конверт {kind, from, version, epoch} не меняется. При несовпадении нет ни живой копии, ни смены. Когда вкладка другой версии закроется, эта продолжит с сервера.
  5. User и ресурс. Канал, lock и запись в localStorage называются mm:editor:{UserId}:{review|course}:{AttemptId|CourseId}. Перед каждой записью синхронно сверяются User сессии и счётчик смен. Выход из аккаунта в любой вкладке останавливает запись во всех. Содержимое скрыто, Working Copy держится в памяти до закрытия вкладки. Вход тем же User продолжает работу, вход другим User удаляет Working Copy.
  6. Живая копия. Полная Working Copy со статусами (синхронизация, публикация, holder lease) уходит после каждого изменения, в той же задаче. Диффов нет, обнаруживать пропуски не нужно: новая копия заменяет старую по (epoch, seq). Вкладка, которая открылась, спрашивает состояние сообщением hello. Поэтому силовая смена не теряет правок, сделанных в браузере.
  7. Своя вкладка, своя сессия, чужой Teacher. Свою вкладку этого браузера видно локально, без сервера. 423 с holder — самим User: «Открыт в другой сессии — на другом устройстве или в другом окне · Вернуть сюда». Чужой holder: «Редактирует Борис · Попробовать снова». interrupted общий для всех вкладок браузера, потому что lease один.
  8. Что теряется при смене: история undo, выделение и курсор, scroll, открытые меню. Working Copy переходит целиком.
  9. Движки. Протокол не опирается на bfcache: pagehide — уход. При pageshow с persisted вкладка подключается заново и продолжает со своей Working Copy, только если запись о пишущей вкладке не менялась. Синхронная видимость счётчика после разморозки — допущение о движках, его проверяет TAB-08; страховка — проверка revision на backend.
