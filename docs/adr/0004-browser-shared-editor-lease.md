# Бронь принадлежит браузеру, вкладки делят редактор локально

Бронь проверки и бронь редактирования курса принадлежат сессии входа, то есть браузеру, а не вкладке. Клиентского `leaseId` нет. Вкладки одного браузера договариваются между собой: пишет одна вкладка, остальные показывают лайв-копию рабочей копии только для чтения. «Продолжить здесь» передаёт рабочую копию локально, без сервера: добровольно, если пишущая вкладка отвечает, или силой, если она молчит 3 с. Какая вкладка пишет, определяет запись `{epoch, writer}` в localStorage. Каждая передача увеличивает счётчик, и пишущая вкладка синхронно сверяет его перед каждой записью на сервер. Web Lock выбирает следующую пишущую вкладку и сообщает, что прежняя закрылась. Лайв-копия получает полную рабочую копию после каждого изменения, поэтому силовая передача не теряет правок, сделанных в браузере.

## Рассмотренные варианты

- **Бронь на вкладку с клиентским `leaseId`.** Так было в [«Спроектировать Review → Grade → Student result vertical»](https://github.com/dsc-sgu/mm-frontend/issues/116) и [«Спроектировать lifecycle Course Page Working Copy»](https://github.com/dsc-sgu/mm-frontend/issues/118): вторая вкладка открывалась только для чтения, а «Продолжить здесь» перехватывало бронь на сервере. Передаче была нужна сеть, а несинхронизированная рабочая копия оставалась в старой вкладке. Отвергнуто в [«Спроектировать матрицу тестовых контрактов критических вертикалей»](https://github.com/dsc-sgu/mm-frontend/issues/120).
- **Лайв-копия получает изменения, а не полную рабочую копию.** Меньше данных, но понадобились бы обнаружение пропусков и второй формат помимо состояния. Отвергнуто.
- **После закрытия пишущей вкладки копии только предлагают «Продолжить здесь».** Пока преподаватель не выбрал, продлевать бронь некому, а правки лежат в памяти копий без защиты от ухода. Отвергнуто: копия продолжает сама.

## Последствия

- Сервер не различает вкладки одного браузера. Запрос, отправленный замороженной вкладкой до силовой передачи, может прийти после записей новой пишущей вкладки. Для страницы курса это закрывает проверка версии черновика на бэкенде (`409`). Без неё на силовом пути остаётся узкое окно молчаливой перезаписи (см. [«Реестр frontend-вопросов к backend API»](https://github.com/dsc-sgu/mm-frontend/issues/113)). Публикации проверки это не грозит: повтор с тем же ключом идемпотентен.
- Сразу после разморозки вкладки счётчик должен читаться синхронно и в актуальном значении. Это допущение о браузерных движках; его проверяет контракт TAB-08 в браузере — в Chromium, Firefox и WebKit.
- `423`, где держатель брони — сам пользователь, всегда означает другую сессию: другое устройство или приватное окно. Свою вкладку этого браузера видно локально, без сервера.
- Канал, Web Lock и запись привязаны к `UserId` и ресурсу. Выход из аккаунта в любой вкладке останавливает запись во всех вкладках браузера.

Решение принято в [«Спроектировать смену пишущей вкладки редактора»](https://github.com/dsc-sgu/mm-frontend/issues/132).
