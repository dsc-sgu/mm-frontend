# Course Page Working Copy синхронизируется по состоянию под Course Editing Lease

Редактор не отправляет на сервер собственные операции. Чистая функция сравнивает Course Page Working Copy с последним подтверждённым состоянием Course Draft Snapshot (`base`) и строит операции над черновиком: create, patch, move и delete блоков, а также изменения metadata и resources. Одновременно в полёте один batch, правки тем временем копятся локально. Если исход операции неизвестен, frontend перечитывает черновик, делает его новой `base` и строит план заново. Это безопасно, потому что в черновик Teacher'а пишет только сессия, удерживающая Course Editing Lease. Поэтому операциям черновика idempotency keys не нужны. Неизвестный исход публикации сверяется чтением активного Course Snapshot: если им стал наш черновик, публикация прошла.

## Considered Options

- **Журнал операций редактора (outbox).** Точнее передаёт намерение, но привязывает операции Plate к backend-контракту, усложняет склеивание правок и требует replay/rebase после сбоев. Отвергнуто.
- **Idempotency key для публикации, как у Review.** Backend его не поддерживает. К тому же опубликованный черновик сам становится активным snapshot, так что `draftSnapshotId` уже служит ключом сверки. Отвергнуто.

## Consequences

- Корректность держится на исключительности lease. Если lease потерян, синхронизация останавливается. После повторного взятия черновик сравнивается с `base`. Если он изменился (например, в другой вкладке того же Teacher'а), Teacher явно выбирает между версией с сервера и перезаписью своей версией. Автоматического merge нет.
- «Перезаписать моей версией» ничего не стоит: это новый план от новой `base`.
- Пока backend сам назначает id блоков, сопоставление локальных и серверных id живёт внутри модуля синхронизации. Клиентские UUID убрали бы это сопоставление.

Решение принято в [«Спроектировать lifecycle Course Page Working Copy»](https://github.com/dsc-sgu/mm-frontend/issues/118).
