# Отказ в доступе не раскрывает существования ни на экране, ни по сети

Чужое и несуществующее неразличимы целиком: на экране, по HTTP-статусу, по телу ответа и во внутренних исходах фронтенда. Курс, которого нет, и курс, где пользователь не участник, дают один исход `not-found` и по сети `404` без тела. Ресурс участника (попытка, репозиторий, проверка), которого нет, и чужой ресурс — так же, и для локаторов (по username и номеру попытки), и для чтений по идентичностям. Явный `403` остаётся только у раздела курса, недоступного по роли: участник и так знает, что курс и раздел существуют.

Скрывать только экран бессмысленно: во вкладке Network видно `403` против `404` или `{ status: 'not-member' }` против `{ status: 'course-not-found' }` при одинаковом `404`. Так было в моках до этого решения: три вида утечки — через статус, через тело и через то и другое сразу.

## Граница гарантии: доступность адреса при создании курса

При создании курса пользователь выбирает адрес и может получить сообщение «Адрес недоступен». Занятость адреса не является секретом: её разрешено сообщать любому вошедшему пользователю в форме создания, включая предварительную проверку при вводе, в том числе если адрес занят закрытым для него курсом. Ответ не раскрывает название, участников, содержимое или другие сведения о чужом курсе. Отказ в доступе к самому курсу по-прежнему неотличим от отсутствия курса.

Это осознанная граница гарантии: ручной выбор человекочитаемого адреса с понятной ошибкой конфликта важнее сокрытия самого факта его занятости. Полное сокрытие занятости потребовало бы пересмотреть ручной выбор адреса, например всегда назначать случайные адреса. Решение согласовано в mm-178 при проектировании создания курса.

## Рассмотренные варианты

- **Различать причины внутри, а снаружи сводить к одному `404`.** Так требовали [«Выбрать явный UX для отказа в course-local доступе»](https://github.com/dsc-sgu/mm-frontend/issues/111) и [«Спроектировать Course access vertical и identity seam»](https://github.com/dsc-sgu/mm-frontend/issues/115): внутренние исходы `course-not-found`, `not-member`, `forbidden`. Но «ресурса нет» и «ресурс чужой» знает только бэкенд. Чтобы фронтенд различал их внутри, бэкенд должен сообщить разницу по сети, а значит, раскрыть её всем. Требование противоречит неразличимости на экране. Отвергнуто; это решение заменяет его.
- **Честный `403` везде, где ресурс существует.** Проще и привычнее, внутреннее различие сохраняется бесплатно. Но раскрывает существование: slug курса человекочитаем (`algorithms-2026`), и закрытый курс находится угадыванием. К тому же экран показывал бы `404` там, где по сети пришёл `403`. Отвергнуто.

## Последствия

- **Перепроверка курса — после любого отказа на ресурсе.** Раньше её запускал только `forbidden`: отказ, который мог означать потерю участия. Теперь причину не знает никто на фронтенде, поэтому перепроверяется каждый отказ. Цена — один запрос контекста курса на битую ссылку.
- **Отказ после `found` — потеря доступа.** Если курс был найден, а затем по тому же slug пришёл `not-found`, кэш данных курса удаляется. Раньше смена slug (`course-not-found`) кэш сохраняла. Смена slug того же курса обрабатывается только через ответ `found` с новым slug ([ADR 0005](0005-locator-urls-resolved-to-stable-identities.md), [«Сохранять страницу при смене courseSlug того же курса»](https://github.com/dsc-sgu/mm-frontend/issues/254)); без истории slug на бэкенде вход по старому адресу даёт `404` в обоих вариантах.
- **Диагностика.** По ответу не видно, почему `404`. Причину знает только бэкенд, в своих логах.
- **Неверный адрес API неотличим от отказа.** Эндпоинт, которого нет, тоже отвечает `404` без тела, и фронтенд покажет «Страница не найдена», а не ошибку. Это нужно проверить при подключении к настоящему бэкенду.
- **Время ответа.** Отказ по разным причинам не должен заметно различаться по времени. Это забота бэкенда.
- **Различимыми остаются:** `401` без сессии, `403` раздела по роли и технический сбой («Не удалось проверить доступ»). Они ничего не раскрывают о чужом.

Позиция фронтенда для бэкенда — в [«Реестр frontend-вопросов к backend API»](https://github.com/dsc-sgu/mm-frontend/issues/113), пункт «Forbidden или not-found».
