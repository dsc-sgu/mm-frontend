# URL адресует ресурс локаторами, данные читаются по идентичностям

URL ресурса участника курса остаётся человекочитаемым: `…/tasks/:taskId/attempts/:username/:attemptNumber/review`. Username и `CourseSlug` — локаторы: они меняются и со временем могут указать на другой ресурс, поэтому идентичностью быть не могут. Локатор разрешается в идентичность (`AttemptId`, `UserId`) один раз, а чтения, записи, ключи кэша и проверка доступа работают только с идентичностью. При входе по URL намерение пользователя — сам URL, и маршрут ждёт свежий ответ локатора. При переходе внутри приложения намерение — выбранная пользователем идентичность: маршрут берёт её из кэша, а устаревший адрес исправляется под неё.

## Рассмотренные варианты

- **Идентичности прямо в URL** (`…/attempts/0f3a…/review`). Разрешать нечего, но URL нечитаем и не говорит, чья это попытка и какая по счёту. Отложено (см. «Когда пересмотреть»).
- **Каждый эндпоинт принимает локаторы и разрешает их на бэкенде.** Цепочки запросов нет, но ключи кэша и ссылки снова строятся на изменяемом username. Отвергнуто.
- **Составная идентичность из стабильных частей** (`CourseId + TaskId + UserId + AttemptNumber`). Корректна, но URL всё равно несёт username, так что разрешение остаётся. При этом на попытку ссылаются проверка, комментарии и проекции с оценкой, и всем пришлось бы носить четыре поля вместо одного UUID, который бэкенд уже хранит (#85). Отвергнуто.
- **Чтения страницы по локатору.** Ключ кэша строится по идентичности, а чтение по username вернёт то, на что username указывает в момент ответа. После смены владельца данные чужой попытки лягут под ключ своей и останутся там до инвалидации. Каждое фоновое обновление заново разрешает локатор, а параллельные чтения страницы могут прийти от разных попыток, хотя записи опираются на них все. По локатору допустимо одно чтение, которое само возвращает идентичность, — сам локатор. Отвергнуто.
- **Свежий ответ локатора на каждом переходе.** Так было до этого пересмотра: переключение попытки ждало лишний сетевой круг на действии, которое преподаватель повторяет чаще всего. Довод «по устаревшему соответствию преподаватель увидит попытку не того студента» не выдерживает проверки: свежий локатор окно не закрывает, а переносит. Строка списка, по которой кликнул преподаватель, — идентичность из того же устаревшего списка, и свежее разрешение покажет попытку, по которой он не кликал. Доступ при этом не утекает: чтения по `AttemptId` проверяют права. Отвергнуто.
- **Показывать из кэша, перепроверять локатор в фоне и блокировать запись до ответа.** Безопасно, но требует состояния подтверждения, блокировки всех путей записи и экрана расхождения. Записи и так идут по показанной идентичности, поэтому преподаватель оценивает ровно то, что видит. Отвергнуто в пользу исправления адреса.

## Последствия

- **Вход по URL стоит один сетевой круг.** Маршрут ждёт ответ локатора в `beforeLoad`; при первом входе в курс он сам идёт после `loadCourseBySlug`. Не меняя URL, вход удешевляют двумя способами:
  - чтения страницы запускаются из `loader` без ожидания, сразу после ответа локатора, и ленивый чанк страницы грузится одновременно с данными (`prefetchAttemptPage`);
  - маршрут предзагружается по намерению (`preload="intent"`): `beforeLoad` и `loader` выполняются при наведении на ссылку или пункт переключателя попыток.
- **Переход внутри приложения не ждёт локатор**, если идентичность уже в кэше локатора: из ответа preload или из переключателя попыток, где `AttemptId` известна. Кэшируется только исход `found`; отказ и `not-found` всегда перепроверяются. Реализация — #253.
- **Адрес следует за идентичностью.** Каждым сегментом URL владеет одно чтение по идентичности ресурса, который сегмент адресует: `courseSlug` — загрузка курса, username и номер попытки — сводка попытки (`loadAttemptSummary`). Если ответ владельца расходится с параметрами маршрута, страница кладёт в кэш локатора соответствие «новые параметры → та же идентичность» и вызывает `navigate({ replace: true })`. Списки и другие чтения показывают username, но адрес не меняют: их ответы устаревают с другой скоростью, и адрес прыгал бы между значениями.
  - Роутер не перемонтирует страницу при смене параметров, пока у маршрутов не задан `remountDeps`, поэтому черновики сохраняются. `remountDeps` не задаём.
  - Уровни попытки и репозитория — #253. На уровне курса guard маршрута курса сейчас размонтирует поддерево при смене `courseSlug`, а `pendingMs: 0` даёт мигание — #254.
- **Старая ссылка исправляется только на бэкенде.** Исправление адреса работает у того, кто уже на странице. Вход по старому username или slug даёт `404`, пока бэкенд не вернёт канонический адрес в ответе локатора. Это и текущий username в сводке попытки — вопросы к бэкенду в [«Реестр frontend-вопросов к backend API»](https://github.com/dsc-sgu/mm-frontend/issues/113): «Адресация попытки: номер и UUID», «Смена локатора: история, повторное занятие и канонический адрес».
- **Не удешевляет: сводка попытки в ответе локатора.** Отдельный `loadAttemptSummary` исчезает, но проверка и материал всё равно ждут `AttemptId`, так что критический путь не короче: минус запрос, но не минус сетевой круг. Убрать круг при входе можно только агрегатом всех чтений, от которого отказался REV2.
- **Когда пересмотреть.** Если в production задержка входа по URL заметно ухудшает UX, URL переводятся на идентичности. Код страниц при этом не меняется: он уже работает только с идентичностями, переписываются маршруты и ссылки.

Решение принято в [«Epic: Course access»](https://github.com/dsc-sgu/mm-frontend/issues/167) (ACC2), доведено до чтений проверки и пересмотрено для переходов внутри приложения в [REV2.1](https://github.com/dsc-sgu/mm-frontend/issues/221).
