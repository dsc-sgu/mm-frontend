# Удалённые данные

Этот документ устанавливает обязательные правила для кода, который выполняет удалённые операции, принимает внешние данные, связывает эти операции с TanStack Query или имитирует HTTP-поведение через MSW.

Термины **ДОЛЖЕН**, **НЕ ДОЛЖЕН**, **ОБЯЗАТЕЛЬНО**, **СЛЕДУЕТ**, **НЕ СЛЕДУЕТ** и **МОЖЕТ** являются нормативными.

## Определения

- **Удалённая операция** — операция, которая взаимодействует с внешней системой, включая HTTP backend.
- **Объявленный исход** — результат, явно представленный типом значения, с которым завершается Promise удалённой операции. Объявленный исход может быть положительным или отрицательным.
- **Ожидаемый отрицательный исход** — отрицательный объявленный исход, который входит в нормальный контракт операции и требует решения вызывающего кода, а не восстановления инфраструктуры.
- **Отказ операции** означает, что удалённая операция не смогла получить ни один объявленный исход.
- **Отмена** — управляющий сигнал, который останавливает операцию. Отмена не является ни объявленным исходом, ни отказом операции.
- **Логическая команда** — одно намерение пользователя или приложения выполнить mutation независимо от количества transport-попыток.
- **Повторная попытка** — новая transport-попытка той же логической команды или того же выполнения query.
- **Авторитетное представление** — провалидированное представление server state, которое backend объявляет полным и актуальным для конкретной проекции на момент ответа.

## Классификация исходов и отказов

1. Удалённая операция ДОЛЖНА завершать Promise объявленным исходом, если получила корректный ответ согласно своему контракту.
2. Взаимоисключающие положительные и ожидаемые отрицательные исходы ДОЛЖНЫ быть вариантами discriminated union, специфичного для операции.
3. Удалённая операция ДОЛЖНА отклонять Promise, если не смогла получить ни один объявленный исход.
4. Отказ операции ДОЛЖЕН быть представлен экземпляром `Error` с машиночитаемым discriminant. Код НЕ ДОЛЖЕН бросать строки, обычные объекты или непроверенное тело ответа.
5. Классификация ДОЛЖНА выполняться отдельно для контракта каждой операции. HTTP status, происхождение ошибки и возможность повтора сами по себе НЕ ДОЛЖНЫ определять классификацию.
6. Один HTTP status МОЖЕТ быть объявленным исходом одной операции и отказом другой операции.
7. Ошибки программирования НЕ ДОЛЖНЫ перехватываться и преобразовываться в отказы запроса. Блок `catch` ДОЛЖЕН охватывать только ту внешнюю операцию, отказы которой он явно нормализует.
8. Ожидаемые отрицательные исходы НЕ ДОЛЖНЫ передаваться в общие error boundaries или operational-error telemetry как отказы операции.

Порядок принятия решения:

1. Перечислить допустимые положительные и отрицательные ответы операции в типе её resolved value.
2. Если получен один из этих ответов, завершить Promise соответствующим объявленным исходом.
3. Если ни один объявленный исход не получен, отклонить Promise типизированным отказом операции.
4. Определить политику повторов отдельно после классификации результата.

## HTTP transport

1. Новый HTTP transport-код ДОЛЖЕН использовать нативный Fetch API. Axios НЕ ДОЛЖЕН добавляться в новый код.
2. Feature-код ДОЛЖЕН предоставлять функции, специфичные для операций, и НЕ ДОЛЖЕН передавать необработанный `Response` в UI или domain-код.
3. Код ДОЛЖЕН проверять `Response.status` или `Response.ok`. Успешное завершение `fetch` Promise НЕ ДОЛЖНО считаться доказательством успешного HTTP-ответа.
4. Ожидаемые HTTP-ответы ДОЛЖНЫ преобразовываться в объявленные исходы согласно контракту операции.
5. Неожиданные HTTP-ответы ДОЛЖНЫ отклонять Promise типизированным HTTP-отказом.
6. Network-, CORS-, request-construction-, body-reading- и body-decoding-отказы ДОЛЖНЫ нормализоваться только на уровне операции, выполняющей соответствующее внешнее действие.
7. Прерывание через переданный `AbortSignal` ДОЛЖНО оставаться отменой и НЕ ДОЛЖНО преобразовываться в network-, HTTP- или domain-отказ.

## Проверка внешних данных

1. Каждый структурированный payload из внешней системы ДОЛЖЕН входить в application-код как `unknown`, если читающая его операция сама не выполняет runtime validation до возврата значения.
2. Код НЕ ДОЛЖЕН присваивать непроверенный внешний payload типу DTO или domain model через `any`, type assertion или непроверенный generic type parameter.
3. Внешний payload ДОЛЖЕН пройти runtime validation до чтения его полей и до помещения в application state или cache.
4. Payload успешного ответа и используемый структурированный payload ответа с ошибкой ДОЛЖНЫ проверяться соответствующими Valibot schemas.
5. Raw bytes, blobs, streams и text ДОЛЖНЫ проверяться согласно контракту, по которому приложение их интерпретирует. Object schema не требуется только потому, что данные пришли из внешней системы.
6. Payload, нарушающий контракт, ДОЛЖЕН отклонять Promise отказом `invalid-response` и НЕ ДОЛЖЕН попадать в domain state или query cache.
7. Runtime validation ДОЛЖНА предшествовать преобразованию DTO в domain model. DTO МОЖЕТ быть преобразован в domain model только после успешной проверки.

Обязательный переход доверия:

```text
внешний payload -> unknown -> runtime validation -> DTO -> domain model
```

Вспомогательная функция МОЖЕТ скрывать промежуточный `unknown` от вызывающего кода, только если сама выполняет runtime validation до возврата:

```ts
const dto = await requestJson({
  url: '/api/courses/42',
  schema: CourseDtoSchema,
});
```

## Интеграция с TanStack Query

1. `queryFn` или `mutationFn` ДОЛЖНА завершаться данными только после получения объявленного исхода удалённой операции.
2. Отказ операции ДОЛЖЕН достигать TanStack Query как rejected Promise.
3. `queryFn` или `mutationFn` НЕ ДОЛЖНА завершаться generic `Result<T, E>`, если его error-вариант представляет отказ операции.
4. Ожидаемые отрицательные исходы ДОЛЖНЫ оставаться в resolved data и НЕ ДОЛЖНЫ преобразовываться в ошибки TanStack Query.
5. Query-функция ДОЛЖНА передавать `AbortSignal` TanStack Query каждой запущенной ею отменяемой удалённой операции.
6. Отмена этим сигналом ДОЛЖНА распространяться как отмена и НЕ ДОЛЖНА преобразовываться в отказ операции.
7. Потребитель query или mutation МОЖЕТ сузить типизированный `Error`, чтобы выбрать пользовательское поведение. Он НЕ ДОЛЖЕН выводить domain-смысл из непроверенного тела ответа.

Generic `Result<T, E>` МОЖЕТ использоваться вне remote-data-пути TanStack Query, только если его error-вариант намеренно входит в объявленный interface соответствующего module. `Result<T, E>` НЕ ДОЛЖЕН вводиться только для упаковки отказа операции непосредственно перед обратным преобразованием в rejected Promise.

## MSW

1. MSW ДОЛЖЕН быть основным HTTP seam для мокирования удалённых операций в development и tests.
2. Application feature-код ДОЛЖЕН вызывать одни и те же Fetch-based функции независимо от того, включён MSW или используется реальный backend.
3. Feature-код НЕ ДОЛЖЕН выбирать между mock- и real-реализациями удалённой операции.
4. TypeScript interface и dependency injection НЕ ДОЛЖНЫ вводиться только ради mock-реализации HTTP-операции.
5. MSW handlers ДОЛЖНЫ возвращать protocol-level ответы, проходящие тот же status handling, body parsing, runtime validation, DTO mapping и TanStack Query integration, что и ответы реального backend.
6. Запуск MSW в browser ДОЛЖЕН завершиться до начала rendering, если initial rendering может отправить перехватываемые запросы.
7. MSW НЕ ДОЛЖЕН включаться в production без отдельного документированного runtime-требования.

Отдельная in-process-реализация МОЖЕТ быть введена только при наличии немоковой потребности менять поведение в этом seam.

## Query keys

1. Каждое семейство query ДОЛЖНО владеть одним типизированным объектом key factory с именем `<область>Keys`.
2. Каждый key ДОЛЖЕН быть readonly tuple и ДОЛЖЕН включать все входные данные, изменение которых меняет результат `queryFn`.
3. Key factory ДОЛЖНА выражать иерархию от общего scope к более точным scopes, если семейство содержит параметры или поддерживает prefix invalidation.
4. Даже семейство с одним key ДОЛЖНО использовать минимальный key factory, чтобы в проекте существовал один способ объявлять и использовать query keys.
5. Raw strings, отдельно экспортированные root constants и вручную собранные tuples НЕ ДОЛЖНЫ быть cross-feature interface.
6. Feature, которому нужен key другого feature, ДОЛЖЕН использовать публичную key factory владельца.
7. Общий registry всех query keys НЕ ДОЛЖЕН создаваться. Key factory принадлежит feature, владеющему соответствующими server data.
8. Semantic cache helper ДОЛЖЕН создаваться только тогда, когда он скрывает повторяемое, многосоставное или инвариантное cache behavior. Однострочная обёртка над одной очевидной операцией `QueryClient` НЕ ДОЛЖНА создаваться только ради сокрытия TanStack Query.
9. UI и domain model НЕ ДОЛЖНЫ зависеть от представления query keys.

Минимальная форма для семейства с одним key:

```ts
export const sessionKeys = {
  all: ['session'] as const,
};
```

Иерархическая форма:

```ts
export const courseAttemptsKeys = {
  all: ['course-attempts'] as const,
  course: (courseId: CourseId) =>
    [...courseAttemptsKeys.all, courseId] as const,
  list: (courseId: CourseId, filters: CourseAttemptsFilters) =>
    [...courseAttemptsKeys.course(courseId), { filters }] as const,
};
```

## Обновление cache после mutation

1. Server state ДОЛЖЕН оставаться источником истины для remote data.
2. После успешной mutation код ДОЛЖЕН определить полный stale scope до выбора между cache update и invalidation.
3. `setQueryData` СЛЕДУЕТ использовать для точного cache entry, когда mutation вернула его полное провалидированное авторитетное представление.
4. `setQueryData` НЕ ДОЛЖЕН использоваться для реконструкции filtered, sorted, paginated или derived representations, если для этого требуется повторить backend business logic во frontend.
5. Derived или неполные представления, затронутые mutation, ДОЛЖНЫ быть инвалидированы через минимальный корректный key prefix.
6. Broad invalidation ДОЛЖНА использоваться только тогда, когда полный stale scope известен, но не может быть выражен более узким стабильным prefix, либо когда mutation действительно изменяет весь scope.
7. Invalidation НЕ ДОЛЖНА расширяться на весь domain scope только ради защиты от гипотетических будущих projections. Новая projection ДОЛЖНА явно объявлять зависимости от существующих mutations или consistency operations.
8. Cache update через `setQueryData` ДОЛЖЕН быть immutable.
9. Cross-feature mutation ДОЛЖНА явно координировать свои cache effects через key factories или содержательные helpers владельцев соответствующих caches.
10. Mutation ДОЛЖНА ожидать завершения invalidation, если дальнейший UI transition предполагает уже согласованные данные. Фоновая invalidation МОЖЕТ не удерживать mutation в pending только при явно допустимом stale UI.

Типичный смешанный случай:

1. Поместить авторитетный mutation response в точный detail cache.
2. Инвалидировать списки и derived projections, которые могли измениться.
3. Не пытаться вручную поддерживать normalized entity cache поверх TanStack Query.

## Optimistic updates

1. Код НЕ ДОЛЖЕН применять optimistic update без подтверждённой потребности в мгновенном speculative UI.
2. Мгновенный speculative UI нужен только тогда, когда ожидание server response заметно нарушает непрерывность действия пользователя, а предполагаемый исход однозначен, понятен пользователю и безопасно обратим.
3. Наличие mutation само по себе НЕ является основанием для optimistic update. Pending indicator, disabled submit или сохранённая local working copy МОГУТ полностью удовлетворять UX-контракт.
4. Если speculative state нужен только в одном UI surface, СЛЕДУЕТ отображать его из mutation state или `mutation.variables`, не изменяя query cache.
5. Optimistic cache update МОЖЕТ использоваться только тогда, когда speculative state одновременно требуется нескольким cache consumers или дальнейшим локальным операциям.
6. До optimistic cache update код ДОЛЖЕН определить поведение параллельных mutations, refetch и out-of-order responses.
7. Optimistic cache update ДОЛЖЕН включать отмену конфликтующего refetch, snapshot предыдущего значения, immutable update, rollback при отказе и reconciliation с авторитетным server state.
8. Temporary identity ДОЛЖНА быть отличима от server identity и НЕ ДОЛЖНА сохраняться после reconciliation.
9. Простая mutation с идемпотентным и однозначным переходом МОЖЕТ использовать optimistic cache update, если rollback не уничтожает более новые подтверждённые изменения.
10. Создание или изменение комментария НЕ ДОЛЖНО использовать optimistic cache update без отдельного доказанного требования нескольких consumers. Pending UI или ожидание server response является достаточным default.
11. Transition Review Read State в `seen` МОЖЕТ использовать optimistic cache update: переход локален, однозначен и должен немедленно отражаться в интерфейсе.

Порядок выбора:

```text
Нужен ли мгновенный speculative UI?
├── Нет -> не применять optimistic update
└── Да
    ├── Состояние нужно только в одном UI surface?
    │   └── Да -> отобразить mutation state без изменения cache
    └── Состояние нужно нескольким cache consumers?
        └── Да -> optimistic cache update с concurrency model,
                 snapshot, rollback и reconciliation
```

## Повторы и идемпотентность

1. Ожидаемые отрицательные исходы НЕ ДОЛЖНЫ запускать retries TanStack Query.
2. Возможность повтора ДОЛЖНА определяться одновременно контрактом операции и видом отказа.
3. Network-отказ или HTTP `5xx` сами по себе НЕ ДОЛЖНЫ означать, что операцию безопасно повторить.
4. Автоматические query retries МОГУТ применяться к временным отказам идемпотентной query-операции.
5. Автоматические mutation retries ДОЛЖНЫ быть отключены, если backend operation не имеет документированной гарантии идемпотентности.
6. Идемпотентность НЕ ДОЛЖНА выводиться только из HTTP method.
7. Если идемпотентность mutation основана на idempotency key, каждая повторная попытка одной логической команды ДОЛЖНА использовать один и тот же key.
8. Новая логическая команда ДОЛЖНА использовать новый idempotency key.
9. Отказы чтения body и runtime validation НЕ СЛЕДУЕТ автоматически повторять.
10. Retry limit, delay и server-provided retry instructions ДОЛЖНЫ быть заданы явно. Бесконечные retries запрещены.

Backend idempotency является предварительным условием прозрачных mutation retries. Frontend-код НЕ ДОЛЖЕН имитировать эту гарантию, если её нет в backend-контракте.

## Примеры классификации

Примеры поясняют правила; определяющим остаётся объявленный контракт операции.

| Ситуация                                                                     | Классификация                      | Причина                                                                      |
| ---------------------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------- |
| Проверка session сообщает об отсутствии аутентифицированного User            | Ожидаемый отрицательный исход      | Получен корректный ответ на вопрос о состоянии session.                      |
| Login отклоняет неверные credentials                                         | Ожидаемый отрицательный исход      | Попытка аутентификации завершилась определённым отрицательным результатом.   |
| Save сообщает о документированном stale-write conflict                       | Ожидаемый отрицательный исход      | Вызывающий код должен выбрать переход разрешения конфликта.                  |
| Network не возвращает response                                               | Отказ операции                     | Application-level ответ не получен.                                          |
| Response body содержит malformed JSON                                        | Отказ операции                     | Невозможно построить корректный объявленный исход.                           |
| Response нарушает DTO schema                                                 | Отказ операции                     | Непроверенные данные не могут попасть в domain state или query cache.        |
| TanStack Query отменяет устаревший request                                   | Отмена                             | Операция намеренно остановлена и не должна становиться user-visible failure. |
| Сохранение возвращает полный авторитетный detail resource                    | Post-success cache update          | Точный cache entry можно обновить без повторного GET.                        |
| Сохранение влияет на filtered list, который response не возвращает полностью | Targeted invalidation              | Frontend не должен повторять backend filtering и sorting.                    |
| Отметка Review Read State как `seen`                                         | Допустимый optimistic cache update | Transition локален, однозначен и требует немедленной обратной связи.         |
| Создание reply без требования нескольких consumers                           | Без optimistic cache update        | Pending state или server-confirmed result обеспечивает достаточный UX.       |
