# Зафиксировать контракт нумерации списков редактора

## Question

Какой регрессионный контракт должен гарантировать корректную нумерацию ordered lists в редакторе страницы курса и после сохранения/повторного открытия: для последовательных элементов, вложенных уровней, смешанных ordered/unordered групп и структурных операций? Ответ должен зафиксировать наблюдаемые сценарии, которые будущие model и real-browser tests обязаны покрыть, включая известную регрессию, когда каждый элемент отображался как `1`, но не реализовывать сами тесты в рамках этой карты.

### 2026-09-13T19:11:29Z · t3m8ch

## Решение: регрессионный контракт списков Course Page

Контракт фиксирует наблюдаемое поведение и persisted-семантику, а не текущий алгоритм Plate. Production/source code и тесты в рамках решения не менялись.

### Каноническая модель и rendering

- Источник структуры — persisted `CourseListBlock`/`CourseListItem`: документный порядок, `variant: ordered | unordered` и нормализованный `indent`. Вычисленный номер не является persisted-полем.
- Read-mode обязан восстановить семантическое дерево: одна непрерывная группа ordered siblings рендерится одним `<ol>` с несколькими `<li>`, unordered — одним `<ul>`, а вложенный список находится внутри соответствующего родительского `<li>`.
- В editor-mode допустимо внутреннее плоское представление Plate, где отдельные `<ol start>` используются как технический механизм. Оно не становится read-mode контрактом.
- Editor, повторно открытая Course Page Working Copy и read-only Course Page для Teacher/Student обязаны показывать одинаковые номера и иерархию. Read-only работает и на mobile; сам editor остаётся desktop-only согласно принятой platform boundary.

### Границы и нумерация

- Одна numbered-серия — максимальная непрерывная группа ordered siblings одного уровня. Скрытый `courseListId` не влияет на наблюдаемые номера.
- Соседние ordered items одного уровня без видимого разделителя продолжаются как `1, 2, 3`, даже если появились из разных внутренних list IDs.
- Обычный non-list block разрывает серию; следующий ordered-фрагмент начинается с `1`.
- Смена `ordered → unordered → ordered` на одном уровне завершает предыдущую numbered-серию: результат `1 / • / 1`, а не `1 / • / 2`.
- Вложенный список не прерывает родительскую нумерацию: `1. parent / nested list / 2. parent`.
- Произвольный старт не поддерживается. Новый ordered-run всегда начинается с `1`; markdown-преобразование должно срабатывать только для `1.`, чтобы ввод `3.` не показывал transient-семантику, которая потеряется после сохранения.

### Структурные операции

- `Enter` в непустом item разделяет его и создаёт следующий sibling; серия сразу уплотняется и перенумеровывается.
- `Enter` в пустом вложенном item поднимает его на один уровень; в пустом item уровня 1 выводит в paragraph.
- `Backspace` в начале вложенного item поднимает его на один уровень; в начале item уровня 1 сначала выводит его из списка. После каждой операции нумерация пересчитывается.
- Вставка paragraph между list items разрывает список и начинает tail ordered-run с `1`; удаление такого paragraph снова объединяет визуально непрерывные ordered siblings и даёт плотную серию.
- Преобразование item между ordered/unordered сохраняет текст и допустимый indent, разрывает серии согласно правилам выше.
- Одиночные Move Up/Down, drag и Duplicate действуют только на блок, чей grab handle/command использован. Descendants автоматически не захватываются; после изменения порядка их parentage выводится из нового соседства и нормализуется.
- Удаление родительского item сохраняет descendants. Их indent сохраняется, если допустим в новом соседстве; orphaned items поднимаются только настолько, насколько требуется для валидной структуры. Поэтому descendants могут позиционно переподчиниться предыдущему подходящему item.
- Если grab handle принадлежит выделенному блоку, multi-drag перемещает все явно выделенные блоки — включая разрозненный Shift-selection — одной группой, сохраняя их исходный документный порядок. Невыделенные descendants не добавляются. Если handle не входит в selection, перемещается только этот блок.
- Multi-selection является явным способом перенести поддерево: пользователь выбирает родителя и нужных descendants. После вставки применяется та же нормализация indent.

### Нормализация загруженной модели

- Первый item списка имеет уровень 1.
- Следующий item может быть максимум на один уровень глубже предыдущего.
- Missing, non-numeric, non-finite и значения меньше 1 нормализуются в 1; дробные значения округляются.
- Editor и read-mode применяют одно правило. Некорректная вложенность не делает всю Course Page нечитаемой.

### Обязательные regression scenarios

Будущие model/contract tests должны фиксировать:

1. последовательные ordered siblings и плотную нумерацию;
2. независимые счётчики вложенного и родительского уровней;
3. reset при смене variant на одном уровне и отсутствие reset из-за вложенного списка;
4. split/merge серии обычным блоком и независимость от internal list ID;
5. round-trip порядка, variant и нормализованной вложенности без persisted start number;
6. нормализацию повреждённых indent-последовательностей;
7. результаты single-block и explicit multi-block reorder без автоматического subtree expansion.

Узкий real-browser contract должен воспроизвести историческую регрессию и доказать, что три последовательных ordered items отображаются как `1, 2, 3`, а не `1, 1, 1`, затем проверить:

- создание через `1.` и editor command;
- Enter, empty Enter, Backspace, Tab/Shift+Tab;
- смену ordered/unordered;
- одиночный drag/delete и multi-selection drag;
- Apply/save → повторное открытие editor;
- parity с read-only Course Page;
- семантический read-only DOM: grouped `<ol>/<ul>`, sibling `<li>` и вложенный список внутри parent `<li>`.

Проверки должны утверждать behavior и доступную структуру, не конкретный `listStart`, внутренние IDs, CSS markers или screenshots. Конкретный runner и распределение по browser matrix остаются решению [«Выбрать слоистую стратегию тестирования»](https://github.com/dsc-sgu/mm-frontend/issues/68).
