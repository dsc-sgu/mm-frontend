# Согласовать, является ли Task подтипом блока Course Snapshot

## Вопрос

Является ли Task подтипом блока Course Snapshot (блок особого типа со своими полями) или отдельной сущностью Course, на которую ссылается блок страницы (Task Reference)?

Frontend не выбирает модель данных за backend. Ему нужно поведение из раздела «Контракт, который нужен frontend». Какая модель его обеспечит, решает backend.

## Контракт, который нужен frontend

1. **Стабильная identity.** У Task есть `taskId`, который не меняется между Course Snapshots. На него ссылаются Task Reference, Attempts и Deadline Overrides.
2. **Отдельная правка опубликованной Task.** Свойства опубликованной Task меняются отдельной командой с проверкой версии Task (`409` при несовпадении). Команда не требует Course Editing Lease, не меняет Course Draft Snapshot и не делает его устаревшим.
3. **Черновик хранит только ссылку.** Для опубликованных Tasks Course Draft Snapshot хранит только `taskId`. Отбросить или пересобрать черновик — значит не тронуть опубликованные Tasks.
4. **Новая Task принадлежит черновику.** Свойства и расписание новой Task до публикации — часть Course Draft Snapshot: они сохраняются и отбрасываются вместе с ним. Где именно их хранить, решает backend.
5. **Атомарная публикация.** Публикация Course Draft Snapshot в одной транзакции:
   - создаёт Tasks новых Task References и Task Groups, в которые попала их первая Task;
   - удаляет Tasks, чьи Task References удалены, и Task Groups, из которых ушла последняя Task.

   Создавать и удалять Tasks можно только пока Course `draft` (mm-180 «Спроектировать настройку Task и Task Groups»). После открытия Task Reference можно только перемещать.

Расписание опубликованной Task (Deadline, Deadline Overrides, Task Opening Time) применяется отдельно от публикации (mm-107 «Согласовать task-only apply с существующим course draft», mm-42 «Спецификация: дедлайны Task с переопределениями для Student Groups и Students»). Расписание новой Task до публикации входит в черновик по пункту 4: самой Task ещё нет, применять его отдельно не к чему.

Ни Editing Lease, ни серверный черновик для Task контракт не требует. Правка опубликованной Task — небольшая форма, ей достаточно проверки версии. Хранить неизменяемые версии Task или нет, решает backend, если они нужны Attempts (например, маски на момент сдачи).

Поведение по контракту показывает прототип mm-181 «Запрототипировать настройку Task и дедлайнов»: `?taskApply=contract` на ветке `prototype/task-and-deadline-settings`.

### Почему такой контракт

- **Identity важнее удобства правки.** После открытия Course Task Key и максимальная Grade заморожены, а расписание и так применяется отдельно. Отдельно от Course Page остаётся править условие, маски и аннотацию. Главный довод — identity: Attempts, Deadline Overrides и Reviews ссылаются на Task через поколения snapshot.
- **Если Task — часть snapshot, её правка блокирует коллег или обесценивает их работу.** На `main` Course Editing Lease один на Course ([`course_locks`](https://github.com/dsc-sgu/mm-backend/blob/ddd98496d1293a3cf9844201e70376b3364fdcc3/db/CreateTables.sql#L86-L91)), а публикация проверяет версию Course ([`PublishDraft`](https://github.com/dsc-sgu/mm-backend/blob/ddd98496d1293a3cf9844201e70376b3364fdcc3/internal/courses/service.go#L219-L244)). Тихой перезаписи нет, но:
  - пока коллега правит страницу, исправить опечатку в условии нельзя (`423`), а в модели «Ezhkin-Kot/fixes» — и продлить дедлайн;
  - публикация правки Task делает черновик коллеги устаревшим (`stale_conflict`, [`internal/courses/service.go` L141-L146](https://github.com/dsc-sgu/mm-backend/blob/ddd98496d1293a3cf9844201e70376b3364fdcc3/internal/courses/service.go#L141-L146)). Опубликовать его нельзя, правки страницы приходится переносить вручную.
- **«Task в snapshot, а сроки отдельно» — не третья модель.** Deadline Overrides ссылаются на Task, поэтому у Task должна быть identity вне snapshot. Получается та же отдельная сущность, только её поля поделены между snapshot и хранилищем сроков. Граница не исчезает, а переезжает, и для новой Task её всё равно пересекает публикация (пункт 4).

### Чем «Ezhkin-Kot/fixes» расходится с контрактом

- **Пункт 1:** в каждом поколении snapshot у Task новый `block_id`. Между поколениями Task опознаётся только по паре (`task_group_id`, `name`) (mm-113 «Реестр frontend-вопросов к backend API»).
- **Пункт 2:** свойства Task, включая `deadline_at` и `available_at`, правятся PATCH-ем блока в Course Draft Snapshot и публикуются вместе с ним ([`internal/blocks/repo.go` L23-L44](https://github.com/dsc-sgu/mm-backend/blob/dd05f5fd05b152ecfda4f5ada378349a77716d24/internal/blocks/repo.go#L23-L44)).
- **Пункт 5:** Task Groups создаются и мягко удаляются отдельными запросами, сразу и вне публикации ([`internal/tasks/service.go` L70-L83](https://github.com/dsc-sgu/mm-backend/blob/dd05f5fd05b152ecfda4f5ada378349a77716d24/internal/tasks/service.go#L70-L83), [L157-L171](https://github.com/dsc-sgu/mm-backend/blob/dd05f5fd05b152ecfda4f5ada378349a77716d24/internal/tasks/service.go#L157-L171)).

## Что выполняет mm-backend PR #187

_Проверено на `14a6abb` ветки `nrydanov/frontend-api-alignment`. PR открыт, не влит; это решение бэкенд-команды._

[mm-backend PR #187](https://github.com/dsc-sgu/mm-backend/pull/187) отвечает на вопрос тикета гибридом. Задание — отдельная строка `tasks` с идентичностью: id, цепочка, ключ. Все его настройки — данные блока задания: условие, маски, `maxGrade`, `maxAttempts`, `availableAt`, `deadlineAt`. Блок версионируется. Брони и черновика курса целиком нет, черновик заводится на каждый изменённый блок.

| Пункт контракта | PR #187 |
|---|---|
| 1. Стабильная идентичность | **Выполнен.** `tasks.id` не меняется, попытки ссылаются на него; id блока общий для всех его версий. Переопределений дедлайна, которые на него ссылались бы, нет. |
| 2. Отдельная правка опубликованного задания | **Почти.** `PATCH /tasks/{id}` с версией блока, без брони; если у автора нет черновика блока задания, правка публикуется сразу своей версией и своей точкой публикации, конфликт — `409`. **Открыто:** если блок задания уже в черновике автора (перемещён, новый, уже правились настройки), правка уходит в этот черновик и ждёт публикации страницы. Черновики коллег не устаревают, но правка их черновика того же блока задания при публикации даст конфликт, даже если поля разные: данные сравниваются целиком. |
| 3. Черновик хранит только ссылку | **Нет, но последствия смягчены.** Черновик блока задания несёт все настройки. Отбросить черновики — значит не тронуть опубликованное задание. Черновик блока, который не трогал задание, на него не влияет. |
| 4. Новое задание принадлежит черновику | **Выполнен.** Строка `tasks` создаётся при добавлении блока в черновик, студенты её не видят до публикации, `cancel-edit` удаляет её. Цепочка с первым заданием создаётся сразу, и её имя занято для всех. |
| 5. Атомарная публикация | **Выполнен для публикации.** Публикация создаёт и удаляет задания и цепочки в одной транзакции. Ограничения «только пока курс `draft`» на бэкенде нет. Восстановление точки публикации тоже удаляет задания, появившиеся позже. |

Расписание опубликованного задания в PR #187 публикуется вместе с блоком и откатывается восстановлением точки публикации. Это расходится с абзацем о расписании выше и с решением mm-180. Вопросы — в комментарии mm-113 про PR #187 (3, 4, 10, 12). Поведение можно посмотреть в прототипе mm-181, режим `taskApply: blocks`. Модель целиком — mm-34k14.

## Что зависит от ответа во frontend

- Identity Task между Course Snapshots и то, на что ссылаются Attempts (пункт 1).
- Входят ли свойства Task в Course Draft Snapshot. Рабочее допущение mm-118 «Спроектировать lifecycle Course Page Working Copy» уточнено контрактом: свойства опубликованных Tasks не входят (пункты 2–3), а свойства новой Task до публикации входят (пункт 4).
- Входят ли дедлайны в Course Snapshot (mm-107 «Согласовать task-only apply с существующим course draft»): у опубликованной Task — нет, у новой — до публикации да.
- Версионирование. Схема `data` визуальных блоков Course Page версионируется полем `version` (mm-119 «Спроектировать structured-document seam Course Page»). У Task другой жизненный цикл: на неё ссылаются Attempts, а её свойства редактируются отдельно (mm-41 «Редактировать существующее задание в боковой панели»). Как версия Task сочетается с версией схемы блока?
- Lifecycle редактирования Task (mm-41 «Редактировать существующее задание в боковой панели», mm-107 «Согласовать task-only apply с существующим course draft»). Своих черновиков и lease у Task по контракту нет, поэтому общий lease module из mm-118 «Спроектировать lifecycle Course Page Working Copy» не получит третьего адаптера. Если backend не обеспечит пункт 2, правка Task из просмотра Course потребует Course Editing Lease (вариант A в mm-181).

## Ограничение модели «Task — отдельная сущность Course»

Найдено в mm-181 «Запрототипировать настройку Task и дедлайнов». У каждой Task ровно одна Task Reference, и Task без неё не существует (`CONTEXT.md`, Task Reference). Отсюда:

- создание Task публикуется вместе с Course Draft Snapshot, в котором появилась её Task Reference: опубликовать Task отдельно от ссылки на неё нельзя, а ссылку без Task — тоже;
- удаление Task Reference удаляет Task, поэтому удаление Task тоже публикуется вместе с Course Draft Snapshot;
- до публикации свойства новой Task — часть черновика Course: либо их хранит сам Course Draft Snapshot, либо неопубликованная Task принадлежит этому черновику и публикуется или отбрасывается вместе с ним.

Значит, отдельная Task даёт собственный lifecycle (отдельная публикация с проверкой версии Task) только для уже опубликованной Task. Публикация Course Draft Snapshot при любом ответе должна атомарно создавать и удалять Tasks. Отсюда пункты 4 и 5 контракта. Разница между моделями меньше, чем казалось: она касается только правки свойств опубликованных Tasks.

## Решения frontend, не зависящие от ответа

- Course Page хранит Task Reference — блок только с `taskId`, без свойств Task. Карточка получает Task Summary (title, дедлайн, максимальная Grade и необязательная аннотация Teacher'а; определение в glossary `CONTEXT.md`) вместе с состоянием доступа зрителя (`open | locked { prerequisite }` для Student'а) через отдельный seam `taskId → Task Summary + доступ | unavailable` (mm-119 «Спроектировать structured-document seam Course Page»).
- Task Reference допускается только на верхнем уровне Course Page и не может лежать внутри Spoiler. Это продуктовое решение, а не ограничение backend (там же).
