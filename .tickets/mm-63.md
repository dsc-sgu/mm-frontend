## Согласовано: mocks и будущий transport boundary

### Наблюдение по текущей реализации

Feature-local RAM-моки образуют несколько частично связанных stores. Одни и те же концепции — courses, memberships, tasks, student attempts, grades и review — представлены в разных модулях независимо, а согласованность поддерживается cross-feature imports и ручными mutations соседних mock stores. Это позволяет демонстрировать отдельные экраны, но не образует единого server-state model.

### Принятое направление

- Frontend feature-модули должны обращаться к feature-local fetch clients, а не импортировать mocks напрямую.
- Development/test запросы будет обслуживать один stateful mock backend adapter за HTTP/MSW seam.
- Mock backend владеет единым каноническим состоянием; attempts list, task history, attempt review, journal и другие read models строятся как projections из одних сущностей.
- «Единый mock backend» означает одну state/operation boundary и одну точку composition, а не один гигантский файл: handlers и внутренние operations остаются разделены по ответственности.
- Mock backend создаётся как resettable instance, а не как набор module-level singleton stores.
- Детерминированные seed-сценарии задают начальное согласованное состояние мира. Состояние продолжает изменяться после mutations; сценарий не является набором заранее записанных endpoint responses.
- Latency, HTTP failures и другие transport profiles конфигурируются отдельно от seed-данных.
- Текущие одноразовые mock-форматы не принимаются автоматически как окончательный HTTP-контракт.

## Согласовано: state ownership и кандидаты в follow-up tickets

### Уточнённые решения

- Route parameter текущей попытки означает `attemptNumber`, а не `attemptId`: это порядковый номер попытки студента в контексте курса, задания и студента.
- Внутренний backend UUID попытки допустим, но frontend route и пользовательская модель остаются основаны на `attemptNumber`; будущий transport contract должен явно связать эти два identity.
- Course draft в целевой архитектуре является persistent server snapshot. Локальное frontend-состояние — только working copy и изменения, ещё не подтверждённые сервером.
- Предупреждение при SPA navigation, reload или закрытии вкладки нужно показывать при наличии **несинхронизированных локальных изменений**, а не просто при существовании server draft.
- Review-lock updates в целевой архитектуре должны приходить от backend через WebSocket. Frontend subscription adapter применяет события к TanStack Query cache или инвалидирует соответствующий scope.
- Runtime source of truth темы — класс на корневом `<html>`. `localStorage` сохраняет preference для следующего запуска, а pre-React bootstrap применяет его без мерцания. Это соответствует mm-10 «Save chosen theme to localStorage and load system theme».
- Generic abstraction для `localStorage` требует отдельного исследования; она не должна создавать второй RAM source of truth для темы.

### Backend research

Исследованы backend `main`, связанные ветки, pull requests, issues и ADR. Результат закреплён отдельным research-коммитом:

- [research commit `a25a8ed`](https://github.com/dsc-sgu/mm-frontend/commit/a25a8ed9f8c485f5aaad5ba0beba4f7909a9cf63)
- [Backend snapshots, drafts, attempts, and frontend integration](https://github.com/dsc-sgu/mm-frontend/blob/a25a8ed9f8c485f5aaad5ba0beba4f7909a9cf63/docs/research/backend-snapshots.md)

Research подтвердил, что backend `main` уже реализует persistent course draft snapshots, PostgreSQL lease с heartbeat, `new` / `restored` / `stale_conflict`, optimistic concurrency, explicit publish/cancel и snapshot timeline. Текущий frontend whole-course save не соответствует этому протоколу, поэтому подключение backend потребует изменения editor lifecycle, а не простой замены mock-функции на `fetch`.

### Кандидаты в отдельные tickets

1. **Переименовать frontend route identity попытки из `attemptId` в `attemptNumber`.**
   - Обновить route params, props, model vocabulary, query identity и mock/MSW contracts.
   - Явно сохранить составной контекст: course + task + student + attempt number.
   - Согласовать отображаемый номер с внутренним backend UUID до фиксации attempts HTTP contract.
   - Эту работу следует завершить до attempts/review slices в mm-73 «Перевести frontend с RAM-моков на fetch и MSW».

2. **Предупреждать об уходе с несинхронизированными изменениями.**
   - Покрыть SPA navigation через router blocker и reload/закрытие вкладки через `beforeunload`.
   - Первый consumer — course page editor; interface должен позже принимать sync-state server-backed draft, а не быть навсегда привязанным к текущему `isDirty`.
   - Не пытаться полагаться на асинхронное сохранение во время `beforeunload`.

3. **Декомпозировать frontend-интеграцию persistent course snapshots.**
   - Это будущий набор tracer-bullet tickets, а не один широкий implementation issue.
   - В scope входят lock/init state machine, `new` / `restored` / `stale_conflict`, загрузка server draft, отдельные block mutations, autosave/debounce и acknowledgement, heartbeat/lease loss, snapshot timeline/switch, publish/cancel и `409 Conflict` UX.
   - Перед реализацией нужно согласовать course metadata vs snapshot-content boundaries и проверить backend concern: `CancelEdit` сейчас может discard-нуть draft без предварительной проверки session-bound lease.
   - Декомпозиция должна ссылаться на research commit и координироваться с course-editing slice MSW-миграции, чтобы MSW не закрепил устаревший whole-course-save contract.

4. **Согласовать и реализовать WebSocket transport для review-lock updates.**
   - Пока это deferred item: backend WebSocket/event contract отсутствует.
   - До frontend implementation нужно определить subscription scope, event schema, entity revision/sequence, reconnect и authoritative resync.
   - После появления контракта frontend adapter должен интегрировать события с TanStack Query, не создавая отдельный attempts store.

5. **Исследовать React/localStorage abstraction.**
   - Сравнить готовые библиотеки, project-level adapter и feature-local hooks.
   - Проверить same-tab/cross-tab synchronization, schema validation/migrations, unavailable/quota errors, SSR/pre-React initialization и отсутствие theme flash.
   - Отдельно зафиксировать, что theme остаётся DOM-owned special case, тогда как обычные preferences вроде diff view mode могут использовать reactive storage hook.

## Решение: согласованная карта реализованной frontend-системы

Ниже отделены **наблюдения по текущему коду** от **подтверждённого продуктового контекста** и от будущей поверхности, для которой пока существуют только route shells и backlog.

### 1. Назначение продукта

MergeMinds — LMS для практики на заданиях, приближенных к реальным программным проектам. Студент ведёт работу и сдаёт попытки через Git; преподаватель проверяет изменения в модели, похожей на review pull/merge request на Git-хостингах.

Это не вывод только из названий текущего UI. Назначение подтверждено владельцем системы, материалами проекта в AnyType и статьёй [«Построение образовательной платформы вокруг системы контроля версий Git»](https://elibrary.ru/download/elibrary_80287768_33682076.pdf). Мотивация включает:

- сохранение промежуточных версий и развитие прикладных Git-навыков у студентов;
- работу с заданиями в форме, близкой к командной разработке;
- фиксацию попытки как состояния репозитория в определённый момент;
- просмотр преподавателем релевантного diff вместо повторного чтения всей работы;
- надёжную фиксацию времени и авторства отправки;
- уменьшение стоимости проверки и сохранение истории обратной связи.

AnyType-страницы `MergeMinds`, `Ругаюсь на Moodle`, `Фронтенд MergeMinds`, `Обсуждение MergeMinds 7.02.2026`, `Ревью MR на задания и попытки` и `Изменение заданий и шаблонного репозитория MergeMinds, когда студенты на него уже зашли` уточняют предметную область: course content, tasks/task groups, student repositories, immutable attempt snapshots, filtered diffs, review history, grades и course snapshots. Эти материалы содержат также открытые и меняющиеся идеи; поэтому они подтверждают направление продукта, но не считаются доказательством уже реализованного frontend-поведения.

### 2. Runtime composition

Наблюдаемая композиция (`src/main.tsx`, `src/routes/__root.tsx`, `src/routes/_authenticated.tsx`):

```text
Browser
└─ React StrictMode
   └─ QueryClientProvider ─────────────┐
      └─ TanStack Router              │ один QueryClient
         ├─ route guards ─────────────┘
         └─ root shell
            ├─ RouterPending
            ├─ Header
            ├─ Route Outlet
            └─ Toaster
               └─ authenticated subtree
                  └─ AttemptReviewWorkerPool
```

- Router владеет navigable identity, validated search state, route context и guards.
- Router guards и UI используют один TanStack Query client.
- TanStack Query играет роль cache/server-state слоя даже там, где фактический источник — RAM mock.
- Feature pages координируют Query, локальные drafts и UI.
- Review worker pool монтируется на весь authenticated subtree, а не только на Attempt page и Review editor.
- `window.__TANSTACK_QUERY_CLIENT__` — глобальный escape hatch к тому же Query client, а не отдельный store.

### 3. Route surface и степень реализации

Pathless `_auth` и `_authenticated` route groups в URL не видны.

```text
/
├─ login / register                                      реализовано
└─ authenticated dashboard                               реализовано
   └─ courses/:courseSlug
      ├─ /                                                course page реализована
      ├─ /edit                                            course-page editor реализован
      ├─ /attempts                                        teacher Course Attempts реализован
      ├─ /tasks/:taskId                                   task page/history реализована
      │  ├─ /edit                                         placeholder
      │  └─ /attempts/:studentUsername/:attemptId
      │     ├─ /                                          readonly review реализовано
      │     └─ /review                                    editable teacher review реализовано
      ├─ /repositories/...                                placeholders
      ├─ /journal                                         placeholder
      ├─ /files                                           placeholder
      └─ /stats                                           placeholder
```

Рабочее ядро текущего frontend: **course content → task/attempt history → attempts triage → diff review/grading**, плюс редактирование course landing page. Оно демонстрирует значимую часть целевого review UX, но ещё не является интегрированным Git-to-review production flow: non-auth domain data поступает из локальных mocks.

#### Конкретное уточнение про teacher-only URL

В teacher navigation отображаются `Журнал` и `Аналитика`, но у соответствующих route files нет собственного `beforeLoad` с `requireCourseRole(... roles: ['teacher'])`:

- `/courses/:courseSlug/journal` — `src/routes/_authenticated/courses/$courseSlug/journal.tsx`;
- `/courses/:courseSlug/stats` — `src/routes/_authenticated/courses/$courseSlug/stats.tsx`.

Поэтому студент, уже допущенный к курсу parent route, может открыть эти placeholder-страницы прямым URL. В student navigation ссылок на них нет. Остальные проверенные teacher-only surfaces — `/attempts`, `/files`, `/edit`, repository list, task edit и editable attempt review — имеют явный role guard.

Желаемая access policy для журнала и аналитики пока **не определена**: остаётся открытым продуктовый вопрос, должны ли студенты видеть эти разделы. Наблюдаемый факт карты: текущий код выражает две разные подсказки — teacher-only navigation и отсутствие teacher-only route guard. Поэтому это фиксируется как неоднозначность реализации, а не как дефект относительно уже принятого требования. Решение вынесено в mm-99 «Определить доступ студентов к журналу и аналитике курса».

### 4. Feature-модули

- `auth` — session/login/register/logout; единственный модуль с реальной Axios-веткой.
- `course` — course summaries, routing policy, theme и content rendering.
- `course/access` — course-local membership и role.
- `course/page` — отображение course landing content.
- `course/page-edit` — provider-scoped Zustand working copy, Plate blocks, DnD, validation и whole-page save.
- `course/task` — task details, attachments и student attempt history.
- `course/attempts` — teacher filters, virtualized list, selection, quick grading и simulated locks.
- `course/attempt-review` — file tree, unified/split diffs, comments/replies, feedback, score и review history.
- `course/grading` — переиспользуемая score-модель.
- `deadlines-calendar` — dashboard projection из mock deadlines.
- `code-block` и `shadcn` — технические UI-модули.

### 5. Владение состоянием

| Вид состояния | Наблюдаемый владелец |
|---|---|
| Session, course/page/task/attempt/review data | TanStack Query cache |
| Path identity и применённые attempts filters | URL/TanStack Router |
| Draft filters, drawers, selection, quick grading | Локальный React/reducer state |
| Course editor working copy | Provider-scoped Zustand store |
| Review draft и layout state | Локальное состояние Review editor и Attempt page |
| Diff view preference | `localStorage` |
| Theme runtime presentation | класс на `<html>`; preference сохраняется в `localStorage` |
| Measurements/focus/scroll/copy feedback | DOM refs, `requestAnimationFrame`, timers |
| Review-lock updates | interval, напрямую изменяющий Query cache |

Согласованное целевое уточнение:

- course draft является persistent server snapshot;
- frontend editor хранит только working copy и несинхронизированные изменения;
- уход блокируется именно при наличии несинхронизированных локальных изменений;
- review-lock updates в будущем приходят по WebSocket и применяются через Query cache/invalidation;
- route identity попытки означает `attemptNumber`, а не backend `attemptId`/UUID;
- runtime source of truth темы — класс на корневом `<html>`.

### 6. Data/mocks composition

```text
feature query hooks
└─ feature-local async mock functions
   ├─ course catalogue
   ├─ course-page store ──mutates──> catalogue/access
   ├─ task attempt-history store
   ├─ attempts-list store
   ├─ review-series store ──partly mutates──> attempts list
   ├─ deadlines generator ──reads──> catalogue
   └─ fixed auth session
```

Текущие RAM mocks не образуют единую server-state model:

- task history, attempts list и review series независимо моделируют попытки;
- только некоторые mutations синхронизируют соседние stores;
- refresh уничтожает изменения;
- deadlines пересоздаются случайно;
- course rename переносится только в часть stores;
- mock logout не меняет session;
- очистка review grade может оставить прежнюю grade в attempts list.

Согласованное направление подробно зафиксировано в предыдущем решении этого тикета: feature-модули обращаются к feature-local fetch clients, а development/test запросы обслуживает единый resettable stateful mock backend через HTTP/MSW seam. Read models строятся как projections из одного канонического состояния; seed scenarios и transport profiles разделены.

### 7. Основные реализованные пользовательские потоки

1. Login/register → session guard → dashboard → выбор курса.
2. Student: course/task → attempt history → readonly feedback/review.
3. Teacher: attempts filters → selection/quick grading → review.
4. Teacher: file/diff navigation → line comments/replies → feedback/score save.
5. Teacher: course page editor → local working copy → whole-page mock save.
6. Teacher: task page → prefiltered attempts или placeholder task editor.

### 8. Наблюдаемые противоречия и незавершённые границы

- `courseId` фактически используется как editable route slug; отдельная immutable identity во frontend-модели не выражена.
- Route `attemptId` фактически содержит порядковый `attemptNumber`; в attempts list при этом есть отдельный string `id`.
- Auth role и course-local role могут противоречить друг другу в fixtures.
- `Task` и `Assignment`, а также разные значения слова `Review`, пока образуют неоднозначный язык.
- Guards проверяют syntax/access, но не всегда существование task/attempt.
- Для `/journal` и `/stats` access policy неоднозначна: ссылки находятся только в teacher navigation, но route guards не запрещают прямой доступ студенту; желаемое продуктовое поведение пока не решено.
- Course editor не имеет явной rebase/conflict policy при обновлении Query data того же курса.
- Simulated lock timer может менять attempts cache рядом с quick-grading draft.
- Часть course/task/repository route tree — только placeholders.

### 10. Итоговая граница карты

Код уже реализует узнаваемый frontend-прототип Git-oriented LMS вокруг course authoring, attempts triage и pull-request-like review. Router/Query/local-state ownership в основном читается, но domain/server state сейчас эмулируется несколькими несогласованными RAM stores. Repository, grade journal, files, analytics и task editing представлены маршрутами и backlog, но не должны описываться как готовые пользовательские потоки. Simulated review locks являются заготовкой под backend realtime protocol.

Production/source code в рамках решения не изменялся.
