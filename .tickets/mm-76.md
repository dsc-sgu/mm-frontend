# Унифицировать ключи запросов и правила согласованности кеша

## Проблема

Ключи TanStack Query объявлены несколькими способами: строковыми константами, массивами, отдельными функциями и частично внедрёнными фабриками. После mutations согласованность поддерживается импортами чужих констант и ручной сборкой ключей. Это затрудняет изменение структуры ключа и делает связи между mutation и затронутыми представлениями неявными.

Первоначальное направление этого issue предполагало broad invalidation всего Course scope по умолчанию. Оно уточнено решением [«Выбрать frontend transport/API seam и правила cache invalidation»](https://github.com/dsc-sgu/mm-frontend/issues/108): безопасным default остаётся минимальная корректная targeted invalidation, а весь Course scope инвалидируется только при фактическом изменении всего scope.

Нормативные правила находятся в [`docs/agents/remote-data.md`](https://github.com/dsc-sgu/mm-frontend/blob/main/docs/agents/remote-data.md). Реализация должна следовать актуальной версии документа.

## Целевая форма

Каждое семейство query владеет типизированным объектом фабрики ключей. Даже семейство с одним ключом использует минимальную фабрику, чтобы проект имел один способ объявления ключей.

```ts
export const sessionKeys = {
  all: ['session'] as const,
};
```

Параметризованное семейство выражает иерархию от общего scope к точному представлению:

```ts
export const courseAttemptsKeys = {
  all: ['course-attempts'] as const,
  course: (courseSlug: string) =>
    [...courseAttemptsKeys.all, courseSlug] as const,
  list: (courseSlug: string, filters: CourseAttemptsFilters) =>
    [...courseAttemptsKeys.course(courseSlug), { filters }] as const,
};
```

Родительский Course module предоставляет общий course scope, который вложенные feature-модули расширяют без ручного повторения его структуры. Конкретный locator должен соответствовать входу query; переход со slug на immutable Course ID выполняется только после согласования transport identity contract.

Другие feature-модули могут использовать публичную фабрику владельца, но не импортируют raw root constants и не собирают чужие tuples вручную. Содержательная cache-функция создаётся только для повторяемого, многосоставного или инвариантного поведения; однострочные обёртки над очевидным вызовом `QueryClient` не требуются.

## Правила обновления после mutation

1. Сначала определить полный stale scope mutation.
2. Если mutation вернула полное провалидированное авторитетное представление точного cache entry, обновить его immutable-вызовом `setQueryData`.
3. Затронутые filtered, sorted, paginated и derived representations инвалидировать минимальным корректным prefix.
4. Не воспроизводить backend business logic во frontend ради ручного обновления derived cache.
5. Не инвалидировать весь Course scope только ради гипотетических будущих projections.
6. Broad invalidation применять только когда mutation действительно изменяет весь scope либо более узкий стабильный scope невозможно выразить.
7. Cross-feature consistency координировать явно через фабрики ключей или содержательные helpers владельцев cache.

## Изменения

- Перевести на единый `<область>Keys`-стиль:
  - session;
  - список Courses;
  - Course Page;
  - Course Access;
  - Task Page;
  - Attempts list;
  - Attempt Review;
  - Deadlines.
- Сохранить и привести к общей форме уже начатые фабрики `taskPageKeys`, `getWeekQueryKey` и `getAttemptReviewQueryKey`.
- Для course-scoped queries создать общий иерархический prefix текущего Course.
- Удалить cross-feature imports raw key constants и ручную сборку чужих keys.
- Переписать post-mutation consistency согласно правилам выше.
- Сохранение Course Page должно отдельно обработать точный detail entry, список Courses, Deadlines, Access и старый/новый locator при смене slug; не инвалидировать несвязанные Course Page entries.
- Сохранение Attempt Review должно обновить точный Review entry из авторитетного ответа, если такой ответ доступен, и инвалидировать затронутые Attempts projections.
- Quick grading должно инвалидировать либо обновлять только затронутый Course/Attempts scope.
- Существующий optimistic transition Review Read State в `seen` сохранить, приведя его keys к общей фабрике; он уже использует cancel, snapshot, immutable update, rollback и reconciliation.

## Критерии готовности

- Все query families используют типизированные readonly key factories одного проектного стиля.
- Каждый key включает все входные данные, изменение которых меняет результат `queryFn`.
- Все course-scoped query keys расширяют один общий Course prefix.
- Ни один feature не импортирует raw key constant другого feature и не собирает его key вручную.
- Содержательные helpers существуют только для нетривиального или повторяемого cache behavior.
- Mutation response обновляет точный cache entry только при наличии полного провалидированного авторитетного представления.
- Derived и неполные representations используют минимальную корректную invalidation.
- Broad Course invalidation отсутствует там, где mutation затрагивает известный более узкий scope.
- Cache updates выполняются immutable.
- UI и domain model не зависят от представления query keys.
- Поведение `seen`, Quick Grading, Course Page save и Attempt Review save проверено через соответствующие пользовательские сценарии.
- `bun run lint` и `bun run build` проходят.

## Вне области

- Замена TanStack Query.
- Сокрытие TanStack Query за transport-agnostic `refresh*` interface.
- Собственная tag-based invalidation framework или event bus.
- Нормализованный entity cache.
- Миграция RAM-моков на MSW.
- Проектирование окончательного backend API.

## Согласование с решениями вертикалей

Решения [«Спроектировать Course access vertical и identity seam»](https://github.com/dsc-sgu/mm-frontend/issues/115), [«Спроектировать individual Course Attempts vertical»](https://github.com/dsc-sgu/mm-frontend/issues/117) и [«Спроектировать Review → Grade → Student result vertical»](https://github.com/dsc-sgu/mm-frontend/issues/116) уточняют форму ключей из этого issue.

- **Identity.** Course-scoped keys используют стабильный `CourseId`, а не `courseSlug`. Вне общего prefix остаётся только поиск Course по slug (`courseContextKeys` с `UserId` и slug), потому что его вход — slug.
- **Общий prefix подтверждён.** Все course-scoped keys расширяют `['course', courseId, …]`. Примеры keys вида `['course-pages', courseId]` и `['course-attempts', courseId, …]` в решениях Course access и Course Attempts считаются иллюстрацией. Общий prefix позволяет одним вызовом удалить cached content Course при подтверждённой потере Membership.
- **Course Attempts.** Семейство называется `courseAttemptsKeys`; фильтры нормализуются в key.
- **Review.** Семейство `reviewKeys` принадлежит nested feature `review`. Содержательный helper владельца `observeReviewRevision(queryClient, { attemptId, courseId, taskId, studentId, revision })`:
  - монотонно пишет авторитетную Review в свой cache, отменяя идущий запрос;
  - инвалидирует selector Attempts, Course Attempts и историю попыток Student'а по prefix через их публичные key factories, не читая чужих данных.

  Его вызывают публикация, загрузка Review, quick grading и будущий SSE. Это не event bus.
- **Сохранение Attempt Review.** Пункт этого issue реализуется slices 2 и 6 Review vertical: точный cache Review из авторитетного ответа и инвалидация проекций через `observeReviewRevision`.
