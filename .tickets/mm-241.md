# Правило размещения состояния: vanilla-стор Zustand вместо самописных сторов

## Проблема

Агенты регулярно пишут собственный стор (`Set` слушателей, `subscribe`/`getSnapshot`, `useSyncExternalStore`) там, где в проекте уже есть Zustand. Последний случай: стор готовности diff в #238 сначала был самописным, потом его переделали на `zustand/vanilla` (коммит 83dcea7).

Причина в документации. Раздел «State modeling» в AGENTS.md говорит «Prefer small transition functions or reducers before adding an FSM library» и «Do not add FSM libraries…», но ни слова не говорит, что Zustand — стор проекта и когда его брать. Агент читает это как «без библиотек, пиши сам».

## Что сделать

### 1. AGENTS.md: правило «где живёт состояние»

Добавить в «State modeling» правило выбора:

- **Состояние одного компонента** (или компонента и его прямых детей) — `useState` / `useReducer`. Переходы — чистая функция в `model/`, если у состояния есть жизненный цикл.
- **Серверные данные** — TanStack Query (см. `docs/agents/remote-data.md`).
- **Vanilla-стор Zustand** — для состояния, которое кто-то рисует и на изменения которого нужно реагировать, если выполняется хотя бы одно:
  - состояние делят компоненты, между которыми иначе пришлось бы пробрасывать props или колбэки через несколько уровней;
  - состояние живёт дольше компонента, который его показывает;
  - состояние меняется извне React (Workers, таймеры, подписки, внешние объекты с колбэками);
  - логику переходов нужно тестировать без React.
- **Как устроен стор:**
  - `createStore` из `zustand/vanilla` в `model/` фичи, рядом с переходами;
  - экземпляр создаётся на время жизни маршрута/страницы и передаётся через контекст;
  - читается через `useStore(store, selector)` в `hooks/`;
  - ресурсы, которые не рисуются (Workers, подписки), держатся в замыкании стора, а не в его состоянии.
  - Образцы: `page-edit/model/editor-store` + `page-edit/hooks/use-editor-store.ts`, `attempt-review/model/diff-readiness.ts` + `hooks/use-diff-readiness.ts`.
- **Нереактивная ячейка или кэш** — не стор. Если данные пишут при изменении и читают только при монтировании (начальное значение `useState`), подписчиков нет — это обычный объект (`Map`) в контексте или `useRef`, поднятый выше места размонтирования. Zustand здесь лишний: уведомления никому не нужны, а `set` на каждое изменение копировал бы данные. Образец: `attempt-review/model/unsent-comment-text.ts`.
- **Явный запрет:** не писать руками `listeners`/`subscribe`/`getSnapshot`/рассылку подписчикам.
- **`useSyncExternalStore`** — только как адаптер к браузерному API (`matchMedia`, `MutationObserver` и т. п.), как `src/hooks/use-media-query.ts`.
- **Состояние, которое нужно до загрузки бандла** (например, тема из inline-скрипта в `<head>`), живёт в DOM/`localStorage`; React читает его через адаптер, а не дублирует в сторе.
- **Уточнить** существующий абзац: запрет на FSM-библиотеки касается xstate/robot и подобных, а не Zustand. Zustand — не FSM-библиотека, а контейнер состояния; переходы внутри него по-прежнему пишутся явными функциями по правилам ADT/FSM.

Правило должно отвечать на вопрос «почему не Zustand?» так же явно, как «почему Zustand?»: стор не нужен для состояния одного компонента.

### 2. ESLint: механическая страховка

Документацию агент может не перечитать; ошибка линта появляется в момент написания кода.

- `no-restricted-imports` (или эквивалент): запретить импорт `useSyncExternalStore` из `react` везде, кроме адаптеров браузерных API. Сейчас это `src/hooks/use-media-query.ts` и `src/features/course/features/attempt-review/hooks/use-html-theme.ts`.
- Сообщение правила должно указывать путь, например: «State outside React → zustand/vanilla store in the feature's model/ (AGENTS.md: State modeling). useSyncExternalStore is only for browser API adapters.»
- Упомянуть правило в AGENTS.md рядом с правилом, как сделано для `no-nested-ternary`.
- Ручной `Set` слушателей линтом надёжно не ловится — его закрывает п. 1.

### 3. Рефакторинг расходящихся мест

По каждому кандидату — решение по правилу из п. 1: переделать или оставить с объяснением в PR.

| Место | Что сейчас | Ожидание |
|---|---|---|
| `attempt-review/page.tsx` | 7 `useState` раскладки страницы (`activeFilePath`, свёрнутость панелей, `mobileDrawer`, `diffViewMode`), пробрасываются в дочерние компоненты | Оценить по критерию «пробрасывание через несколько уровней». **Не трогать** состояние черновика Review (Grade, Overall Feedback, комментарии) — его перестраивает epic #218 (REV6/REV7) |

Проверено и соответствует правилу, менять не нужно:
- `src/hooks/use-media-query.ts` — адаптер браузерного API.
- Тема: класс `dark` на `<html>` + `localStorage`, `ToggleThemeBtn` в `src/app/header/ui/header.tsx`, `attempt-review/hooks/use-html-theme.ts`. Источник правды — DOM **намеренно**: inline-скрипт в `<head>` `index.html` выставляет класс до загрузки бандла (без вспышки светлой темы), поэтому стор в JS не может быть первичным. `use-html-theme` — законный адаптер к DOM через `MutationObserver` и остаётся исключением ESLint с этим обоснованием в комментарии.
- `attempt-review/model/unsent-comment-text.ts` + `hooks/use-unsent-comment-text.ts` — нереактивная ячейка: CodeView размонтирует карточку комментария, когда файл уходит из отрисованного окна или переключается вид Markdown; карточка пишет неотправленный текст на каждое изменение и читает только при монтировании, живой текст — в её `useState`. Подписчиков нет, поэтому не стор.
- `attempts/hooks/use-grading.ts` — `useReducer` состояния одной страницы с переходами-функцией.
- `src/app/testing/diff-workers.ts` — тестовый фейк, повторяет API `DiffWorkerPool`, а не стор приложения.
- `attempt-review/model/diff-readiness.ts` — уже на `zustand/vanilla` в #238.
