# Восстанавливать несинхронизированную рабочую копию страницы курса из браузера

## Источники

- mm-118 — жизненный цикл рабочей копии страницы курса.

## Делает

После MVP добавляет восстановление неподтверждённой рабочей копии страницы курса из хранилища браузера — только для правок, которые сервер отклонил или не получил за долгий офлайн (раздел «Уже решено»). Черновик курса на сервере остаётся источником истины; локальная запись — только кандидат на восстановление изменений, которые сервер ещё не подтвердил.

## Готово, когда

- [ ] Несинхронизированные изменения сохраняются локально с идентичностью курса и известной базой — черновиком курса на `main` бэкенда или версиями блоков в модели mm-backend PR #187.
- [ ] После перезагрузки восстановление предлагается только после загрузки черновика с сервера и проверки, совместима ли с ним локальная запись.
- [ ] Совместимая запись не применяется автоматически: преподаватель явно выбирает восстановить её или удалить.
- [ ] Несовместимая, устаревшая, повреждённая или неизвестной версии запись не смешивается с черновиком на сервере, и её можно безопасно удалить.
- [ ] Подтверждённые сервером операции удаляются из локального журнала восстановления; публикация, отмена и явный сброс очищают связанную запись.
- [ ] Выход из аккаунта или смена сессии не позволяют следующему пользователю восстановить чужую рабочую копию.
- [ ] Отказ локального хранилища не блокирует открытие и редактирование черновика на сервере; интерфейс не сообщает о ложном успехе восстановления.
- [ ] Решение не превращает локальное хранилище во второй источник истины и не вводит автоматическое слияние или перебазирование.
- [ ] Сценарии сбоя и перезагрузки, устаревшей базы, явного восстановления и сброса, очистки проверены через наблюдаемое поведение.

## Уже решено

_Решено владельцем 2026-10-25:_ тикет остаётся в бэклоге с низким приоритетом и нужен только для отказов синхронизации: сервер отклонил правку (`sync-rejected`) или преподаватель долго был офлайн.

Почему так. В модели [mm-backend PR #187](https://github.com/dsc-sgu/mm-backend/pull/187) (mm-34k14) черновики блоков хранятся на сервере и переживают уход из редактора, а фоновая синхронизация пишет их через 1–5 с после правки. Правки последних секунд покрывает защита от ухода (DRF-12, DRF-13). Потерять можно только то, что сервер отклонил или так и не получил. Ещё одна причина держать тикет: черновики общие для всех устройств преподавателя, и версия черновика при записи не растёт (вопрос 5 комментария mm-113 про PR #187). Если правку перезапишут с другого устройства, локальная запись — единственная копия.

Критерии выше написаны до этого решения. Когда тикет возьмут в работу, их нужно сузить до этих двух случаев.

## Зависит от

- Стабильные идентичности черновика и семантика подтверждений и ревизий в согласованном контракте API фронтенда и бэкенда.
