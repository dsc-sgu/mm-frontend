# Восстанавливать несинхронизированную Course Page Working Copy из браузера

## Source

[Спроектировать lifecycle Course Page Working Copy](https://github.com/dsc-sgu/mm-frontend/issues/118)

## What to build

После MVP добавить browser-local recovery для неподтверждённой Course Page Working Copy. Server-backed Course Draft Snapshot остаётся authoritative state; локальная запись является только кандидатом на восстановление изменений, которые ещё не получили acknowledgement.

## Acceptance criteria

- [ ] Несинхронизированные изменения сохраняются локально с identity Course, Course Draft Snapshot и известной server revision/base identity.
- [ ] После reload восстановление предлагается только после загрузки authoritative server draft и проверки совместимости локальной записи с ним.
- [ ] Совместимая запись не применяется автоматически: Teacher явно выбирает восстановить её или удалить.
- [ ] Несовместимая, stale, повреждённая или неизвестной версии запись не смешивается с server draft и может быть безопасно удалена.
- [ ] Acknowledged operations удаляются из локального recovery journal; publish, cancel и явный discard очищают связанную запись.
- [ ] Logout/session replacement не позволяет следующему User восстановить чужую Working Copy.
- [ ] Отказ local storage не блокирует открытие и редактирование server-backed draft; UI не сообщает ложный success восстановления.
- [ ] Решение не превращает local storage во второй authoritative persistence layer и не вводит автоматический merge/rebase.
- [ ] Сценарии crash/reload, stale base, explicit restore/discard и cleanup проверены через наблюдаемое поведение.

## Blocked by

- Завершение решения [«Спроектировать lifecycle Course Page Working Copy»](https://github.com/dsc-sgu/mm-frontend/issues/118).
- Наличие стабильных draft identity и acknowledgement/revision semantics в согласованном frontend/backend contract.

Вкладки одного браузера делят редактор локально: пишет одна, остальные показывают живую копию, «Продолжить здесь» передаёт Working Copy. Поведение нескольких вкладок и восстановление из браузера нужно согласовать с [«Спроектировать смену пишущей вкладки редактора»](https://github.com/dsc-sgu/mm-frontend/issues/132): живая копия в соседней вкладке уже хранит неотправленные правки, а общий storage и привязка к `UserId` у обоих механизмов одни.
