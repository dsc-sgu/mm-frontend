# Синхронизировать добавление, перемещение и удаление content blocks

## Parent

mm-78 «Перевести course dashboard и редактирование курса на общий mock backend»

## What to build

Сохранять добавление, перемещение и удаление content blocks как согласованные atomic operations над persistent draft вместо отправки полной копии курса.

## Acceptance criteria

- [ ] Новый блок создаётся в выбранной позиции и получает server identity после acknowledgement.
- [ ] Перемещение сохраняет порядок после refetch и reload.
- [ ] Удаление исчезает из draft после подтверждения и не затрагивает published snapshot.
- [ ] Несколько pending structural operations не повреждают порядок и не теряют working copy при ошибке.
- [ ] Reset/discard возвращает согласованное server draft state.
- [ ] Whole-course save больше не нужен для content structure.
- [ ] Lint и build проходят.

## Уточнения из mm-118, комментарий от 2026-10-09T22:31:46Z «Спроектировать lifecycle Course Page Working Copy»

Синхронизация больше не делится по видам изменений: изменение существующего блока, добавление, перемещение и удаление блоков, а также metadata и resources обрабатывает один планировщик `planDraftSync(base, workingCopy)` (ADR 0002 в [PR #127](https://github.com/dsc-sgu/mm-frontend/pull/127)). Этот issue покрывается slice 2 «Сессия черновика» (планировщик выполняется перед публикацией) и slice 3 «Фоновая синхронизация».

- Синхронизация фоновая: после ~1 с бездействия, не реже раза в 5 с, сразу при уходе и публикации. Одновременно в полёте один batch.
- Состояние `sync`: `synchronized | pending | syncing | sync-failed | sync-rejected`; индикатор «Сохранено» / «Сохранение…» / «Не сохранено · Повторить».
- Неизвестный исход операции: черновик перечитывается, становится новой базой, план строится заново. Отказ backend по операции останавливает batch (`sync-rejected`), Working Copy не теряется.
- Пока сервер назначает id блоков, сопоставление локальных и серверных id живёт внутри модуля синхронизации.
- Явного «Сохранить черновик» и `Mod+S` для сохранения нет.

Каноническим источником является решение по ссылке выше. Окончательную нарезку на implementation-тикеты определит mm-69 «Определить последовательность подготовки и выполнения рефакторинга».
