# Выбрать persisted contract review-текста при переходе на Plate

## Question

Какой persisted contract использовать для overall feedback, line comments и replies после замены TipTap на Plate: сохранить sanitized HTML на transport/API boundary с явной Plate serialization/deserialization либо перейти на структурированную rich-text model? Решение должно определить каноническое представление в domain state, границу sanitization, поддержку links/images/lists/code, readonly rendering и допустимость потери текущих mock-данных; конкретная реализация editor cutover остаётся вне planning-only карты.

## Решение: Plate-native structured contract review-текста

### Каноническая модель

- **Overall Feedback**, root message в **Line Comment Thread** и reply используют один persisted contract: `ReviewTextDocument`.
- `ReviewTextDocument` — versioned project-owned schema вида `{ version: 1, children: ReviewTextBlock[] }`. Форма nodes естественна для Slate/Plate и после validation почти напрямую используется как Plate `Value`.
- Это не независимый domain AST уровня Course Page и не raw library contract. Feature владеет Valibot schema и разрешённым subset; произвольные plugin/runtime fields, selection, history и editor instance state не persist-ятся.
- Author, timestamps, identity, line anchor и lifecycle message остаются полями Review/Thread model вне rich-text document.

### Разрешённая семантика v1

Один компактный профиль применяется во всех трёх местах:

- paragraph и hard break;
- bold, italic, strike и inline code;
- blockquote;
- ordered и unordered nested lists без произвольного start number;
- plain code block без persisted language metadata;
- links.

Headings, horizontal rules, images и другие Plate nodes в v1 не поддерживаются. Изображения возвращаются только вместе с отдельным managed-asset contract; произвольные external image URLs не входят в persisted model.

Links принимают только `http`, `https` и root-relative internal paths. Root-relative links открываются в текущем контексте; внешние — в новой вкладке с `rel="noopener noreferrer"`. Protocol-relative URLs, fragments-only, `mailto`, `tel`, `javascript`, `data` и неизвестные schemes отклоняются.

### Trust seam, sanitization и rendering

- Structured DTO входит как `unknown` и валидируется Valibot на transport seam до cache/domain mapping согласно решению mm-108 «Выбрать frontend transport/API seam и правила cache invalidation».
- Schema строго проверяет version, node/mark discriminants, разрешённые fields, child shape и URL policy. Unknown version/node/mark/field либо запрещённый URL делает response invalid и переводит операцию в уже принятый typed failure path; authoritative content не урезается молча.
- Version upgrades реализуются как явные pure migrations между поддерживаемыми document versions.
- HTML не является transport/domain/persisted представлением. Единственная постоянная HTML trust seam — paste/import: DOMPurify очищает входной HTML, converter сохраняет только разрешённый v1 subset, затем node normalizer проверяет результат. Unsupported formatting удаляется с сохранением текста; images отбрасываются. Plain-text paste остаётся plain text.
- Edit и readonly используют один Plate profile. Readonly строит React elements из validated nodes; raw HTML и `dangerouslySetInnerHTML` отсутствуют. Поэтому DOMPurify не нужен на readonly output: там нет HTML-строки, а text экранируется React и URL уже проверен schema.

### Пустота и mutation semantics

- Отсутствующий Overall Feedback представлен явно: `overallFeedback: ReviewTextDocument | null`. Пустая строка не используется как sentinel структурированного contract.
- Пустой Plate paragraph допустим только как local editor draft. Очистка Overall Feedback сохраняет `null`.
- Root messages и replies persist-ятся только как non-empty documents. Non-empty определяется observable text после normalization whitespace/hard breaks; images не создают исключение, поскольку v1 их не поддерживает.
- Create/update mutations передают structured document и проходят ту же schema/normalization до transport serialization.

### Cutover текущих mock-данных

Текущие fixtures содержат простые `<p>`, `<strong>`, `<code>` и root-relative `<a>`, то есть переводятся в v1 без потери содержания. Поскольку production-данных нет и migration compatibility ранее снята как ограничение, допустимо разово конвертировать либо пересоздать fixtures. Dual reader, legacy HTML fallback и постоянный HTML→Plate adapter не сохраняются.

Конкретная реализация Plate cutover, transport endpoints и backend storage остаются вне planning-only границы карты. Production/source code и тесты не изменялись.
