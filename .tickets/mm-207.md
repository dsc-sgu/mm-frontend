# Спроектировать управление преподавателями курса

## Источники

- Страница AnyType «Фронтенд MergeMinds», «Что нужно уметь редактировать в курсе»: «Преподаватели — Добавление новых преподавателей, Удаление преподавателей, Изменение прав преподавателям».
- Страница AnyType «Обсуждение MergeMinds 30.01.2026»: «Теме больше нравится мандатная модель, где прям будет "он может оценить работу, он может создать блок и тд"».

## Проблема

В редакторе курса список преподавателей только для чтения (`src/features/course/features/page-edit/ui/hero-editor.tsx`). Добавить, удалить преподавателя или ограничить его права нельзя. mm-176 лишь упоминает ссылку-приглашение с ролью преподавателя.

## Что решить

- **Добавление:** ссылка-приглашение с ролью преподавателя (mm-176) или поиск пользователя по username.
- **Удаление:**
  - что происходит с его бронью проверки и с его неопубликованными правками курса: на `main` бэкенда — бронь редактирования курса и черновик курса, в модели mm-backend PR #187 — черновики блоков, которые видит, публикует и отменяет только автор;
  - его проверки остаются с его авторством;
  - последнего преподавателя удалить нельзя, и сам он выйти не может.
- **Права.** По `CONTEXT.md` у участия в курсе ровно одна роль: студент или преподаватель. Права преподавателя — это возможности внутри роли: редактировать курс, проверять попытки, открывать курс, управлять преподавателями. Нужны новые термины в `CONTEXT.md`, и надо решить, как фронтенд узнаёт, что можно текущему пользователю (встреча 30.01).
- **Кто управляет преподавателями.**
- Вопросы к бэкенду добавить в mm-113 — реестр вопросов фронтенда к API бэкенда.

## Интеграционные предпосылки и образцы

API проектирует фронтенд; отсутствие операции в прежнем API бэкенда не блокирует этот тикет. Перед реализацией прочитать `docs/agents/remote-data.md`. Образцы ниже проверены в `origin/main` на `045ea6d`; брать свежий `origin/main`, а не старый локальный checkout. Новые операции — Fetch через `runHttpOperation`, URL через `apiPath`, DTO проверяются до кэша; MSW хранит данные в общем `mockBackend`, а не в новом RAM-хранилище.

**Блокеры рефакторинга не нужны:** проектирование управления преподавателями не требует предварительно реализованных списков участников или редактора курса. mm-176 — связанный сценарий приглашения, а не основание ждать всю его реализацию для обсуждения прав.

**Готовые образцы:** `src/app/mock-backend/state.ts` моделирует участие по `courseId`/`userId` и роли; `src/features/course/features/access/api/load-course.ts` и `model/section-policy.ts` показывают существующую роль в контексте курса. `src/features/auth/model/full-name.ts` — части ФИО и форматирование. Общая форма человека запланирована mm-269; будущая реализация списка преподавателей должна использовать её, а не копировать исключение `Teacher` без `id` из `course/model/types.ts` и ключи по username в `page-edit/ui/hero-editor.tsx`.

**Не копировать:** глобальную роль сессии и сохранение списка преподавателей в документе страницы. Выбранная модель — личные черновики блоков; при удалении преподавателя отдельно определить их судьбу и судьбу брони проверки, не восстанавливая бронь курса. Уточнить серверный контракт возможностей внутри роли и авторства: новый доменный термин сначала согласовать и добавить в глоссарий. Этот тикет не объявляет готовыми ни управление преподавателями, ни будущий `course-shell`.

Проверено по `origin/main` (`045ea6d`). Наличие решения в спецификации или рабочей ветке не означает, что его реализация уже доступна в `main`. Перед реализацией перечитать `docs/agents/remote-data.md` и проверить актуальность указанных путей.
