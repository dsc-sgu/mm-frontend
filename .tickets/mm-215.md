# Единообразно собирать API URL через общий builder во всех HTTP-операциях

## Контекст

При обсуждении PR #214 обнаружена длинная сборка URL в `src/features/course/features/attempt-review/api/load-attempt.ts:44` и `src/features/course/features/repository/api/load-repository.ts:34`.

Общий builder нужен не только для сокращения длинных строк: если вводим его, все application HTTP-операции должны использовать один способ сборки API URL, независимо от длины пути. Это затрагивает Auth, список Courses и Course context вне ответственности PR #214, поэтому рефакторинг выполняется отдельной задачей и не блокирует этот PR.

Перед реализацией прочитать `AGENTS.md` и `docs/agents/remote-data.md`.

## Что сделать

- Добавить небольшой общий builder API-путей в `src/app/remote-data/api-path.ts`, например `apiPath(...segments: (string | number)[]): string`.
- Builder принимает сырые сегменты, кодирует каждый через `encodeURIComponent(String(segment))`, соединяет их `/` и добавляет существующий префикс `/api/v1`. Возвращает same-origin относительный путь.
- Перевести **все существующие application HTTP-операции** на builder — и короткие статические, и параметризованные URL. На момент обсуждения это:
  - `src/features/auth/api/check-session.ts`;
  - `src/features/auth/api/login.ts`;
  - `src/features/auth/api/register.ts`;
  - `src/features/auth/api/logout.ts`;
  - `src/features/course/api/load-courses.ts`;
  - `src/features/course/features/access/api/load-course.ts`;
  - `src/features/course/features/repository/api/load-repository.ts` из PR #214;
  - `src/features/course/features/attempt-review/api/load-attempt.ts` из PR #214.
- При реализации повторно проверить актуальные HTTP-операции: список выше — начальная инвентаризация, не закрытый whitelist.
- Описание endpoint и порядок его сегментов остаются у feature-владельца операции. Не создавать глобальный реестр endpoints и не переносить domain-ответственность в transport.
- Закрепить в `docs/agents/remote-data.md` единое правило: application HTTP-операции собирают API URL через builder независимо от длины пути; передают сырые, не предварительно закодированные сегменты.

Пример использования:

```ts
url: apiPath(
  'courses',
  courseId,
  'tasks',
  taskId,
  'attempts',
  studentUsername,
  attemptNumber
),
```

## Границы

- Речь о URL запросов к backend API, не о любых URL-строках в репозитории. URL страниц принадлежат TanStack Router; внешние ссылки, изображения и пути Web Workers не мигрировать.
- MSW route patterns и ожидаемые адреса в HTTP contract tests оставить независимым описанием wire-контракта. Не собирать ожидаемый URL тем же builder, который проверяется: это может скрыть ошибку production-сборки.
- Не менять фактические endpoints, методы, credentials, payloads, runtime validation, классификацию исходов, retry/cancellation, Query keys и правила доступа.
- Query-parameter API, конфигурация backend origin и дополнительные библиотеки не входят в задачу: подтверждённые текущие операции этого не требуют.

## Готово, когда

- Все application HTTP-операции используют общий builder, включая короткие статические пути.
- Нет ручного `encodeURIComponent` или ручной сборки API-пути в этих операциях.
- Тесты builder проверяют статический и вложенный пути, числовой сегмент, Unicode, пробелы и символы `/`, `?`, `#`, `%`; кодирование не меняет границы сегментов и не создаёт query/hash.
- Тесты операций независимо подтверждают сохранение wire-адресов; существующие transport/access contracts остаются зелёными.
- Lint, build, unit/component tests и затронутые E2E в Chromium, Firefox и WebKit проходят.
