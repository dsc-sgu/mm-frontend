# Спецификация: дедлайны Task с переопределениями для Student Groups и Students

Спецификация по итогам гриллинга исходного issue «Edit deadlines layout». Термины — в `CONTEXT.md`: Deadline, Deadline Override, Effective Deadline, Student Group.

Где расположен экран, как применяются правки и как выглядит массовый сдвиг, решит общий прототип настройки Task и дедлайнов [#181](https://github.com/dsc-sgu/mm-frontend/issues/181). Он ждёт grilling о настройке Task и Task Groups [#180](https://github.com/dsc-sgu/mm-frontend/issues/180). Решения прототипа переносятся сюда, в «Решения по реализации», и только после этого спецификация режется на implementation-тикеты.

## Проблема

Teacher управляет сроками заданий вслепую и по одному:

- **Один срок на всех.** У Task ровно один дедлайн. Разным Student Groups (например, подгруппам с лабораторными в разные дни) и отдельным Students дать другой срок нельзя. В версии Moodle, которая стоит в вузе, разных дедлайнов для групп тоже нет. Индивидуальные продления делаются вручную, вне системы.
- **Нет обзора.** Срок виден и правится только внутри отдельной Task. Нельзя увидеть все сроки Course сразу: их плотность, пересечения и задания без срока.
- **Нет объяснения.** Невозможно ответить на вопрос «какой срок у Пети по Лаб 3 и почему».
- **Массовые изменения — ручная работа.** Сдвинуть сроки нескольких Task (праздник в день лабы одной подгруппы, перенос курса на новый учебный год) можно только правкой каждой Task. Из-за этого в новом году Students видят «просрочено на 1984 дня» (AnyType, «Ругаюсь на Moodle»).
- **Неудобный ввод времени.** Чтобы поставить 23:59, в Moodle листают длинные списки.

## Решение

- **Три уровня дедлайна.**
  - Deadline Task — общий срок.
  - Deadline Override для Student Group.
  - Deadline Override для Student.

  Для каждого Student действует самое конкретное значение, даже если оно строже: личное, затем групповое, затем общее. Это его Effective Deadline.
- **Три состояния каждого уровня:** не задано (наследуется), задана дата, явно «без срока». У общего уровня состояния «не задано» нет: у Task либо дата, либо «без срока». Явно заданное значение остаётся переопределением, даже если совпадает с наследуемым.
- **Дедлайн только мягкий.** Он не закрывает Task: Attempt после срока принимается и считается опоздавшей.
- **Опоздание считается от текущего Effective Deadline.** Перенос срока, новое переопределение или перевод Student в другую группу меняют статус уже отправленных Attempts. Так Teacher может задним числом простить опоздание.
- **Один экран на Course для Teacher'а.** На нём:
  - все Task Course с общими сроками;
  - групповые и личные переопределения;
  - Effective Deadline любого Student с указанием источника;
  - массовый сдвиг, где видно, как сдвигается каждое значение, и каждое переопределение можно исключить;
  - необязательная причина переопределения. Её видят Teachers и те Students, к которым оно относится.
- **Время.** Дедлайн — момент времени. Teacher вводит дату и время с клавиатуры одним контролом в часовом поясе своего браузера, время по умолчанию 23:59. Пояс показа всегда подписан.
- **Правки в любой момент.** Сроки и переопределения меняются и после открытия Course, в отличие от максимальной Grade.

## User Stories

### Обзор сроков Course

1. As a Teacher, I want to see all Tasks of a Course with their deadlines on one screen, so that I can plan the semester without opening each Task.
2. As a Teacher, I want Tasks listed in Course Page order, so that the screen matches the course structure I already know.
3. As a Teacher, I want to see, for every Student Group, whether its deadline is inherited from the Task or set explicitly, so that I know which values will follow a change of the Task's Deadline.
4. As a Teacher, I want Tasks and Student Groups without a deadline marked explicitly, so that a missing deadline is never mistaken for a forgotten one.
5. As a Teacher, I want to see how many personal Deadline Overrides a Task has and open their list with reasons, so that exceptions stay visible.
6. As a Teacher, I want every deadline shown with its time zone, so that I never misread the moment by an hour.

### Общий Deadline Task

7. As a Teacher, I want to set a Task's Deadline, so that all Students know when to submit.
8. As a Teacher, I want to set a Task to «без срока», so that optional exercises have no deadline at all.
9. As a Teacher, I want to type the date and time from the keyboard in a single control, with 23:59 as the default time, so that setting many deadlines is fast.
10. As a Teacher, I want to change deadlines after the Course has been opened to Students, so that I can react to schedule changes mid-semester.

### Deadline Overrides для Student Groups

11. As a Teacher, I want to set a Deadline Override for a Student Group, later or earlier than the Task's Deadline, so that subgroups with lab classes on different days get fair deadlines.
12. As a Teacher, I want to set a Student Group's deadline while the Task itself has none, so that only that group is bound by a date.
13. As a Teacher, I want to set «без срока» for one Student Group while the Task has a deadline, so that a group can be exempted.
14. As a Teacher, I want to reset a Student Group's override back to the Task's Deadline, so that the group follows future changes again.
15. As a Teacher, I want a group deadline I set explicitly to stay put even when it equals the Task's Deadline, so that I can pin it before moving the Task's Deadline.
16. As a Teacher, I want to attach an optional reason to a group override, such as a holiday, so that Teachers and Students understand the exception.

### Личные Deadline Overrides

17. As a Teacher, I want to set a personal Deadline Override for one Student, so that I can grant an extension without changing anyone else's deadline.
18. As a Teacher, I want a personal override to win over the Student Group's deadline even when it is stricter, so that one rule — the most specific value wins — covers every case.
19. As a Teacher, I want to set «без срока» for one Student, so that a Student on academic leave is not marked late.
20. As a Teacher, I want to write a reason for a personal override that the Student will also see, so that the Student knows why their deadline differs.
21. As a Teacher, I want to remove a personal override, so that the Student returns to their Student Group's deadline.
22. As a Teacher, I want to find a Student and see their Effective Deadline for every Task together with its source (personal, group or Task), so that I can answer «why is my deadline this» immediately.
23. As a Teacher, I want a Student's personal overrides to survive their move to another Student Group while everything else follows the new group, so that individual extensions are not lost.

### Массовый сдвиг

24. As a Teacher, I want to select several Tasks and shift their deadlines by N days, so that rescheduling a block of work is one action.
25. As a Teacher, I want to shift deadlines only for chosen Student Groups across several Tasks, so that a holiday on one subgroup's lab day affects only that subgroup.
26. As a Teacher, I want shifting a Student Group that inherits the Task's Deadline to give that group its own override, so that other groups keep their deadlines.
27. As a Teacher, I want to see how every affected value (Task, group, personal) moves before the shift takes effect, so that nothing changes by surprise.
28. As a Teacher, I want to include or exclude each Deadline Override from the shift individually, so that I decide which exceptions keep their dates.
29. As a Teacher, I want «без срока» values to stay untouched by any shift, so that exempted groups and Students remain exempt.
30. As a Teacher, I want to be warned how many already submitted Attempts will become late or stop being late, so that I see the consequences of rescheduling.
31. As a Teacher preparing a Course for a new academic year, I want to shift all its deadlines at once, so that Students never see deadlines from last year.

### Применение и опоздание

32. As a Teacher, I want to always know whether my deadline changes are saved, so that I do not leave the screen with changes I think are applied.
33. As a Teacher, I want a late Attempt to become on time when I extend that Student's deadline afterwards, so that I can forgive lateness retroactively.
34. As a Teacher, I want a failed save or load to show an explicit error with a way to retry, so that a network problem never looks like lost data.

### Доступ

35. As a Student, I want the deadline settings to be unavailable to me, so that only Teachers change deadlines.
36. As a Teacher of the Course, I want the deadlines screen reachable from the Course itself, so that I do not need to switch modes to change a deadline.

### Разработка

37. As a developer, I want the mock backend to hold Student Groups, Task deadlines and Deadline Overrides in its single canonical state, so that the deadlines screen, the Task page, the dashboard calendar and Course Attempts never disagree.
38. As a developer, I want deadline resolution, lateness and shift planning as pure functions, so that their many combinations are tested without rendering UI.

## Решения по реализации

### Модель

- **Модуль.** Дедлайны — новый вложенный feature внутри course со своими `api`, `model` и `ui`. Календарь дедлайнов на dashboard остаётся отдельным feature и переходит на Effective Deadline в [#182](https://github.com/dsc-sgu/mm-frontend/issues/182).
- **Значение уровня** — дискриминированный union «дата | без срока».
  - Отсутствие Deadline Override означает наследование.
  - Deadline Override — запись с адресатом (Student Group или Student), значением и необязательной причиной.
  - Общий Deadline Task не наследуется: у него либо дата, либо «без срока». Поэтому frontend-тип Task перестаёт требовать дедлайн.
- **Effective Deadline** — чистая функция. Принимает Deadline Task и переопределения группы Student'а и самого Student'а. Возвращает значение, источник (личное, групповое, общее) и причину.
- **Опоздание** — чистая функция от момента отправки Attempt и текущего Effective Deadline. Варианты результата: вовремя, опоздала на N, без срока. Существующий расчёт отношения к дедлайну в feature Task расширяется до этой функции, а не дублируется.
- **План массового сдвига** — чистая функция. Принимает конфигурацию сроков, выбор Task, выбор адресатов (весь Course или конкретные Student Groups), N дней и исключённые переопределения. Возвращает список изменений «было → стало» и число Attempts, у которых меняется статус опоздания. Правила:
  - «без срока» не сдвигается;
  - сдвиг группы, которая наследует общий срок, создаёт ей явное переопределение;
  - сдвиг на +N и затем на −N возвращает исходную конфигурацию.
- **Правки** моделируются командами, тоже дискриминированным union:
  - задать или снять Deadline Task;
  - задать или сбросить переопределение группы;
  - задать или сбросить личное переопределение;
  - изменить причину.

  Модель поддерживает оба способа применения: локальный набор правок с одной командой «Применить» и применение по одной. Какой способ выбрать, решит прототип.

### Удалённые операции

Backend для переопределений пока нет. Всё ниже — рабочие допущения frontend, помеченные в MSW handlers и вынесенные в [«Реестр вопросов фронтенда к API бэкенда»](https://github.com/dsc-sgu/mm-frontend/issues/113), пункты «Хранение переопределений дедлайна», «Модель подгрупп» (уровень 2) и «Операции для сроков» (уровень 3).

- **Загрузка конфигурации сроков Course по `CourseId`.** Операция возвращает:
  - Task в порядке Course Page с общими Deadlines;
  - Student Groups;
  - Students с их группой;
  - групповые и личные Deadline Overrides с причинами;
  - моменты отправки Attempts по Student и Task, нужные для предупреждения об опоздании.
- **Применение правок** — одна атомарная операция. Ответ возвращает авторитетную конфигурацию. Поведение при одновременной правке двумя Teachers ещё не решено: его решают вместе со способом применения после прототипа.
- **Remote-data contract.** Операции следуют [`docs/agents/remote-data.md`](https://github.com/dsc-sgu/mm-frontend/blob/main/docs/agents/remote-data.md):
  - DTO-схемы Valibot в `api`;
  - типизированные отказы;
  - автоматических повторов нет;
  - кэш под `CourseId` ([ACC3, #173](https://github.com/dsc-sgu/mm-frontend/issues/173)).
- **Что обновляется после применения:** конфигурация сроков, календарь дедлайнов, страница Task, Task Summary на Course Page и Course Attempts.
- **Сроки не входят в рабочую копию страницы курса** (mm-118) и применяются отдельно от публикации страницы (решение mm-180).
  - Для личных переопределений это совпадает со страницей AnyType «Как устроена платформа»: если бы они входили в публикуемую версию, публикация откатывала бы работу студентов.
  - Бэкенд думает иначе. В открытом mm-backend PR #187 (не влит) время открытия и общий дедлайн — данные блока задания: они публикуются вместе с блоком, а восстановление точки публикации их откатывает. Переопределений там нет. Решение фронтенда остаётся, спор — в mm-113 (вопрос 4 комментария про PR #187), модель — mm-34k14.
- **Время** передаётся как момент UTC. UI показывает его в поясе браузера с подписью пояса. Выбор даты без времени ставит 23:59 местного времени.

### Mock backend

- Каноническое состояние хранит:
  - Student Groups (в каждом Course хотя бы одна, у Student ровно одна);
  - необязательный Deadline Task;
  - Deadline Overrides.

  Из этого же состояния строятся страница Task, календарь и Course Attempts.
- Seed-сценарий повторяет fixture прототипа:
  - четыре группы: 151-1пп, 151-2пп, 111-1пп, 111-2пп;
  - Task без срока;
  - групповые переопределения;
  - личные переопределения с причинами, среди них одно строже группового и одно «без срока»;
  - Attempts до и после сроков.

### Доступ

Править сроки может только Teacher. Если экран окажется разделом Course, доступ задаёт section policy ([ACC1.3, #170](https://github.com/dsc-sgu/mm-frontend/issues/170)): Student получает явный `403`. Если экран окажется внутри другой страницы, его элементы правки показываются только Teacher'у.

### Что решает прототип [#181](https://github.com/dsc-sgu/mm-frontend/issues/181)

- **Место экрана:**
  - A — раздел «Дедлайны» с матрицей «Task × Student Group»;
  - B — список Task и боковая панель;
  - C — в редакторе Course Page;
  - D — таймлайн.
- **Применение:** сразу или через «Применить» с предпросмотром.
- **Связь с полем дедлайна в панели [#41](https://github.com/dsc-sgu/mm-frontend/issues/41).** Рекомендация: поле правит только Deadline Task, рядом «Переопределений: N» со ссылкой на экран.
- **Вид массового сдвига** и исключения отдельных переопределений.

После прототипа сюда дописываются выбранные варианты, а также поведение при одновременной правке двумя Teachers.

## Решения по тестированию

- **Принцип.** Тест проверяет внешнее поведение: видимый результат и состояние mock backend. Внутреннее устройство компонентов и порядок вызовов не проверяются.
- **Model-тесты (Vitest, Node)** для чистых функций:
  - Effective Deadline: все сочетания трёх уровней и трёх состояний; явное значение, равное наследуемому;
  - опоздание: вовремя, опоздала, без срока, ровно в момент срока;
  - план массового сдвига: выбор Task и адресатов, исключения, «без срока», возврат +N/−N, подсчёт смены статуса опоздания.

  Для комбинаторики — property-based тесты на fast-check, принятом в стек в [#120](https://github.com/dsc-sgu/mm-frontend/issues/120).
- **Component-тесты (jsdom).** Экран рендерится через маршрут приложения с MSW mock backend. Сценарии:
  - Teacher видит унаследованные и явные значения;
  - меняет групповое переопределение;
  - снимает срок у Task;
  - добавляет личное переопределение с причиной;
  - сдвигает сроки;
  - применяет правки и видит результат в mock backend;
  - Student не получает доступа;
  - отказы загрузки и применения показываются явными состояниями с повтором.

  Prior art — harness `renderRoutes`, тесты формы входа, сброс mock backend к seed после каждого теста.
- **Тесты операций.** Загрузка и применение классифицируют отказы так же, как тесты загрузки «Моих курсов»: сеть, `500`, невалидный ответ, удерживаемый запрос. Используются failure profiles mock backend.
- **Real-browser (Playwright)** — только если выбранный в прототипе контрол даты и времени зависит от поведения реального браузера.
- **Прототип #181 тестами не покрывается.** Тесты пишутся при реализации по этой спецификации.

## Дополнительно

### Решения, принятые этой спецификацией

Перепроверить при нарезке на тикеты:

- старшинство «личное → групповое → общее», даже если конкретное значение строже;
- «без срока» — значение любого уровня;
- явное значение не превращается в наследуемое;
- мягкий срок;
- опоздание от текущего Effective Deadline;
- причина видна Teachers и тем Students, к которым относится;
- правки в любой момент жизни Course;
- момент времени, ввод в поясе браузера, 23:59 по умолчанию, пояс всегда подписан;
- Student Groups плоские, у Student ровно одна группа, в Course хотя бы одна.

### Факты backend

_Проверено на `mm-backend@ddd9849` (`main`) и в открытом [«Ezhkin-Kot/fixes»](https://github.com/dsc-sgu/mm-backend/pull/172) (`dd05f5f`)._

- **Дедлайн Task.** У Task одно поле `deadline_at`, nullable. На `main` это `timestamp`, в #172 — `timestamptz`. Рядом лежит `available_at`.
- **Переопределения.** Ни групповых, ни личных переопределений нет ни в одной ветке.
- **mm-backend PR #187** (`14a6abb`, открыт): `availableAt` и `deadlineAt` — поля данных блока задания, версионируются с ним; через `PATCH /tasks` их нельзя очистить (`null` значит «не менять»). Переопределений нет. Подгрупп в курсе нет.
- **Группы.** Таблица `groups` не привязана к Course. `course_users_groups` допускает несколько групп у Student. Код их не использует.
