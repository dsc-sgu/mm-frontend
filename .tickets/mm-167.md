# Epic: Course access — вход в Course по slug, явные 403/404 и стабильные identities

Epic группы «Course access» из решения [«Определить последовательность подготовки и выполнения рефакторинга»](https://github.com/dsc-sgu/mm-frontend/issues/69#issuecomment-6108811160). Целевая форма — резолюции [«Спроектировать Course access vertical и identity seam»](https://github.com/dsc-sgu/mm-frontend/issues/115) и [«Выбрать явный UX для отказа в course-local доступе»](https://github.com/dsc-sgu/mm-frontend/issues/111) с уточнениями из [«Спроектировать матрицу тестовых контрактов критических вертикалей»](https://github.com/dsc-sgu/mm-frontend/issues/120). Тикеты slices — sub-issues этого epic (таблица «Slices» в «Дополнительно»).

## Проблема

User открывает Course по ссылке и не понимает, что произошло, когда доступа нет:

- **Тихие redirects.** Неизвестный Course и Course без Course Membership молча возвращают на панель управления. Student на teacher-only разделе молча попадает на Course Page. Ссылка теряется, причину никто не называет. Shared link на раздел Course Attempts у Student'а превращается в «ничего не произошло».
- **Роль — свойство аккаунта.** Session несёт глобальную роль, и права в attempt review частично берутся из неё. Один User бывает Teacher'ом в одном Course и Student'ом в другом, поэтому права считаются неверно.
- **Владение по username.** Доступ к чужому Repository или Attempt решает клиент: сравнивает username из URL с username из session и сверяется со списком username всех Students курса, который получает каждый участник. Username изменяем и не доказывает identity, а список Students раскрывает состав курса.
- **Кэш без identity.** Ключи строятся из slug и username. После смены User в той же вкладке или смены slug кэш показывает чужое или устаревшее содержимое: название, навигацию и роль другого Course или другого User.
- **Технический отказ неотличим от отказа в доступе.** Проверка доступа — RAM-мок без сетевого пути, поэтому сбой сети или невалидный ответ некуда отнести, кроме как в redirect.
- **Номер Attempt выглядит как глобальный id.** Параметр route `attemptId` на деле — порядковый номер Attempt у Student'а в Task.

## Решение

Вход в любой Course route начинается одной загрузкой Course по slug, которая сразу называет роль текущего User. Все исходы показываются явными состояниями route без redirects:

- **`404` для неизвестного Course и для Course без Course Membership.** Внешне они неразличимы: «Страница не найдена» с действием «К моим курсам».
- **`403` для раздела не по роли.** Course shell с разрешённой навигацией остаётся, текст называет требуемую роль, действие — «На страницу курса».
- **`404` для чужого или отсутствующего participant-bound ресурса**, внутри Course shell. Существование чужого ресурса не раскрывается.
- **Технический отказ** — «Не удалось проверить доступ» с «Повторить» и «К моим курсам». URL сохраняется.
- **Единственный автоматический redirect** — unauthenticated → login.

Права разделов задаёт одна таблица, из неё строятся и навигация, и проверка route. Владение participant-bound ресурсом решает backend по стабильным identities. Кэш Course живёт под общим prefix `CourseId` и очищается при смене User или потере Course Membership. Список курсов и загрузка Course идут через Fetch и MSW.

Работа режется на три PR, и каждый оставляет единственный путь доступа:

| Slice | Делает | После |
|---|---|---|
| ACC1 | Identity-типы, загрузка Course по slug, список курсов, route states `404`/`403`/технический отказ, section policy; без старой проверки доступа, redirect guards и роли в session | K, V-TQ |
| ACC2 | Participant-bound ресурсы на стабильных identities (`AttemptId`, `AttemptNumber`); без проверки владения по username | ACC1 |
| ACC3 | Все дочерние query families под `['course', courseId, …]` | ACC2 |

Для объёма одного контекста ACC1 разбит на три тикета, а из ACC2 вынесен prefactor с переименованием (см. «Slices» в «Дополнительно»). На каждом шаге остаётся один путь доступа.

## User Stories

### Вход в Course

1. As a Course Member, I want a Course to open by its slug with my role in it, so that I see the sections I'm allowed to use.
2. As a Course Member returning to a Course I opened recently, I want its content to appear immediately while access is rechecked in the background, so that navigation stays fast.
3. As a Course Member opening a Course for the first time in this session, I want a neutral loading state without any Course title, breadcrumbs or navigation, so that I never see data I haven't been confirmed for.
4. As a User with roles in two Courses, I want switching from one Course to another to never show the previous Course's title, navigation or role under the new URL, so that I'm not misled about where I am and what I can do.
5. As a User who is Teacher in one Course and Student in another, I want each Course to use my role in that Course, so that my rights are correct in both.
6. As a User, I want my Course list to come from the same backend as the Course I open, so that the list and the Course agree on what I can access.

### Отказы

7. As an authenticated User without Course Membership, I want an opened Course link to show «Страница не найдена» with «К моим курсам», so that I can go back to my Courses.
8. As a User who opens a non-existent or outdated slug, I want the same «Страница не найдена» as for a Course I'm not a member of, so that the page reveals nothing about which Courses exist.
9. As a User who opens a syntactically invalid Course link, I want «Страница не найдена» instead of a silent redirect, so that I understand the link is broken.
10. As a Student opening a teacher-only section (Course Attempts, repositories, files, analytics, Course editing, Task editing, Review editor) by a direct, stale or shared link, I want «Нет доступа» saying the section is for the Course's Teachers, inside the Course shell, so that I know why and can go to the Course Page.
11. As a Student, I want the navigation to show only the sections I can open, so that I don't click into a `403`.
12. As a Teacher, I want the teacher navigation in my Courses, so that I reach Course Attempts, repositories, files, analytics and editing.
13. As a Course Member whose network fails while access is checked, I want «Не удалось проверить доступ» with «Повторить» and «К моим курсам» instead of `403` or `404`, so that a technical failure isn't presented as lost access.
14. As a Course Member, I want «Повторить» to recheck access without losing the URL, so that I continue where I was going.
15. As a Course Member, I want the URL to stay unchanged on every access denial, so that I can retry, copy it or go back with the browser.
16. As an unauthenticated visitor, I want any Course link to lead to login, so that I can sign in first.

### Потеря доступа

17. As a User removed from a Course while it's open, I want its content replaced by the course `404` and actions blocked as soon as the recheck confirms it, so that I can't keep acting in a Course I no longer belong to.
18. As a Teacher whose role in the Course changed to Student while on a teacher-only section, I want that section replaced by `403`, so that I don't act with rights I no longer have.
19. As a Course Member, I want access rechecked when I come back to the tab, when the network returns and after a protected operation is refused for access, so that the shown access is not stale for long.

### Participant-bound ресурсы

20. As a Student, I want to open my own Repository and my own Attempts, so that I see my work and its Reviews.
21. As a Student who opens another Student's Attempt or Repository by link, I want the same «Страница не найдена» as for a missing one, with no name, files or Grade of the other Student anywhere on the page, so that other Students' work stays private.
22. As a Teacher, I want to open any Student's Repository and Attempts in my Course, so that I can review their work.
23. As a Teacher who opens a Student or Attempt that doesn't exist in the Course, I want a resource `404` inside the Course shell with «На страницу курса», so that I stay in the Course.
24. As a Student whose username changed, I want my Attempts and Repository to stay mine, so that ownership doesn't depend on a mutable name.
25. As a Course Member, I want the Attempt URL and breadcrumbs to say «attempt number», so that the number reads as «my n-th Attempt at this Task», not a global id.

### Session и кэш

26. As a User signing out and another User signing in in the same tab, I want nothing of the first User's Courses, roles or navigation to appear at any moment, so that a shared computer doesn't leak data.
27. As a User whose session was replaced, I want every Course I open to be looked up again for me, so that the previous User's role is never reused.
28. As a Teacher whose Course slug changed, I want the Course's cached content to remain valid under the new slug and the old slug to give `404`, so that identity doesn't depend on the address.
29. As a Course Member, I want a confirmed loss of Course Membership to remove all cached content of that Course in one step, so that no stale screen of it can reappear.

### Разработка

30. As a frontend developer, I want `UserId`, `CourseId`, `CourseSlug`, `Username`, `AttemptId` and `AttemptNumber` to be distinct types, so that passing a locator where an identity is expected fails type checking.
31. As a frontend developer, I want one section policy table used by both navigation and route checks, so that a new section can't be visible in navigation but forbidden on its route, or the other way round.
32. As a frontend developer, I want each remote operation to declare its own outcome union, so that callers handle `not-found` and `forbidden` explicitly and failures stay failures.
33. As a frontend developer, I want every Course-scoped query key to extend one Course prefix by `CourseId`, so that Course-wide cache operations are one call and no key depends on the slug.
34. As a frontend developer, I want feature code to import no in-memory course mocks for the Course list and lookup, so that switching to the real backend needs no feature changes.
35. As a frontend developer, I want backend working assumptions about access to be marked in MSW handlers, so that a different backend answer becomes a targeted fix.
36. As a test author, I want named mock-backend worlds with Courses, Teachers, Students, a cross-role User and a non-member, so that access tests read like the scenarios they prove.
37. As an E2E test author, I want to choose the world and the signed-in User through a test-only channel, so that E2E tests don't depend on the login UI.
38. As an E2E test author, I want to hold a specific response until I release it, so that loading-state contracts are deterministic.
39. As an assistive-technology user, I want the `403` and `404` pages to pass automated accessibility checks, so that I can understand the denial and use its actions.

## Решения по реализации

### Identity

- `UserId`, `CourseId`, `CourseSlug`, `Username`, `AttemptId` и `AttemptNumber` — статически различимые типы. `UserId` уже есть в session (K).
- `Username` и `CourseSlug` — изменяемые locators маршрута. Они не служат доказательством владения или авторизации.
- Глобальная роль удаляется из session и из схемы ответа session. Course-local роль приходит только из загрузки Course. Права ответа на комментарии в attempt review берутся из роли в Course, а не из session.
- `CourseMembership` как `CourseId + UserId + CourseRole` нужна только в проекциях нескольких участников. Для текущего User достаточно `role` в результате загрузки Course.

### Загрузка Course по slug (ACC1)

Вход в любой реализованный Course route начинается одной access-aware операцией `loadCourseBySlug(courseSlug, signal)`. Это загрузка самого Course по locator, а не отдельный permission check. Форма результата — из резолюции #115:

```ts
type LoadCourseResult =
  | {
      status: 'found';
      course: { id: CourseId; title: string; shortTitle: string; iconName: CourseIconName; color: CourseColor };
      role: CourseRole;
    }
  | { status: 'course-not-found' }
  | { status: 'not-member' };
```

- Сеть, необъявленный status и невалидный DTO — отказ операции (`OperationFailure`), а не отказ в доступе.
- Slug в ответе не дублируется: им владеет Router.
- Ключ — `courseContextKeys.bySlug(userId, courseSlug)`. Он стоит вне Course prefix, потому что вход операции — slug. `UserId` в ключе нужен потому, что session — неявный вход lookup.
- Перепроверка — при входе в Course, focus, reconnect и после отказа защищённой операции по доступу.
- Поиск Course в списке курсов удаляется. Course Page загружается отдельно и только на своём route. Вложенные routes не загружают Course Page ради identity или роли.
- Контекст Course route содержит `CourseId`, metadata shell (title, shortTitle, иконка, цвет) и `CourseRole`. Списка username Students в нём нет.
- Wire format (URL, statuses, различие `course-not-found` и `not-member`) — рабочее допущение из [«Реестр frontend-вопросов к backend API»](https://github.com/dsc-sgu/mm-frontend/issues/113), помеченное в handlers. Frontend contract выше backend wire format не определяет.

### Список курсов (ACC1)

- «Мои курсы» загружаются Fetch-операцией через MSW из того же состояния mock backend, что и загрузка Course.
- Список зависит от User, поэтому его семейство ключей содержит `UserId` и очищается вместе с остальным session-bound кэшем.

### Section policy (ACC1)

Одна таблица задаёт правила и для навигации, и для авторизации route реализованных разделов Course. Таблица из резолюции #115:

```ts
const courseSectionAccess = {
  page: 'member',
  journal: 'member',
  attempts: 'teacher',
  repositories: 'teacher',
  files: 'teacher',
  analytics: 'teacher',
  edit: 'teacher',
} as const;
```

- Course Page и Task Page доступны любому Course Member.
- Journal доступен обеим ролям: Student получает персональную проекцию, Teacher — общую. Route пока заглушка, и проверяется только доступ.
- Task editing относится к разделу `edit`, Review editor — к разделу `attempts`.
- Repository Student'а — participant-bound ресурс, а не раздел (см. ACC2). Раздел `repositories` — это индекс репозиториев для Teacher'а.
- Недоступные пункты навигации скрыты. Direct, stale и shared links обслуживает проверка route.
- Таблица не становится permission framework и не решает владение ресурсами и права mutations.

### Route states и тексты (ACC1)

Внутренние исходы различают отсутствие Course, отсутствие Course Membership, несовпадение роли, отсутствие ресурса, ресурс вне разрешённой области и технический отказ. Внешне несколько исходов намеренно сходятся в один `404`.

| Внутренний исход | Что видит User | Действие |
|---|---|---|
| `course-not-found`, `not-member`, синтаксически неверный locator | «Страница не найдена» — «Возможно, ссылка устарела или страница больше недоступна.», только общий authenticated shell | «К моим курсам» |
| Роль не подходит разделу | «Нет доступа» — «Этот раздел доступен только преподавателям курса.», Course shell и разрешённая навигация | «На страницу курса» |
| Resource `not-found` или `forbidden` | Тот же текст `404`, внутри Course shell | «На страницу курса» |
| Сеть, неожиданный ответ, невалидный DTO | «Не удалось проверить доступ», защищённое содержимое не показывается | «Повторить», «К моим курсам» |

- URL при отказе не меняется. Автоматических redirects, кроме unauthenticated → login, нет. Отдельной кнопки «Назад» нет: её роль выполняет навигация браузера.
- **Пока Membership не подтверждён,** показывается нейтральная загрузка без metadata, breadcrumbs, навигации и без предыдущего или закэшированного содержимого.
- **Подтверждением считается** закэшированный Course context того же User для `(UserId, CourseSlug)`. Содержимое видно сразу, context перепроверяется в фоне.
- **Shell и содержимое предыдущего Course** под URL нового не показываются никогда.
- **Подтверждённая потеря Membership** сразу заменяет содержимое на course `404`, понижение роли на teacher-only разделе — на `403`. Действия блокируются.
- **Header** берёт breadcrumbs и навигацию из подтверждённого Course context. Подставного title из slug и выдуманного доступа «по умолчанию» нет.
- Категории `403` и `404` — состояния route в client-rendered приложении. При server rendering им соответствуют HTTP statuses.

### Participant-bound ресурсы (ACC2)

- Форма URL сохраняется: `$studentUsername` остаётся locator `Username`, а `$attemptId` переименовывается в `$attemptNumber`. Название route, breadcrumbs, навигация, query identity и mock-данные используют одну терминологию.
- Feature-owned операции разрешают locators в `UserId` и `AttemptId`. После разрешения операции и кэш работают со стабильными id.
- У каждой операции свой union, общего `LoadResourceResult<T>` нет. Пример из #115:

  ```ts
  type LoadAttemptResult =
    | { status: 'found'; attempt: Attempt }
    | { status: 'not-found' }
    | { status: 'forbidden' };
  ```

- `not-found` и `forbidden` дают одинаковый resource `404` внутри Course shell.
- Наличие и доступ решает backend (MSW): Student видит только собственные Repository, Attempts и опубликованные Reviews, Teacher — ресурсы Students своего Course.
- Ответ handler'а на отказ не несёт данных о ресурсе и его владельце ни в теле, ни в заголовках. Требование к backend записано в #113.
- Сравнения username из URL с username из session и клиентские проверки состава Students удаляются.
- **Сопоставление `AttemptNumber` → `AttemptId`** — рабочее допущение до ответа [«Согласовать transport mapping attemptNumber и backend attempt UUID»](https://github.com/dsc-sgu/mm-frontend/issues/85), помеченное в handlers.
- **Минимальные Attempts в MSW.** ACC2 вводит в состояние mock backend только identity Attempt: Task, Student, номер и владелец. REV2 расширяет его до единого состояния Attempts и Reviews. Содержимое Attempt page остаётся на прежнем источнике до REV2.

### Query cache и session (ACC3)

- **Общий prefix.** Все course-scoped семейства расширяют `['course', courseId, …]`: Course Page, Task Page, Course Attempts, Attempt Review и participant-bound ресурсы из ACC2. Примеры `['course-pages', courseId]` и `['course-attempts', courseId, …]` в резолюциях — иллюстрация (уточнение в [«Унифицировать ключи запросов и правила согласованности кеша»](https://github.com/dsc-sgu/mm-frontend/issues/76)).
- **Вне prefix** остаются только Course context (его вход — slug), список курсов (вход — User) и календарь дедлайнов (он поперёк Course, slice DEADLINES).
- **Адресация.** Дочерние операции и ключи адресуют `CourseId`. RAM-моки, ещё не переведённые на MSW, адресуются тем же `CourseId`, который выдаёт загрузка Course.
- **Key factories.** Каждое семейство владеет key factory по `docs/agents/remote-data.md`. Raw-константы ключей других feature не импортируются, чужие tuples вручную не собираются.
- **Login, logout и замена session** очищают весь session-bound кэш: Course context, список курсов и всё под Course prefix.
- **Подтверждённая потеря Membership** удаляет кэш Course одним вызовом по prefix `['course', courseId]`.
- **Смена slug.** Старый slug даёт `course-not-found`, aliases нет. Кэш Course Page по `CourseId` остаётся. Сама операция смены slug — DRF1. Пока её нет, существующее сохранение Course Page инвалидирует Course context вместо удалённого ключа старой проверки доступа.

### Mock backend и test-only канал

- В состоянии mock backend появляются Courses и Course Memberships. Handlers списка курсов и загрузки Course читают это состояние.
- **Dev-seed** остаётся демо-набором, согласованным с RAM-моками Course Page, Attempts и Review, которые ещё не переведены.
- **Мир `world:access`** выбирают тесты:
  - Courses «Алгоритмы» (open) и «Базы данных»;
  - Анна и Борис — Teachers «Алгоритмов»;
  - Саша и Петя — Students «Алгоритмов»;
  - Вера — Student «Алгоритмов» и Teacher «Баз данных»;
  - Гость — authenticated, без Course Membership;
  - несуществующий slug.
- **`world:review`** в ACC2 расширяет его минимальными Attempts Саши и Пети.
- **Test-only канал для E2E** — handler MSW, доступный только в test build. Он не глобал на `window` и никогда не попадает в production. Канал:
  - выбирает мир;
  - задаёт session текущего User;
  - удерживает ответ названной операции, пока тест его не отпустит.

  Выбранный мир и session переживают полную загрузку страницы, иначе «прямая ссылка» в E2E сбросила бы их к seed. Обычный dev-режим по-прежнему сбрасывает состояние при каждой загрузке. Канал появляется в ACC1 как часть его первого потребителя, отдельного PR «только инфраструктура» нет.
- **Список исключений ESLint** для импортёров RAM-моков сокращается на модули списка курсов и старой проверки доступа.

### Удаляется

- **ACC1:**
  - старая операция проверки доступа и её ключ;
  - поиск Course в списке курсов;
  - redirect guards Course routes;
  - redirects на синтаксически неверные locators;
  - роль в session;
  - список username Students в контексте Course;
  - подставные title и доступ в header;
  - глобально-ролевые подсказки в моках вроде «Текущий преподаватель».
- **ACC2:**
  - проверка владения по username;
  - клиентские проверки состава Students;
  - `attemptId` в значении «порядковый номер».
- **ACC3:**
  - ключи на slug и username;
  - raw-константы ключей в cross-feature импортах;
  - устаревшие пути инвалидации.

## Решения по тестированию

- **Что такое хороший тест.** Тест проверяет наблюдаемый исход через внешний interface: состояние route, которое видит User, объявленный исход операции, содержимое кэша по публичной key factory. Внутренности не проверяются. Fixtures именованы, MSW отвечает на уровне протокола, pixel screenshots запрещены (#68).
- **Контракты.** Фильтр по slice в [матрице тестовых контрактов](https://github.com/dsc-sgu/mm-frontend/blob/ddda126c5e73ec787362805c286ee081ee26244d/docs/prototypes/test-contract-matrix.html) (commit `ddda126`) пишется в PR своего slice. Каждая новая операция добавляет экземпляр шаблона TR-05: каждый объявленный status даёт свой исход, необъявленный — `unexpected-http`, невалидный DTO — `invalid-response`.

| ACC2 (3) | — | ACC-08 | ACC-16 | ACC-E1 |
| ACC3 (3) | — | ACC-06, ACC-07 | — | ACC-E4 |

- **Fail-closed инварианты** I1 (точная identity) и I2 (нет доступа к чужому) доказываются независимо на нескольких слоях, включая браузер.

**Seams** (согласованы):

- **Model и Static.** Таблица section policy × роль (исчерпывающе), отображение внутреннего исхода в категорию route state, type tests различимости identity-типов через `@ts-expect-error`.
- **Boundary.** Операции и их query options с настоящим QueryClient против MSW в Node на `world:access`/`world:review`. Образец — тесты операций auth и их query options.
- **Component.** Настоящее дерево routes приложения с memory history, настоящим Header, свежими Router и QueryClient и MSW в Node. Делается опцией существующего harness рендеринга routes. Тест видит то же, что User: route state, Course shell, breadcrumbs, навигацию. Только так ловится route, забывший применить section policy (ACC-12 параметризован по всем teacher-only разделам).
  - Риск: в Vitest нет code splitting router plugin, поэтому дерево загружает в jsdom все route-модули, а authenticated layout монтирует worker pool attempt review. Это решается в ACC1: подменой модуля worker в конфиге тестов или переносом pool на routes review.
  - Образец — тесты route error и выхода из аккаунта.
- **E2E.** Playwright в Chromium, Firefox и WebKit, приложение целиком с MSW в браузере. Мир, session и удержанные ответы задаёт test-only канал.
  - ACC-E4 — единственный сценарий, где выход идёт через Header, а вход — через форму login: он проверяет смену session в той же вкладке без перезагрузки.
  - Образец — E2E страницы проверки Attempt.
- **A11Y-01.** Axe на устойчивых состояниях `403` и `404` появляется в ACC1. Экраны других вертикалей добавляют их slices.

**Slice готов**, когда проходят lint и build, а все его контракты зелёные в трёх движках.

## Вне области

- **Чужие slices:**
  - операция смены slug и согласованность адреса — DRF1;
  - read-side опубликованной Course Page поверх snapshots — READ;
  - календарь дедлайнов на Fetch — DEADLINES;
  - перевод данных Attempt, Review и Course Attempts на MSW — REV2 и ATT1;
  - модель прав ответа и Review Lease — Review vertical.
- **Login и register UI.** Mock-авторизация, целевой flow сменится с OpenID. Закрепляется только redirect unauthenticated → login (ACC-17).
- **Содержимое персонального журнала** ([#99](https://github.com/dsc-sgu/mm-frontend/issues/99)). Проверяется только доступ к разделу.
- **Backend wire format.** Окончательные URL и statuses, aliases и canonicalization slug, сопоставление номера и UUID Attempt — #113 и #85. Contract tests против реального backend — вне карты.
- **Смена username.** Profile mutation пока нет. Правило из #115 (`UserId` неизменен, session согласуется до завершения success-flow, старый username в URL заменяется) применяется, когда она появится.
- **Универсальная permission framework**, права mutations и владение ресурсами за пределами participant-bound загрузок.
