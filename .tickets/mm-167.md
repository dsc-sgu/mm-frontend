# Эпик: Доступ к курсу — вход в курс по slug, явные 403/404 и стабильные идентичности

Эпик группы «Доступ к курсу» (Course access) из решения mm-69 (комментарий от 2026-10-11). Целевая форма — резолюции mm-115 (вертикаль доступа к курсу и шов идентичности) и mm-111 (явный интерфейс отказа в доступе внутри курса) с уточнениями из mm-120 (матрица тестовых контрактов критических вертикалей). Тикеты этапов — дочерние тикеты этого эпика (таблица «Этапы» в «Дополнительно»).

## Проблема

Пользователь открывает курс по ссылке и не понимает, что произошло, когда доступа нет:

- **Тихие редиректы.** Неизвестный курс и курс, в котором пользователь не участвует, молча возвращают на панель управления. Студент в разделе только для преподавателей молча попадает на страницу курса. Ссылка теряется, причину никто не называет. Пересланная студенту ссылка на список попыток курса превращается для него в «ничего не произошло».
- **Роль — свойство аккаунта.** Сессия несёт глобальную роль, и права на странице попытки частично берутся из неё. Один пользователь бывает преподавателем в одном курсе и студентом в другом, поэтому права считаются неверно.
- **Владение по username.** Доступ к чужому репозиторию или попытке решает клиент: сравнивает username из URL с username из сессии и сверяется со списком username всех студентов курса, который получает каждый участник. Username изменяем и не доказывает идентичность, а список студентов раскрывает состав курса.
- **Кэш без идентичности.** Ключи строятся из slug и username. После смены пользователя в той же вкладке или смены slug кэш показывает чужое или устаревшее содержимое: название, навигацию и роль другого курса или другого пользователя.
- **Технический отказ неотличим от отказа в доступе.** Проверка доступа — RAM-мок без сетевого пути, поэтому сбой сети или невалидный ответ некуда отнести, кроме как в редирект.
- **Номер попытки выглядит как глобальный id.** Параметр маршрута `attemptId` на деле — порядковый номер попытки студента по заданию.

## Решение

Вход в любой маршрут курса начинается одной загрузкой курса по slug, которая сразу называет роль текущего пользователя. Все исходы показываются явными состояниями маршрута без редиректов:

- **`404` для неизвестного курса и для курса, в котором пользователь не участвует.** Внешне они неразличимы: «Страница не найдена» с действием «К моим курсам».
- **`403` для раздела не по роли.** Оболочка курса с разрешённой навигацией остаётся, текст называет требуемую роль, действие — «На страницу курса».
- **`404` для чужого или отсутствующего ресурса участника курса**, внутри оболочки курса. Существование чужого ресурса не раскрывается.
- **Технический отказ** — «Не удалось проверить доступ» с «Повторить» и «К моим курсам». URL сохраняется.
- **Единственный автоматический редирект** — невошедшего пользователя на страницу входа.

Права разделов задаёт одна таблица, из неё строятся и навигация, и проверка маршрута. Владение ресурсом участника курса решает бэкенд по стабильным идентичностям. Кэш курса живёт под общим префиксом `CourseId` и очищается при смене пользователя или потере участия в курсе. Список курсов и загрузка курса идут через Fetch и MSW.

Работа режется на три PR, и каждый оставляет единственный путь доступа:

| Этап | Делает | После |
|---|---|---|
| ACC1 | Типы идентичностей, загрузка курса по slug, список курсов, состояния маршрута `404`/`403`/технический отказ, правила доступа к разделам курса; без старой проверки доступа, охранных редиректов маршрутов (redirect guards) и роли в сессии | K, V-TQ |
| ACC2 | Ресурсы участника курса на стабильных идентичностях (`AttemptId`, `AttemptNumber`); без проверки владения по username | ACC1 |
| ACC3 | Все дочерние семейства запросов под `['course', courseId, …]` | ACC2 |

Чтобы уложиться в объём одного контекста, ACC1 разбит на три тикета, а из ACC2 вынесен подготовительный рефакторинг с переименованием (см. «Этапы» в «Дополнительно»). На каждом шаге остаётся один путь доступа.

## Решения по реализации

### Идентичность

- `UserId`, `CourseId`, `CourseSlug`, `Username`, `AttemptId` и `AttemptNumber` — статически различимые типы. `UserId` уже есть в сессии (K).
- `Username` и `CourseSlug` — изменяемые локаторы маршрута. Они не служат доказательством ни владения, ни прав.
- Глобальная роль удаляется из сессии и из схемы ответа сессии. Роль в курсе приходит только из загрузки курса. Права на ответы к комментариям на странице попытки берутся из роли в курсе, а не из сессии.
- `CourseMembership` как `CourseId + UserId + CourseRole` нужна только в проекциях с несколькими участниками. Для текущего пользователя достаточно `role` в результате загрузки курса.

### Загрузка курса по slug (ACC1)

Вход в любой реализованный маршрут курса начинается одной операцией с учётом доступа — `loadCourseBySlug(courseSlug, signal)`. Это загрузка самого курса по локатору, а не отдельная проверка прав. Форма результата — из резолюции mm-115:

```ts
type LoadCourseResult =
  | {
      status: 'found';
      course: { id: CourseId; title: string; shortTitle: string; iconName: CourseIconName; color: CourseColor };
      role: CourseRole;
    }
  | { status: 'course-not-found' }
  | { status: 'not-member' };
```

- Сеть, необъявленный статус и невалидный DTO — сбой операции (`OperationFailure`), а не отказ в доступе.
- Slug в ответе не дублируется: им владеет роутер.
- Ключ — `courseContextKeys.bySlug(userId, courseSlug)`. Он стоит вне префикса курса, потому что вход операции — slug. `UserId` в ключе нужен потому, что сессия — неявный вход поиска курса.
- Перепроверка — при входе в курс, возврате фокуса, переподключении и после отказа защищённой операции из-за доступа.
- Поиск курса в списке курсов удаляется. Страница курса загружается отдельно и только на своём маршруте. Вложенные маршруты не загружают страницу курса ради идентичности или роли.
- Контекст маршрута курса содержит `CourseId`, метаданные оболочки (название, краткое название, иконка, цвет) и `CourseRole`. Списка username студентов в нём нет.
- Формат API (URL, статусы, различие `course-not-found` и `not-member`) — рабочее допущение из mm-113, помеченное в обработчиках. Контракт фронтенда выше не определяет формат API бэкенда.

### Список курсов (ACC1)

- «Мои курсы» загружаются Fetch-операцией через MSW из того же состояния мок-бэкенда, что и загрузка курса.
- Список зависит от пользователя, поэтому его семейство ключей содержит `UserId` и очищается вместе с остальным кэшем, привязанным к сессии.

### Правила доступа к разделам курса (ACC1)

Одна таблица задаёт правила и для навигации, и для авторизации маршрутов реализованных разделов курса. Таблица из резолюции mm-115:

```ts
const courseSectionAccess = {
  page: 'member',
  journal: 'member',
  attempts: 'teacher',
  repositories: 'teacher',
  files: 'teacher',
  analytics: 'teacher',
  edit: 'teacher',
} as const;
```

- Страница курса и страница задания доступны любому участнику курса.
- Журнал доступен обеим ролям: студент получает персональную проекцию, преподаватель — общую. Маршрут пока заглушка, и проверяется только доступ.
- Редактирование задания относится к разделу `edit`, редактор проверки — к разделу `attempts`.
- Репозиторий студента — ресурс участника курса, а не раздел (см. ACC2). Раздел `repositories` — это индекс репозиториев для преподавателя.
- Недоступные пункты навигации скрыты. Прямые, устаревшие и пересланные ссылки обрабатывает проверка маршрута.
- Таблица не становится фреймворком прав и не решает владение ресурсами и права на операции записи.

### Состояния маршрута и тексты (ACC1)

Внутренние исходы различают отсутствие курса, отсутствие участия в курсе, несовпадение роли, отсутствие ресурса, ресурс вне разрешённой области и технический отказ. Внешне несколько исходов намеренно сходятся в один `404`.

| Внутренний исход | Что видит пользователь | Действие |
|---|---|---|
| `course-not-found`, `not-member`, синтаксически неверный локатор | «Страница не найдена» — «Возможно, ссылка устарела или страница больше недоступна.», только общая оболочка для вошедшего пользователя | «К моим курсам» |
| Роль не подходит разделу | «Нет доступа» — «Этот раздел доступен только преподавателям курса.», оболочка курса и разрешённая навигация | «На страницу курса» |
| Ресурс: `not-found` или `forbidden` | Тот же текст `404`, внутри оболочки курса | «На страницу курса» |
| Сеть, неожиданный ответ, невалидный DTO | «Не удалось проверить доступ», защищённое содержимое не показывается | «Повторить», «К моим курсам» |

- URL при отказе не меняется. Автоматических редиректов, кроме редиректа невошедшего пользователя на вход, нет. Отдельной кнопки «Назад» нет: её роль выполняет навигация браузера.
- **Пока участие в курсе не подтверждено,** показывается нейтральная загрузка без метаданных, хлебных крошек, навигации и без предыдущего или закэшированного содержимого.
- **Подтверждением считается** закэшированный контекст курса того же пользователя для `(UserId, CourseSlug)`. Содержимое видно сразу, контекст перепроверяется в фоне.
- **Оболочка и содержимое предыдущего курса** под URL нового не показываются никогда.
- **Подтверждённая потеря участия** сразу заменяет содержимое на `404` курса, понижение роли в разделе только для преподавателей — на `403`. Действия блокируются.
- **Шапка (Header)** берёт хлебные крошки и навигацию из подтверждённого контекста курса. Подставного названия из slug и выдуманного доступа «по умолчанию» нет.
- Категории `403` и `404` — состояния маршрута в приложении с рендерингом на клиенте. При рендеринге на сервере им соответствуют HTTP-статусы.

### Ресурсы участника курса (ACC2)

- Форма URL сохраняется: `$studentUsername` остаётся локатором `Username`, а `$attemptId` переименовывается в `$attemptNumber`. Название маршрута, хлебные крошки, навигация, идентичность запросов и мок-данные используют одну терминологию.
- Операции фич разрешают локаторы в `UserId` и `AttemptId`. После этого операции и кэш работают со стабильными id.
- У каждой операции свой union-тип исходов, общего `LoadResourceResult<T>` нет. Пример из mm-115:

  ```ts
  type LoadAttemptResult =
    | { status: 'found'; attempt: Attempt }
    | { status: 'not-found' }
    | { status: 'forbidden' };
  ```

- `not-found` и `forbidden` дают одинаковый `404` ресурса внутри оболочки курса.
- Наличие и доступ решает бэкенд (MSW): студент видит только собственные репозиторий, попытки и опубликованные проверки, преподаватель — ресурсы студентов своего курса.
- Ответ обработчика на отказ не несёт данных о ресурсе и его владельце ни в теле, ни в заголовках. Требование к бэкенду записано в mm-113.
- Сравнения username из URL с username из сессии и клиентские проверки состава студентов удаляются.
- **Сопоставление `AttemptNumber` → `AttemptId`** — рабочее допущение до ответа mm-85 (связь номера попытки с UUID попытки на бэкенде), помеченное в обработчиках.
- **Минимальные попытки в MSW.** ACC2 вводит в состояние мок-бэкенда только идентичность попытки: задание, студент, номер и владелец. REV2 расширяет его до единого состояния попыток и проверок. Содержимое страницы попытки остаётся на прежнем источнике до REV2.

### Кэш запросов и сессия (ACC3)

- **Общий префикс.** Все семейства в рамках курса расширяют `['course', courseId, …]`: страница курса, страница задания, список попыток курса, страница попытки и ресурсы участника курса из ACC2. Примеры `['course-pages', courseId]` и `['course-attempts', courseId, …]` в резолюциях — иллюстрация (уточнение в mm-76 — единые ключи запросов и правила согласованности кэша).
- **Вне префикса** остаются только контекст курса (его вход — slug), список курсов (вход — пользователь) и календарь дедлайнов (он охватывает все курсы, этап DEADLINES).
- **Адресация.** Дочерние операции и ключи адресуют `CourseId`. RAM-моки, ещё не переведённые на MSW, адресуются тем же `CourseId`, который выдаёт загрузка курса.
- **Фабрики ключей.** Каждое семейство владеет фабрикой ключей по `docs/agents/remote-data.md`. Сырые константы ключей других фич не импортируются, чужие кортежи вручную не собираются.
- **Вход, выход и замена сессии** очищают весь кэш, привязанный к сессии: контекст курса, список курсов и всё под префиксом курса.
- **Подтверждённая потеря участия** удаляет кэш курса одним вызовом по префиксу `['course', courseId]`.
- **Смена slug.** Старый slug даёт `course-not-found`, псевдонимов (aliases) нет. Кэш страницы курса по `CourseId` остаётся. Сама операция смены slug — DRF1. Пока её нет, существующее сохранение страницы курса инвалидирует контекст курса вместо удалённого ключа старой проверки доступа.

### Мок-бэкенд и канал только для тестов

- В состоянии мок-бэкенда появляются курсы и участия в курсах. Обработчики списка курсов и загрузки курса читают это состояние.
- **Начальные данные для разработки (dev-seed)** остаются демо-набором, согласованным с RAM-моками страницы курса, попыток и проверки, которые ещё не переведены.
- **Мир `world:access`** выбирают тесты:
  - курсы «Алгоритмы» (`open`) и «Базы данных»;
  - Анна и Борис — преподаватели «Алгоритмов»;
  - Саша и Петя — студенты «Алгоритмов»;
  - Вера — студентка «Алгоритмов» и преподаватель «Баз данных»;
  - Гость — вошёл в систему, без участия в курсе;
  - несуществующий slug.
- **`world:review`** в ACC2 расширяет его минимальными попытками Саши и Пети.
- **Канал только для тестов в E2E** — обработчик MSW, доступный только в тестовой сборке. Это не глобальная переменная на `window`, и в продакшен он никогда не попадает. Канал:
  - выбирает мир;
  - задаёт сессию текущего пользователя;
  - удерживает ответ названной операции, пока тест его не отпустит.

  Выбранный мир и сессия переживают полную загрузку страницы, иначе «прямая ссылка» в E2E сбросила бы их к начальным данным. Обычный режим разработки по-прежнему сбрасывает состояние при каждой загрузке. Канал появляется в ACC1 вместе с первым потребителем, отдельного PR «только инфраструктура» нет.
- **Список исключений ESLint** для импортёров RAM-моков сокращается на модули списка курсов и старой проверки доступа.

### Удаляется

- **ACC1:**
  - старая операция проверки доступа и её ключ;
  - поиск курса в списке курсов;
  - охранные редиректы маршрутов курса (redirect guards);
  - редиректы на синтаксически неверные локаторы;
  - роль в сессии;
  - список username студентов в контексте курса;
  - подставные название и доступ в шапке;
  - подсказки в моках, завязанные на глобальную роль, вроде «Текущий преподаватель».
- **ACC2:**
  - проверка владения по username;
  - клиентские проверки состава студентов;
  - `attemptId` в значении «порядковый номер».
- **ACC3:**
  - ключи на slug и username;
  - сырые константы ключей в импортах между фичами;
  - устаревшие пути инвалидации.

## Решения по тестированию

- **Что такое хороший тест.** Тест проверяет наблюдаемый исход через внешний интерфейс: состояние маршрута, которое видит пользователь, объявленный исход операции, содержимое кэша по публичной фабрике ключей. Внутренности не проверяются. Фикстуры именованы, MSW отвечает на уровне протокола, попиксельные скриншоты запрещены (mm-68).
- **Контракты.** Фильтр по этапу в [матрице тестовых контрактов](https://github.com/dsc-sgu/mm-frontend/blob/ddda126c5e73ec787362805c286ee081ee26244d/docs/prototypes/test-contract-matrix.html) (коммит `ddda126`) пишется в PR своего этапа. Каждая новая операция добавляет экземпляр шаблона TR-05: каждый объявленный статус даёт свой исход, необъявленный — `unexpected-http`, невалидный DTO — `invalid-response`.

| Этап | Model / Static | Boundary | Component | Real browser / E2E |
|---|---|---|---|---|
| ACC1 (17) | ACC-01, ACC-02, ACC-03 | ACC-04, ACC-05, ACC-09 | ACC-10…15, ACC-17 | ACC-E2, ACC-E3, ACC-E5, A11Y-01 (`403`, `404`) |
| ACC2 (3) | — | ACC-08 | ACC-16 | ACC-E1 |
| ACC3 (3) | — | ACC-06, ACC-07 | — | ACC-E4 |

- **Инварианты fail-closed** I1 (точная идентичность) и I2 (нет доступа к чужому) доказываются независимо на нескольких уровнях тестирования, включая браузер.

**Швы** (согласованы):

- **Модельный уровень и статический анализ (Model и Static).** Таблица правил доступа к разделам курса × роль (исчерпывающе), отображение внутреннего исхода в категорию состояния маршрута, тесты типов на различимость типов идентичностей через `@ts-expect-error`.
- **На границе API (Boundary).** Операции и их query options с настоящим QueryClient против MSW в Node на `world:access`/`world:review`. Образец — тесты операций входа и их query options.
- **Компонентный уровень (Component).** Настоящее дерево маршрутов приложения с историей в памяти (memory history), настоящей шапкой (Header), свежими Router и QueryClient и MSW в Node. Делается опцией существующей тестовой обвязки для рендеринга маршрутов. Тест видит то же, что пользователь: состояние маршрута, оболочку курса, хлебные крошки, навигацию. Только так ловится маршрут, который забыл применить правила доступа к разделам курса (ACC-12 параметризован по всем разделам только для преподавателей).
  - Риск: в Vitest нет плагина роутера для разделения кода (code splitting), поэтому дерево загружает в jsdom все модули маршрутов, а раскладка для вошедшего пользователя монтирует пул Workers страницы попытки. Это решается в ACC1: подменой модуля Worker в конфиге тестов или переносом пула на маршруты проверки.
  - Образец — тесты ошибки маршрута и выхода из аккаунта.
- **В браузере (E2E).** Playwright в Chromium, Firefox и WebKit, приложение целиком с MSW в браузере. Мир, сессию и удержанные ответы задаёт канал только для тестов.
  - ACC-E4 — единственный сценарий, где выход идёт через шапку, а вход — через форму входа: он проверяет смену сессии в той же вкладке без перезагрузки.
  - Образец — E2E-тесты страницы проверки попытки.
- **A11Y-01.** Axe на устойчивых состояниях `403` и `404` появляется в ACC1. Экраны других вертикалей добавляют их этапы.

**Этап готов**, когда проходят линтер и сборка, а все его контракты зелёные в трёх движках.

## Вне области

- **Чужие этапы:**
  - операция смены slug и согласованность адреса — DRF1;
  - чтение опубликованной страницы курса поверх снапшотов — READ;
  - календарь дедлайнов на Fetch — DEADLINES;
  - перевод данных попыток, проверок и списка попыток курса на MSW — REV2 и ATT1;
  - модель прав на ответы и бронь проверки — вертикаль проверки.
- **Интерфейс входа и регистрации.** Авторизация на моках, целевой сценарий входа сменится с OpenID. Закрепляется только редирект невошедшего пользователя на вход (ACC-17).
- **Содержимое персонального журнала** (mm-99). Проверяется только доступ к разделу.
- **Формат API бэкенда.** Окончательные URL и статусы, псевдонимы и канонизация slug, сопоставление номера и UUID попытки — mm-113 и mm-85. Контрактные тесты против настоящего бэкенда — вне карты.
- **Смена username.** Операции записи профиля пока нет. Правило из mm-115 (`UserId` неизменен, сессия согласуется до завершения успешного сценария, старый username в URL заменяется) применяется, когда она появится.
- **Универсальный фреймворк прав**, права на операции записи и владение ресурсами за пределами загрузок ресурсов участника курса.

## Дополнительно

### Этапы

Дочерние тикеты этого эпика; порядок задают зависимости между ними. Контракты каждого тикета — подмножество контрактов его этапа в матрице.

| id | Тикет | После |
|---|---|---|
| ACC1.1 | mm-168 — «Мои курсы» из мок-бэкенда через Fetch | — |
| ACC1.2 | mm-169 — вход в курс через загрузку по slug с явным `404` и отказом проверки доступа | ACC1.1 |
| ACC1.3 | mm-170 — правила доступа к разделам курса с явным `403` | ACC1.2 |
| ACC2.1 | mm-171 — номер попытки называется `attemptNumber` | ACC1.1 |
| ACC2.2 | mm-172 — доступ к репозиторию и попытке решает бэкенд по стабильным идентичностям | ACC1.3, ACC2.1 |
| ACC3 | mm-173 — кэш курса под `CourseId` и его очистка при смене сессии | ACC2.2 |

Между ACC1.2 и ACC1.3 на раздел не по роли ещё отвечает редирект, но роль уже берётся из нового контекста курса.

**Решения, принятые этой спецификацией** поверх резолюций, — их стоит перепроверить при нарезке тикетов:

1. **Список username студентов** исчезает из контекста курса в ACC1 вместе с проверкой состава студентов у преподавателя. До ACC2 студент на чужом ресурсе участника курса получает `404` ресурса по прежнему сравнению username, без редиректа. ACC2 заменяет сравнение исходом от бэкенда.
2. **Редактирование задания** покрывается разделом `edit`, **редактор проверки** — разделом `attempts`. В таблице остаётся 7 разделов (ACC-01).
3. **ACC2 вводит минимальные попытки в MSW** раньше REV2. Проверки в MSW по-прежнему проектирует только REV2, двойного проектирования нет (mm-69: «ATT1 ждёт REV2»).
4. **Ключи списка курсов содержат `UserId`** по правилу mm-115 для проекций, зависящих от пользователя.

**Уточнения закрытых тикетов**, перенесённые сюда:

- mm-75: роль — отношение пользователя к курсу, а не свойство аккаунта; подсказки в моках, завязанные на глобальную роль, убираются.
- mm-76: общий префикс курса и фабрики ключей.
- mm-84: `attemptNumber` во всех потребителях.
- mm-89 и mm-78: список курсов и доступ — на Fetch и MSW, модули фич не импортируют реализацию мок-бэкенда.

**Кто ждёт доступа к курсу.** Связи с этими тикетами добавляются, когда заводятся эпики их групп:

- **Проверка (Review):** REV1 ждёт ACC3.
- **Список попыток курса (Course Attempts):** ATT1 ждёт ACC3.
- **Редактирование курса (Course editing):** DRF1 ждёт ACC1.2 (контекст курса с `CourseId`), READ — ACC3.
- **Хвост:** DEADLINES ждёт ACC3.

**Правила этапов** — из mm-69: один этап — один PR, замена за один шаг; контракты пишутся в PR своего этапа; вопросы к бэкенду не блокируют этапы; продуктовые тикеты в зоне доступа к курсу берутся только после этих этапов или переформулируются на новые швы.
