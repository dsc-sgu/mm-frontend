# Согласовать, как номер попытки attemptNumber связан с UUID попытки на бэкенде

## Делает

Согласовывает между фронтендом и бэкендом контракт идентичности попытки: пользователь и маршрут обращаются к попытке по `attemptNumber`, бэкенд может хранить внутренний UUID, а контракт API однозначно связывает эти значения и не закрепляет случайную форму ещё не влитой реализации.

Учитывать [mm-backend PR #159 «Attempt, Task, Git API»](https://github.com/dsc-sgu/mm-backend/pull/159), [mm-backend PR #164 «refactor: reworked based on design doc»](https://github.com/dsc-sgu/mm-backend/pull/164) и [исследование бэкенда](https://github.com/dsc-sgu/mm-frontend/blob/a25a8ed9f8c485f5aaad5ba0beba4f7909a9cf63/docs/research/backend-snapshots.md).

## Готово, когда

- [ ] Записано, где API использует `attemptNumber`, а где внутренний UUID.
- [ ] Определено, как курс, задание, студент и `attemptNumber` разрешаются в одну попытку на бэкенде.
- [ ] Определено, возвращается ли UUID в DTO и нужен ли он фронтенду.
- [ ] Эндпоинты списка попыток, проверки и diff одинаково понимают идентичность попытки.
- [ ] Решение согласовано с командой бэкенда и записано там, где его видят оба репозитория.
- [ ] Мок-бэкенд на MSW может воспроизвести решение и не зависит от формы ещё не влитой ветки.

## Связи

- Появился в mm-63 — карте реализованной системы фронтенда.

## Интеграционные предпосылки и образцы

Новых блокеров на рефакторинг нет: тикет закрепляет контракт API, а не реализует экран. Frontend-first решение уже принято: внешние маршруты используют номер попытки и локаторы, а операции после разрешения используют стабильный AttemptId; UUID хранения бэкенда не должен диктовать адрес UI. Реализованные части не требуется переписывать под ещё одну промежуточную модель.

Проверенные образцы origin/main: `src/features/course/model/identity.ts` — различение AttemptId и AttemptNumber; `src/features/course/features/attempt-review/api/load-attempt.ts` — разрешение курса/задания/username/номера в AttemptId и стабильный UserId; `attempt-review/api/locator-queries.ts` — отдельный кэш разрешения локатора; `attempt-review/api/load-student-attempts.ts`, `review/api/load-review.ts` и `attempt-review/api/load-material.ts` — чтения по стабильным идентичностям. `src/features/course/features/access/api/participant-resources.test.ts` закрепляет серверный доступ и различие пользователей с совпадающими номерами попыток.

Не копировать старые агрегаты страницы задания и списка попыток, где attemptNumber или username подменяют идентичность; не вводить временный адаптер AttemptId → username/номер ради вызова старого чтения. Тикет должен документировать уже выбранное разделение локатора и идентичности, уточнить единые DTO/результат отправки для mm-280 и зафиксировать работу реализации бэкенда в mm-113. Исторические ссылки на старые ветки бэкенда не являются актуальным источником обязательных полей. mm-222/mm-227 не нужны для записи этого решения и не должны задерживать её.

Проверено по `origin/main` (`045ea6d`). Наличие решения в спецификации или рабочей ветке не означает, что его реализация уже доступна в `main`. Перед реализацией перечитать `docs/agents/remote-data.md` и проверить актуальность указанных путей.
