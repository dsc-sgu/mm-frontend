# Спроектировать вертикаль: проверка → оценка → результат студента

## Question

Какие целевые модули, интерфейсы и швы должны провести критический путь от выбора неизменяемой попытки до публикации целостной версии проверки и её согласованного отображения в редакторе проверки, списке попыток курса, истории попыток задания и результате студента? Решение должно определить, кто владеет точной идентичностью попытки, авторитетным манифестом изменённых файлов и состоянием полноты, отказом diff Worker, рабочей копией проверки, атомарной первой публикацией с оценкой, ожиданием и сверкой исхода и согласованностью кеша между фичами; использовать выбранный Plate-native контракт текста проверки и не проектировать окончательный API бэкенда. Итогом должна быть декомпозиция будущего рефакторинга вертикали на независимые проверяемые этапы без изменения production/source code или тестов.

## Решение: проверка → оценка → результат студента как атомарные версии проверки

Решение задаёт целевую форму второй по риску вертикали. Окончательный API бэкенда здесь не проектируется: зависимости от бэкенда внесены в mm-113 «Реестр frontend-вопросов к backend API». Production/source code и тесты не изменялись.

### Термины и места

- **Список попыток курса** («Попытки») — список всех попыток курса для преподавателя. Прежнее «workbench» заменено во всех тикетах карты.
- **Страница попытки** («Попытка #N», `…/$attemptNumber`) — неизменяемая попытка и её опубликованная проверка. Здесь студент видит свой результат, а преподаватель смотрит без брони. Ответы доступны обоим.
- **Редактор проверки** («Проверка попытки #N», `…/$attemptNumber/review`) — только для преподавателя: бронь проверки, рабочая копия проверки, публикация. Прежнее «Review workspace» заменено.
- **Манифест изменённых файлов** — инженерный термин контракта (в UI «Изменённые файлы»): авторитетная опись записей попытки относительно базы сравнения, по которой проверяется полнота.
- Rich-text редактор называется **редактором текста проверки**, чтобы «редактор проверки» означал только страницу.
- В коде `score`/`maxScore` заменяются на `grade: Grade` и `Task.maxGrade`; `publishedAt`/`publishedBy` — атрибуты версии проверки, а не оценки.

Глоссарий в `CONTEXT.md` дополнен терминами «версия проверки» (Review Revision) и «рабочая копия проверки» (Review Working Copy), уточнены «оценка», «тред к строкам», «бронь проверки» и «прочитанность проверки». Атомарность версии записана в ADR [`docs/adr/0001-atomic-review-revision.md`](https://github.com/dsc-sgu/mm-frontend/blob/docs/review-grade-vertical/docs/adr/0001-atomic-review-revision.md); изменения глоссария и ADR — в PR [«docs: record review vertical glossary and ADR»](https://github.com/dsc-sgu/mm-frontend/pull/126).

### Версия проверки и ответы

- Версия проверки — оценка, общий отзыв и комментарии преподавателей. Всё это копится в рабочей копии проверки и становится видимым студенту одной публикацией. Мгновенная публикация отдельных комментариев преподавателя отвергнута: студент видел бы частично пересмотренную проверку.
- Ответы студента и преподавателей — отдельные мгновенные операции вне рабочей копии, версии и брони проверки. Сейчас они попадают в payload Save полной заменой и могут затереть ответ студента; это уходит.
- Держатель брони меняет оценку, общий отзыв и свои комментарии, но не чужие.
- Удалённый комментарий преподавателя оставляет пометку «Комментарий удалён», ответы других авторов сохраняются.
- Новая версия или ответ преподавателя делает проверку непрочитанной; собственные ответы студента — нет.

### Бронь проверки

- Бронь покрывает проверку конкретной попытки, включая первую публикацию.
- Берётся автоматически при входе в редактор проверки. Страница попытки бронь никогда не берёт.
- Принадлежит сессии редактора проверки: клиент генерирует `leaseId`; в UI показывается имя преподавателя. Вторая вкладка того же преподавателя открывается только для чтения с действием «Продолжить здесь» (явный перехват брони тем же пользователем).
- Heartbeat примерно каждые 20 с, пока редактор проверки открыт, и сразу при возвращении на вкладку. Если своя бронь истекла незаметно (замедление таймеров в фоне), редактор проверки сразу бронирует проверку снова; если её уже забронировал другой преподаватель — состояние `interrupted`.
- Снимается при уходе из редактора проверки и при переключении попытки через selector. Публикация бронь не снимает.
- Если проверка уже забронирована при входе: только чтение, «Проверяет X» и действие «Попробовать взять на проверку»; держатель обновляется при фокусе. Автоматического захвата нет.
- Механика повторяет бронь курса в бэкенде (TTL, heartbeat, `423` с держателем). `leaseId` от клиента возвращает реализацию к замыслу ADR бэкенда о «сессии в браузере».
- Realtime не требуется для корректности. Предпочтительное направление — SSE (mm-98 «Согласовать SSE protocol для realtime-обновлений Review и lease»), события служат подсказками для инвалидации.
- Бронь остаётся внутренним модулем `review`. Общий модуль с редактированием курса появится, когда mm-118 «Спроектировать lifecycle Course Page Working Copy» придёт к тому же протоколу.

### Идентичность и материал попытки

- Локаторы маршрута разрешаются в стабильные `CourseId`, `TaskId`, `UserId` и `AttemptId` по mm-115 «Спроектировать Course access vertical и identity seam»; дальше операции и ключи запросов используют только стабильные ID.
- Базу сравнения выбирает бэкенд и описывает её в манифесте: попытка (возможно, другого задания той же цепочки заданий), шаблон или пустое дерево. Фронтенд показывает «Сравнение с …» и адресует материал только `AttemptId`.
- Сначала загружается атомарный манифест, затем содержимое по записям (транспорт может группировать). Содержимое неизменяемо. Автоматический retry ограничен для каждой записи, ручной retry — только для упавших.
- Полнота — чистая функция от манифеста и статусов записей. Будущий streaming заменит только способ доставки.
- Публикация разрешена только после загрузки всех записей манифеста. Нетекстовой записи (`binary`, `too-large`, `unsupported`) достаточно явной пометки «не отображается». Это ослабляет прежнее требование «дать способ проверить содержимое».
- Diff Worker монтируется только на странице попытки и в редакторе проверки, состояния `loading | ready | failed` с Retry. `failed` блокирует публикацию, поля рабочей копии остаются редактируемыми.

### Оценка

- Тип `Grade` создаётся только проверенным разбором ввода (`,` и `.`). Больше трёх знаков после запятой — ошибка, а не округление. Сравнение и сложение в целых тысячных. `maxGrade` подчиняется той же точности.
- Пустое поле оценки — невалидная рабочая копия и для первой, и для существующей проверки. Команды «снять оценку» нет.

### Публикация и неопределённость

```ts
type PublishReviewInput = {
  attemptId: AttemptId;
  leaseId: LeaseId;
  baseRevision: ReviewRevisionNumber | null; // null — первая Review
  idempotencyKey: IdempotencyKey;
  grade: Grade;
  overallFeedback: ReviewTextDocument | null;
  ownRootComments: readonly OwnRootComment[]; // полный набор своих, id новых генерирует клиент
};

type PublishReviewResult =
  | { status: 'published'; revision: ReviewRevision }
  | { status: 'revision-conflict'; latestRevision: ReviewRevisionNumber }
  | { status: 'lease-not-held'; holder: TeacherSummary | null }
  | { status: 'not-found' }
  | { status: 'forbidden' };
```

Это форма уровня домена, не DTO.

- Отказ операции (сеть, `5xx`, невалидный ответ) означает неизвестный исход: `publication-unconfirmed`. Рабочая копия заморожена, потому что тот же ключ обязан нести то же содержимое. Повтор идёт с тем же `idempotencyKey`: сначала ограниченный автоматический, затем «Повторить». Уход со страницы предупреждает «Публикация не подтверждена». Ответ на повтор является авторитетной сверкой; ложный успех, мгновенный провал и вторая проверка исключены.
- `revision-conflict` или потеря брони переводят редактор проверки в `interrupted`. Показывается авторитетная последняя версия, а рабочая копия уходит в панель «Неопубликованные изменения»: оценка, общий отзыв и каждый свой комментарий с привязкой, всё можно скопировать. После того как преподаватель снова забронирует проверку, новая рабочая копия строится от последней версии, элементы переносятся кнопкой «Применить». Автоматического слияния нет.
- Несохранённая рабочая копия защищена подтверждением при навигации, переключении попытки и закрытии вкладки; бронь снимается только после подтверждения ухода.
- Восстановление из браузера отложено, но рабочая копия — сериализуемые данные с пометкой `attemptId + baseRevision`. Позже восстановление использует ту же панель восстановления. Отдельный тикет вне карты: mm-125 «Восстанавливать неопубликованную Review Working Copy из браузера».

### Редактор проверки как глубокий модуль

- Чистая функция `transitionReviewSession(state, event)` с состояниями `loading | unavailable | viewing | editing | publishing | publication-unconfirmed | interrupted`.
- `useReviewSession(attemptId, intent)` отдаёт состояние и намерения: `editGrade`, `editFeedback`, `editOwnComment`, `publish`, `retryPublication`, `tryTakeLease`, `continueHere`, `applyRecoveryItem`, `discardRecovery`. Бронь, загрузка версии, повторы публикации и обновление проекций скрыты внутри.
- `getPublishGate(...)` возвращает `{ status: 'ready' }` либо `{ status: 'blocked'; reasons }`. Причины: бронь не моя, версия не загружена, материал неполон (число записей), Worker `failed`, оценка отсутствует, больше максимума или с лишними знаками, нет изменений, публикация идёт или не подтверждена. UI показывает все текущие причины.

### Результат студента

- Страница попытки показывает оценку и общий отзыв независимо от diff. При сбое diff треды появятся вместе с ним.
- Без проверки — diff и «Ещё не проверено», без отметки прочитанности.
- `markReviewSeen` передаёт то, что студент действительно видел: номер версии и последний показанный ответ преподавателя. Оптимистичная отметка `seen` сохраняется.

### Согласованность оценки на всех экранах

- Каждая проекция с оценкой несёт номер версии проверки: проверка, selector попыток, список попыток курса, история попыток на странице задания. Будущий журнал студента объявит зависимость сам.
- `observeReviewRevision(queryClient, { attemptId, courseId, taskId, studentId, revision })` в `review`:
  - монотонно пишет авторитетную проверку в свой кеш (отменяя идущий запрос; старая версия не заменяет новую);
  - инвалидирует чужие проекции по префиксу через их публичные фабрики ключей, не читая их данных.

  Её вызывают публикация, загрузка проверки, быстрое оценивание и будущий SSE. Это не шина событий.
- Сравнение версий происходит только внутри каждого владельца кеша.
- Все ключи запросов в пределах курса расширяют общий префикс `['course', courseId, …]`, как требует mm-76 «Унифицировать ключи запросов и правила согласованности кеша»; вне его остаётся только поиск курса по slug. Примеры ключей в решениях вертикалей доступа к курсу и списка попыток курса считаются иллюстрацией.
- Сообщение «идёт синхронизация» показывается только при явном сигнале бэкенда. Каждый ответ обязан содержать одну целостную версию.

### Этапы будущего рефакторинга

Предпосылки: идентичность и поиск попытки из вертикали доступа к курсу, малое транспортное ядро и MSW, общий префикс ключей курса. Каждый этап — замена за один шаг, без слоёв совместимости, и проверяется через интерфейс своего модуля и наблюдаемый исход маршрута; сценарии задаёт mm-120 «Спроектировать матрицу тестовых контрактов критических вертикалей».

1. **Оценка.**
   - Делает: тип `Grade`, поле оценки в `course`, пустое поле невалидно, `score` → `grade`.
   - Удаляет: `grading`, `score`/`maxScore`.
2. **Раздельные операции чтения и единое состояние мок-бэкенда.**
   - Делает: проверка по `AttemptId`, selector и история студента из одного состояния попыток и проверок; номер версии в каждой проекции; `reviewKeys` и ключи проекций под общим префиксом.
   - Удаляет: агрегирующий `fetchAttemptReview`, захардкоженный мок истории.
3. **Материал попытки и готовность diff.**
   - Делает: манифест и содержимое по записям, `useAttemptMaterial`, retry упавших, пометка нетекстовых записей; Worker pool на уровне маршрута с `loading | ready | failed`.
   - Удаляет: вычисление изменённых файлов на клиенте, Worker pool на всём `_authenticated`, бесконечный loader.
4. **Текст проверки на Plate.**
   - Делает: редактор текста проверки и readonly-отображение по `ReviewTextDocument` для общего отзыва, комментариев преподавателей и ответов; граница доверия HTML только для paste; диалог вместо `window.prompt`.
   - Удаляет: TipTap, HTML в модели.
5. **Ответы вне рабочей копии.**
   - Делает: мгновенные операции независимо от брони, пометка удалённого комментария преподавателя, ответ преподавателя делает проверку непрочитанной.
   - Удаляет: ответы в рабочей копии и Save.
6. **Ядро редактора проверки.**
   - Делает: `transitionReviewSession`, `getPublishGate`, команда публикации и её исходы, `publication-unconfirmed`, `interrupted` с панелью восстановления, защита при уходе (mm-87 «Предупреждать об уходе с несохранённого attempt review»), `observeReviewRevision`.
   - Удаляет: `useAttemptReviewDraft`, статусы `pending-*`, «очистку» оценки, ручную инвалидацию в Save.
7. **Бронь проверки.**
   - Делает: `leaseId`, бронирование при входе, heartbeat и повторное бронирование, снятие при уходе, «Проверяет X», «Продолжить здесь», потеря брони → `interrupted`.
   - Удаляет: мок-события брони для проверки.
8. **Результат студента и прочитанность.**
   - Делает: сводка без зависимости от diff, «Ещё не проверено», отметка по фактически увиденному, непрочитанность в истории из того же состояния.
   - Удаляет: `TaskAttemptAttention`.

Порядок внутри вертикали:
- 4 идёт до 5 и 6, чтобы рабочая копия и ответы сразу строились на `ReviewTextDocument`.
- 7 идёт после 6: между ними публикацию защищает только `baseRevision`. Целостность сохраняется, страдает лишь удобство совместной работы.
- Быстрое оценивание из mm-117 «Спроектировать individual Course Attempts vertical» опирается на этапы 1 и 6.
- Порядок относительно других вертикалей определяется в mm-69 «Определить последовательность подготовки и выполнения рефакторинга».

## Уточнения из mm-120, комментарий от 2026-10-11T06:53:09Z «Спроектировать матрицу тестовых контрактов критических вертикалей»

- **Вкладки одного браузера.** Пишет одна вкладка, остальные показывают лайв-копию рабочей копии только для чтения. «Продолжить здесь» меняет пишущую вкладку локально, без обращения к серверу: добровольно, если пишущая вкладка отвечает, или силой после таймаута. Бронь привязана к браузеру — к сессии входа, как бронь курса на `mm-backend@ddd9849`; клиентского `leaseId` нет. Единственность пишущей вкладки обеспечивают Web Lock и счётчик передач в localStorage, который сверяется синхронно перед каждой записью. Перехват брони тем же пользователем остаётся только для другой сессии: другого устройства или приватного окна. Протокол проектируется в mm-132 «Спроектировать смену пишущей вкладки редактора». Это заменяет «вторая вкладка того же преподавателя открывается только для чтения с «Продолжить здесь»» и `leaseId` в брони проверки и в контракте публикации.
- **Привязка комментария преподавателя.** Выделение строки или диапазона в diff выбранного файла и стороны привязывает комментарий к этому диапазону; после публикации студент видит тред на тех же строках. Это контракт целостности (REV-12): комментарий не на той строке вводит студента в заблуждение так же, как неверная оценка. Как бэкенд хранит привязку, спрошено в mm-113 «Реестр frontend-вопросов к backend API».

Контракты: REV-12, REV-32, REV-E5, TAB-01…TAB-09.

## Уточнения из mm-132, комментарий от 2026-10-11T11:21:50Z «Спроектировать смену пишущей вкладки редактора»

- **Вкладки редактора проверки.**
  - Пишет одна вкладка браузера, остальные показывают лайв-копию: полную рабочую копию проверки после каждого изменения.
  - «Продолжить здесь» передаёт рабочую копию локально. Добровольно — если пишущая вкладка отвечает; силой — если она молчит 3 с, и только от лайв-копии.
  - Закрытая пишущая вкладка передаёт роль первой лайв-копии в очереди, и та продолжает сама. Бронь снимается, когда уходит последняя вкладка редактора проверки этой попытки.
- **Публикация при передаче.** Запрос в полёте пишущая вкладка дожидается. `publication-unconfirmed` передаётся вместе с `idempotencyKey` и замороженной рабочей копией, повторы продолжает новая вкладка (TAB-04).
- **`interrupted`** видят все вкладки браузера. `423` с держателем брони — самим пользователем: «Открыт в другой сессии — на другом устройстве или в другом окне · Вернуть сюда».
- **Выход из аккаунта** останавливает запись во всех вкладках. Рабочая копия скрыта и держится до входа тем же пользователем; вход другим пользователем её удаляет.
- В `useReviewSession` намерение `continueHere` теперь означает локальную передачу между вкладками. «Вернуть сюда» — отдельный перехват брони тем же пользователем из другой сессии.
