# Открывать попытку и репозиторий студента по идентичности из перехода и обновлять адрес при смене username

## Зачем

Маршруты попытки (`…/attempts/$studentUsername/$attemptNumber`) и репозитория студента (`…/repositories/$studentUsername`) при каждом переходе заново запрашивают локатор (`staleTime: 0`). Так происходит, даже когда идентичность уже известна: из ответа предзагрузки (preload) при наведении, или из переключателя попыток. Это лишний сетевой круг на действии, которое преподаватель повторяет чаще всего, — переключении попыток во время проверки.

По [ADR 0005](https://github.com/dsc-sgu/mm-frontend/blob/main/docs/adr/0005-locator-urls-resolved-to-stable-identities.md) при переходе внутри приложения намерение пользователя — идентичность, а адрес лишь следует за ней. Поэтому переход берёт идентичность из кэша, а устаревший адрес исправляется через `replace`. Сейчас бэкенд не умеет менять username, так что вторая часть — задел; первая ускоряет переключение уже сегодня.

## Делает

1. **Переход не ждёт локатор, если идентичность уже известна.**
   - `beforeLoad` маршрутов попытки и репозитория берёт исход `found` из кэша локатора. `forbidden` и `not-found` не кэшируются и всегда перепроверяются, например `staleTime: (query) => (query.state.data?.status === 'found' ? … : 0)`.
   - Время жизни `found` — не меньше времени жизни списков, из которых заполняется кэш.
   - Вход по URL без кэша (ссылка, закладка, перезагрузка) по-прежнему ждёт свежий ответ локатора.
2. **Переключатель попыток заполняет кэш локатора** через `setQueryData` для каждой попытки с известной `AttemptId` (`attempt-review/ui/attempt-select.tsx`).
3. **Адрес следует за идентичностью.**
   - Сводка попытки (`loadAttemptSummary`) возвращает текущий `student.username`. Это рабочее допущение контракта до ответа бэкенда (mm-113, «Адресация попытки: номер и UUID» → «Текущий username»): обновить схему, мок и тесты.
   - Сегментами `studentUsername` и `attemptNumber` владеет только сводка попытки. Списки, комментарии и другие чтения показывают username как текст, но на адрес не влияют.
   - Если сводка расходится с параметрами маршрута, страница кладёт в кэш локатора соответствие «новые параметры → та же идентичность» и вызывает `navigate({ to: '.', params, replace: true })`.
   - Для репозитория то же самое. Владелец сегмента — чтение репозитория по идентичности; если в нём нет username, добавить допущение в контракт и вопрос в mm-113.
4. **Страница не перемонтируется при `replace`.**
   - `remountDeps` и `defaultRemountDeps` не задаются. Без них роутер рендерит компонент маршрута без `key` (`@tanstack/react-router` 1.170.42, `src/Match.tsx` L194–L214), и React сохраняет состояние.
   - У маршрутов попытки и репозитория нет `pendingComponent`, иначе `replace` покажет индикатор загрузки.

## Не входит

- Сегмент курса (`courseSlug`): mm-254, там мешает guard маршрута курса.
- Заполнение кэша из списка попыток курса и истории попыток задания: после перевода этих списков на `AttemptId` (ATT1).
- Фоновая перепроверка локатора с блокировкой записи до её ответа: отвергнута в [ADR 0005](https://github.com/dsc-sgu/mm-frontend/blob/main/docs/adr/0005-locator-urls-resolved-to-stable-identities.md).
- Канонический адрес в ответе локатора при входе по старой ссылке: ждёт ответа бэкенда (mm-113, «Смена локатора: история, повторное занятие и канонический адрес»).

## Готово, когда

- Переключение попытки после наведения или из заполненного кэша не делает запрос локатора. Тест считает запросы MSW.
- Вход по URL без кэша делает один запрос локатора, как сейчас.
- Закэшированный `forbidden` или `not-found` не используется: повторный вход перепроверяет.
- Когда сводка попытки возвращает другой username, адрес меняется через `replace`. При этом нет запроса локатора и индикатора загрузки, введённая оценка и черновик комментария на месте, а «Назад» не возвращает на старый адрес.
- То же для репозитория студента.
