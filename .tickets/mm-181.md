# Запрототипировать настройку Task и дедлайнов

## Question

Как выглядит настройка Task вместе с дедлайнами? Нужно увидеть:

- где Teacher правит свойства Task и все дедлайны Course;
- как применяются правки;
- как показан массовый сдвиг дедлайнов.

- Решения о настройке Task и Task Groups из [#180](https://github.com/dsc-sgu/mm-frontend/issues/180) — комментарий «Решение». По ним добавлены разделы «Применение правок Task» и «Поля панели».
- Прототип [#101](https://github.com/dsc-sgu/mm-frontend/issues/101) «Запрототипировать боковое редактирование задания» влит сюда, см. раздел «Боковая панель на Course Page». [#41](https://github.com/dsc-sgu/mm-frontend/issues/41) и [#106](https://github.com/dsc-sgu/mm-frontend/issues/106) заменит спецификация «Настройка Task и Task Groups». Её пишут после всей цепочки прототипов.
- **Цепочка прототипов в одной песочнице:** этот → [«Запрототипировать управление Task Groups»](https://github.com/dsc-sgu/mm-frontend/issues/190) → [«Запрототипировать редактор масок путей»](https://github.com/dsc-sgu/mm-frontend/issues/191). Каждый следующий строится поверх предыдущего. Сквозной просмотр всего пути — в конце последнего; на нём вердикт этого прототипа можно пересмотреть.

## Дедлайны: что сравнить

Решено в гриллинге #42.

- **Четыре варианта места экрана:**
  - **A, раздел «Дедлайны».**
    - Матрица «Task × Student Group»: унаследованные значения бледные, явные обычные, «без срока» отмечен.
    - Личные Deadline Overrides — счётчик в строке Task, раскрывается списком с причинами.
    - Поиск Student показывает его Effective Deadline по всем Task и откуда взялся каждый срок.
  - **B, список Task и боковая панель.** Список Task с общими сроками. Клик открывает боковую панель с редактором всех переопределений этой Task.
  - **C, в редакторе Course Page.** Чипы сроков по группам на карточках Task Reference, правка в popover. Сохраняется отдельно от Course Draft Snapshot.
  - **D, таймлайн.** Строки Task, отметки групп и Students на оси времени, сдвиг перетаскиванием.
- **Применение правок:** переключатель `?apply=instant|batch` во всех вариантах. Сравниваем мгновенное сохранение каждого значения и «Применить» с предпросмотром «было → стало».
- **Связь с полем дедлайна в панели #41.** Рекомендованный вариант: поле правит только общий Deadline, рядом «Переопределений: N» со ссылкой на экран дедлайнов. Сравнить с альтернативами, например с полным редактором переопределений прямо в панели.
- **Массовый сдвиг.**
  - Teacher выбирает Task и адресатов: весь Course или конкретные Student Groups.
  - Видно, как сдвигается каждое значение: общее, групповое, личное.
  - Каждое переопределение можно отдельно включить в сдвиг или исключить.
  - Предпросмотр предупреждает, сколько уже отправленных Attempts станут опоздавшими или перестанут быть ими.
- **Task Opening Time на экране сроков** (#180):
  - показывается рядом с Deadline, и массовый сдвиг может его включать. Пример: семестр начался на неделю позже;
  - в предпросмотре видно, скольким Students Task уже открыта: для них перенос на более позднее время ничего не меняет;
  - своё время открытия для Student Group — вне прототипа ([#186](https://github.com/dsc-sgu/mm-frontend/issues/186)).

## Боковая панель на Course Page

Перенесено из #101. Вопрос из [спецификации #100](https://github.com/dsc-sgu/mm-frontend/issues/100): как Teacher правит Task прямо из обычного просмотра Course, не переходя в редактор всего документа.

- **Два поведения панели:**
  - наложение поверх документа: ширина документа сохраняется, но панель закрывает часть содержимого;
  - место рядом с документом: содержимое остаётся открытым, но документ перестраивается.
- **Где править условие Task:** в панели, прямо в документе или в развёрнутом, полноэкранном состоянии.
- **Готово, когда:**
  - оба поведения доступны в одном сценарии с Task в середине длинного Course;
  - открытие и закрытие панели сохраняют выбранную Task и понятное положение в документе;
  - проверены узкий и широкий desktop и телефон;
  - проверена правка короткого и длинного условия;
  - видны состояния: просмотр, правка, ошибка валидации, применённое изменение;
  - результат называет выбранный вариант, причины и ограничения для [#41](https://github.com/dsc-sgu/mm-frontend/issues/41).
- **Связь с экраном дедлайнов.** Поле дедлайна в этой панели сравнивается по пункту «Связь с полем дедлайна в панели #41» выше.

## Применение правок Task

По [#180](https://github.com/dsc-sgu/mm-frontend/issues/180): модель зависит от [#129](https://github.com/dsc-sgu/mm-frontend/issues/129). Если Task — подтип блока, правки идут через Course Draft Snapshot (A). Если отдельный версионируемый ресурс — отдельной публикацией Task с проверкой версии (D). Расписание (Deadline, Deadline Overrides, Task Opening Time) в обоих случаях применяется отдельно, по правилам раздела «Дедлайны».

Переключатель `?taskApply=course|task`. A показывается честно: правка из просмотра берёт Course Editing Lease, пишет в черновик и публикует весь черновик, а рядом с кнопкой список того, что уйдёт вместе с правкой. Прототип должен стать доводом в #129.

По умолчанию Course `open`. Сценарии:

| # | Сценарий | A (`course`) | D (`task`) |
|---|---|---|---|
| 1 | Правка в режиме редактирования Course | правка уходит в Course Draft Snapshot, публикует общий бар | у Task своя кнопка «Опубликовать» |
| 2 | Из просмотра: исправить опечатку в условии. Черновика нет, lease свободен | панель берёт Course Editing Lease, пишет в черновик, публикуется весь курс | публикуется только эта Task |
| 3 | Из просмотра, когда у этого Teacher уже есть свой неопубликованный черновик с правками страницы | исправление уйдёт вместе с правками страницы, панель перечисляет, что ещё опубликуется | Task публикуется отдельно, черновик остаётся как был |
| 4 | Из просмотра, пока lease держит другой Teacher | панель только для чтения: «Курс редактирует …» | правка доступна |
| 5 | Два Teacher одновременно правят одну Task | невозможно из-за lease | второй получает конфликт версий |
| 6 | Черновик устарел: другой Teacher опубликовал курс раньше | правка Task попадает в устаревший черновик | не влияет |
| 7 | В одной правке меняются условие и Deadline | условие уходит в черновик, срок применяется отдельно (#42) | две отдельные операции за одной кнопкой или двумя |

## Поля панели

Набор и правила — по [#180](https://github.com/dsc-sgu/mm-frontend/issues/180):

| Поле | Обязательно | По умолчанию | После открытия Course |
|---|---|---|---|
| Название | да | — | меняется |
| Условие, вложения, аннотация Task Summary | нет | — | меняются |
| Task Key | да | транслит названия | только чтение |
| Task Group и раздел группы | да | Q5, решается в [#190](https://github.com/dsc-sgu/mm-frontend/issues/190) | только чтение, кроме названия группы |
| Максимальная Grade | да | нет | только чтение |
| Маски путей | нет: пусто — любые файлы | — | меняются |
| Task Opening Time | нет: пусто — время не сдерживает | — | меняется |
| Deadline уровня Task и «Переопределений: N» | нет | без срока | меняется |

- **Task Opening Time:** тот же контрол, что у дедлайна; время по умолчанию 00:00. Если время открытия позже Deadline или чьего-то Effective Deadline — предупреждение, не запрет.
- **Task Group и маски:** пока упрощённые поля, но по объёму похожие на настоящие, чтобы раскладку панели не пришлось переделывать. Группа — выпадающий список с разделом группы (название, ключ, адрес шаблона, список её Task), маски — список из нескольких строк. Полноценный UI делают [#190](https://github.com/dsc-sgu/mm-frontend/issues/190) и [#191](https://github.com/dsc-sgu/mm-frontend/issues/191).
- **Создание Task:** только вставкой Task Reference в редакторе Course Page, после чего сразу открывается панель новой Task. Удаление Task Reference до открытия удаляет Task; после открытия Task Reference можно только перемещать.
- **«Создать ещё» переносит**, оставляя видимым и редактируемым: Task Group, максимальную Grade, Deadline уровня Task, Task Opening Time.
- **Очищается:** название, условие, вложения, аннотация; Task Key предлагается заново. Маски и переопределения не переносятся.
- **В панели нет:** максимума Attempts, вариантов, командных Task.
- **Одна панель везде:** из просмотра Course, из режима редактирования и со страницы Task.

## Устройство

- **Курс.** «Современные информационные технологии», вход под `mit-teacher`.
- **Маршруты.**
  - A и D — `/courses/$courseSlug/deadlines`;
  - B — `/courses/$courseSlug/tasks`;
  - C — `/courses/$courseSlug/edit?variant=C`.
  - Боковая панель — на существующем `/courses/$courseSlug` с `?variant`.

  Новые маршруты открываются только с `?variant`. Плавающая панель переключает варианты, переходя между маршрутами.
- **Fixture в памяти, после перезагрузки возвращается к исходному состоянию.**
  - 4 Student Groups: 151-1пп, 151-2пп, 111-1пп, 111-2пп; около 48 Students с реалистичными ФИО.
  - Около 14 Task, одна без срока. Они разложены по 2–3 Task Groups, у каждой свой Task Group Key.
  - Для сценариев применения: второй Teacher и его Course Editing Lease, свой неопубликованный черновик с правками страницы, устаревший черновик.
  - Групповые переопределения на нескольких Task.
  - 6–8 личных переопределений с причинами; среди них одно строже группового и одно «без срока».
  - Несколько Attempts для предупреждений о смене опоздания.
  - Везде подпись часового пояса.
- **Порядок Task.**
  - Внутри Task Group порядок задан явно; хотя бы у одной пары Task он расходится с порядком Course Page.
  - Списки сроков идут по группам, в порядке выполнения.
- **Не делаем:** предпросмотр «глазами Student»; тесты (тесты пишутся при реализации по спецификации).
- **Ветка** `prototype/task-and-deadline-settings`.

### 2026-10-24T19:38:29Z · t3m8ch

В `prototype/sandbox` добавлен режим `taskApply: blocks` (коммит `e863f5d`). Он моделирует бэкенд из [mm-backend PR #187 «Frontend API alignment»](https://github.com/dsc-sgu/mm-backend/pull/187), ветка `nrydanov/frontend-api-alignment`. В этой модели нет брони редактирования курса, `heartbeat` и черновика курса целиком: черновик заводится на каждый изменённый блок.

Что показывает режим:
- **Черновики блоков.** Изменённый, перемещённый, новый или удалённый блок становится черновиком автора поверх опубликованной версии. В редакторе такой блок отмечен чертой и плашкой, над документом полоса «Мои черновики блоков: N». Черновики видит только автор, и они переживают уход из редактора.
- **«Применить»** — это `POST /courses/{id}/publish`. Каждый черновик сливается с тем, что опубликовали после его базы. Если с обеих сторон менялись данные блока или удаление пришлось на правку, приходит `409` со списком блоков, и не публикуется ничего.
- **Конфликт** виден в той же полосе и на самом блоке. Варианты: «Взять его версию» или «Оставить мою поверх». Для удаления свои варианты в обе стороны. Чужие правки других блоков сливаются молча.
- **Правка задания из панели** — это `PATCH /tasks/{id}`, настройки задания лежат в данных его блока. Если блок задания уже в моём черновике, правка ложится туда же и публикуется вместе с черновиком («В черновик»). Иначе она публикуется сразу, как в D.
- **Новое задание** и проверки перед «Применить» — как в `contract`.
- **Сценарии в песочнице.** 3 — «У меня черновики блоков». 8 — коллега публикует свои черновики раньше. Сценарии 4 и 6 в этом режиме скрыты.

Как посмотреть: `C` с `taskApply: blocks`, сценарии 3 и 8, панель «Docker-образ приложения», затем «Применить». Подробно — раздел «Черновики блоков» в README прототипа.

Открытые вопросы:
- Что считать отдельным блоком. Бэкенд хранит блоки плоско, а вложенное в спойлер оказывается данными родителя.
- Решения конфликта на `14a6abb` пока не выразить через API, это вопрос к бэкенду:
  - «Взять его версию»: нет запроса, который отбрасывает черновик одного блока, `cancel-edit` удаляет все черновики автора;
  - «Оставить мою поверх»: `PATCH` с версией опубликованного блока при своём черновике отвечает `409`, а правка черновика оставляет ему старую базу, так что следующая публикация снова конфликтует;
  - значит, сейчас после конфликта остаётся только отменить все свои черновики.
- Бэкенд сравнивает данные блока целиком, а настройки задания — одни данные его блока. Два преподавателя, поменявшие у одного задания разные поля, получат конфликт, а не слияние.
- В данных блока задания есть только `availableAt` и `deadlineAt`: переопределений дедлайнов нет, а расписание публикуется вместе с блоком. По решению mm-180 расписание применяется отдельно от публикации. Прототип так и делает: в черновик попадает только расписание нового задания.
- Правка задания может уйти в черновик курса. Это отступление от контракта mm-129, где правка опубликованного задания — отдельная публикация.

Вердикта по режиму ещё нет.
