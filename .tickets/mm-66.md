# Исследовать тестовые практики для текущего frontend-стека

## Question

Какие официально поддерживаемые инструменты и практики подходят для тестирования текущего стека React 19, Vite, TypeScript, TanStack Router/Query, Zustand, Plate и сложных browser interactions? Исследование должно опираться на первичные источники, отделить обязательные ограничения версий от вариантов выбора и не принимать за владельца проекта итоговое решение о стеке.

### 2026-08-24T16:04:58Z · t3m8ch

Исследование завершено: [документ с выводами и первичными источниками](https://github.com/dsc-sgu/mm-frontend/blob/research/frontend-test-practices/docs/research/frontend-test-practices.md).

Краткий ответ: для текущей системы нужен не один универсальный runner, а слоистая поверхность — быстрые model/contract tests, DOM component integration, узкие real-browser проверки для Plate/contenteditable и тонкий E2E-слой. Официально поддерживаемый shortlist включает Vitest, jsdom + Testing Library/user-event, MSW после определения transport seam и Playwright/Vitest Browser Mode для browser-зависимых контрактов. Финальный выбор оставлен тикету стратегии.

Артефакт находится в ветке [research/frontend-test-practices](https://github.com/dsc-sgu/mm-frontend/tree/research/frontend-test-practices), commit [908f2d0](https://github.com/dsc-sgu/mm-frontend/commit/908f2d0ae5305e33642171b037fd3b446318c25b).

### 2026-08-24T19:53:27Z · t3m8ch

Владелец проекта просмотрел research-артефакт; [ответы даны прямо в комментариях к commit](https://github.com/dsc-sgu/mm-frontend/commit/908f2d0ae5305e33642171b037fd3b446318c25b).

Контекст для последующего решения [Выбрать слоистую стратегию тестирования](https://github.com/dsc-sgu/mm-frontend/issues/68):

- приоритет — прочные behavioral tests через устойчивые seams; меньше white-box unit tests, больше feature/component integration и Playwright для критических путей;
- page-edit использует локальный Zustand store factory, поэтому тесты должны получать свежий store; глобальный reset нужен только для singleton/mock stores;
- текущие redirects при ошибках стоит точечно фиксировать как наблюдаемое characterization-поведение, меняя тест вместе с будущим продуктовым решением;
- целевая browser matrix: Chromium, Firefox и WebKit;
- pixel screenshot assertions не нужны; screenshots допустимы как диагностические artifacts, основной контракт — behavior и доступная семантика;
- RAM-моки — временная замена backend; MSW имеет смысл только после выбора transport/API seam, потенциально как мост от frontend-прототипа к реальному backend;
- CI-бюджет пока не фиксируется: быстрые и долгие suites можно развести, а режим запуска выбрать по фактическим duration/flaky-rate;
- отдельно создан ticket [Разобрать низкоуровневые browser- и scheduling-механизмы](https://github.com/dsc-sgu/mm-frontend/issues/72) для `queueMicrotask` и похожих workaround.

### 2026-08-24T20:07:51Z · t3m8ch

Дополнительные решения владельца после повторного review [research-артефакта](https://github.com/dsc-sgu/mm-frontend/commit/908f2d0ae5305e33642171b037fd3b446318c25b):

- миграция RAM-моков исключена из текущей planning-карты и вынесена в отдельный execution ticket [Перевести frontend с RAM-моков на fetch и MSW](https://github.com/dsc-sgu/mm-frontend/issues/73);
- текущие mock-данные одноразовые, production deployment отсутствует — обратную совместимость старых Plate/mock schemas и migrations сейчас гарантировать не нужно;
- внутренние generated IDs не являются видимым пользовательским контрактом: тестировать нужно их свойства и связи, а не конкретные значения;
- корректная последовательная нумерация списков редактора признана обязательным регрессионным контрактом; спецификация вынесена в [Зафиксировать контракт нумерации списков редактора](https://github.com/dsc-sgu/mm-frontend/issues/74).
