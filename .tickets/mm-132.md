# Спроектировать смену пишущей вкладки редактора

## Question

Как вкладки одного браузера делят Review editor и Course Page editor, чтобы смена пишущей вкладки не теряла и молча не перезаписывала Working Copy (I5, I6 из mm-64 «Выбрать критические пользовательские пути и гарантии»)?

Владелец уже решил в mm-120 «Спроектировать матрицу тестовых контрактов критических вертикалей» (Q14):

- пишет одна вкладка, остальные показывают лайв-копию Working Copy только для чтения;
- «Продолжить здесь» меняет пишущую вкладку локально, Working Copy переходит без обращения к серверу;
- смена бывает добровольной (пишущая вкладка отвечает и отдаёт Working Copy) и силовой (пишущая вкладка молчит дольше таймаута, новая продолжает от последней лайв-копии);
- lease привязан к браузеру — auth session, как Course lease на [`mm-backend@ddd9849`](https://github.com/dsc-sgu/mm-backend/blob/ddd98496d1293a3cf9844201e70376b3364fdcc3/internal/pg/courses_locks.go); клиентского `leaseId` нет;
- единственность пишущей вкладки обеспечивают Web Lock и счётчик смен в localStorage: каждая смена его увеличивает, пишущая вкладка синхронно сверяет свой номер перед каждой записью;
- от backend нужна проверка revision черновика при записи: запрос, ушедший из замороженной вкладки до силовой смены, иначе может молча перезаписать новые правки (mm-113 «Реестр frontend-вопросов к backend API»).

Нужно спроектировать протокол и состояния вкладки:

- что считается спокойным состоянием для добровольной смены: пакет синхронизации Course Page в полёте, загрузка картинки, публикация Review и `publication-unconfirmed`;
- таймаут силовой смены и что видит Teacher, пока он идёт;
- закрытие или выгрузка пишущей вкладки: копия становится пишущей сама или предлагает «Продолжить здесь»;
- версия протокола сообщений и несовпадение версий приложения во вкладках;
- привязка канала и lock к `UserId` и ресурсу (Attempt, Course); выход из аккаунта и вход другим User в соседней вкладке;
- как лайв-копия получает обновления: полная Working Copy или изменения, частота, обнаружение пропусков;
- как UI отличает свою вкладку этого браузера от своей другой сессии (другое устройство или приватное окно: `423` с holder — сам User), перехват lease из другой сессии и его сочетание с `interrupted` (вопросы Q12 и Q13 матрицы);
- что теряется при смене: история undo, selection, scroll;
- BroadcastChannel, Web Locks, freeze и bfcache во всех трёх движках.

Решение уточняет mm-116 «Спроектировать Review → Grade → Student result vertical» и mm-118 «Спроектировать lifecycle Course Page Working Copy»: там вторая вкладка открывается только для чтения и перехватывает lease по клиентскому `leaseId`.

## Решение: одна пишущая вкладка на браузер, смена без сервера

Протокол собран как throwaway-прототип и проверен в нём. Прототип — одна HTML-страница: браузер (localStorage, Web Lock, BroadcastChannel, заморозка) и сервер смоделированы в памяти, есть двенадцать сценариев по TAB-01…TAB-09, REV-E5 и DRF-E3. Решения владельца приняты по ходу разбора прототипа. Production/source code и тесты не изменялись.

- Ветка: [`prototype/editor-tab-handoff`](https://github.com/dsc-sgu/mm-frontend/tree/prototype/editor-tab-handoff), файл [`docs/prototypes/editor-tab-handoff.html`](https://github.com/dsc-sgu/mm-frontend/blob/fc7fb23c7669f1990ecfa94a9686b6ed67d56c1f/docs/prototypes/editor-tab-handoff.html) на `fc7fb23`. Открывается в браузере без сборки. Переносимая логика — в первом блоке `<script>`.
- Glossary и ADR — в PR [«docs: record editor tab handoff glossary and ADR»](https://github.com/dsc-sgu/mm-frontend/pull/134):
  - оба lease принадлежат одной sign-in session, её делят все вкладки браузера;
  - ADR 0004 «Lease принадлежит браузеру, вкладки делят редактор локально»;
  - уточнение в ADR 0002.

### Модель

Lease (Review и Course) принадлежит auth session, клиентского `leaseId` нет — это решение из mm-120 «Спроектировать матрицу тестовых контрактов критических вертикалей». Вкладки одного браузера координируются через три механизма. Имя каждого — `mm:editor:{UserId}:{review|course}:{AttemptId|CourseId}`.

- **Запись `{epoch, writer}` в localStorage** определяет, какая вкладка пишет. Каждая смена увеличивает `epoch` (счётчик смен). Перед каждой записью на сервер, в том числе перед heartbeat, вкладка синхронно сверяет свой номер и `UserId` сессии.
- **Web Lock** выбирает следующую пишущую вкладку и сообщает, что прежняя закрылась. Копии стоят в очереди за ним. Пишущая вкладка держит lock. Браузер освобождает lock вместе с документом — и при закрытии, и при падении.
- **BroadcastChannel** доставляет живую копию и сообщения смены.

Роли вкладки: `writer`, `copy` (живая копия), `joining`, `no-copy` (нет живой копии, пишущая молчит), `incompatible` (другая версия протокола), `signed-out`, `other-user`. Переходы — чистые функции. Главные из них:

- `writeGuard(record, auth, tab)`;
- `quietBlockers(resource, wc)`;
- `hasUnsavedWork(resource, wc)`;
- `isNewerState(seen, wc, msg)`;
- `adoptOrphanedWorkingCopy(resource, wc)`.

### Решения

1. **Спокойное состояние для добровольной смены.**
   - Пишущая вкладка отвечает на «Продолжить здесь» сразу и перестаёт принимать правки.
   - Она дожидается только запросов, исход которых меняет Working Copy: пакета синхронизации Course Page, публикации или удаления черновика, публикации Review.
   - `pending` и `sync-failed` передаются как есть, без досылки.
   - Неподтверждённая публикация Review (`publication-unconfirmed`) передаётся вместе с `idempotencyKey` и замороженной Working Copy, повторы продолжает новая вкладка. Ключ и Working Copy всегда находятся в одной вкладке (TAB-04).
   - Если исход пакета Course Page неизвестен, новая вкладка перечитывает черновик (mm-118).
   - Загрузки картинок в реализованном редакторе нет. Будущая загрузка станет ещё одной причиной в `quietBlockers`, а её UX решается вместе с самой загрузкой, вне карты.
2. **Силовая смена.**
   - Если пишущая вкладка молчит 3 с, копия продолжает сама, без второго нажатия.
   - Если вкладка ответила `handoff-accepted` и ждёт свой запрос, срок — таймаут запроса плюс 3 с.
   - Продолжить силой может только вкладка с живой копией. Вкладка, открытая уже при замороженной пишущей, показывает «Редактор открыт в другой вкладке, она не отвечает — перейдите в неё». Иначе Review Working Copy, которая есть только в замороженной вкладке, пропала бы молча.
   - Порядок: сначала счётчик в localStorage, потом `steal` lock'а.
   - Если перед заморозкой был отправлен пакет, новая вкладка перечитывает черновик.
   - Проснувшаяся бывшая пишущая вкладка сверяет счётчик раньше, чем узнаёт о потере lock. Её просроченный таймер автосохранения ничего не отправляет (TAB-03).
3. **Закрытие или уход пишущей вкладки.**
   - Lock переходит к первой копии в очереди, она продолжает сама и показывает «Вкладка N закрыта — редактирование продолжено здесь».
   - Предупреждение об уходе нужно, только если совместимой живой копии нет.
   - Lease снимается, когда уходит последняя вкладка редактора этого ресурса.
   - Почему не «копии предлагают «Продолжить здесь»»: пока Teacher не выбрал, heartbeat никто не шлёт (TTL 60 с), а правки лежат в памяти копий без защиты от ухода.
   - Пишущая вкладка при добровольной смене держит lock, пока получатель его не заберёт `steal`. Так в эту паузу не вклинится третья вкладка. Если получатель не забрал lock за 1 с, роль возвращается.
4. **Версии.**
   - Одно целое `TAB_PROTOCOL_VERSION` покрывает формат сообщений и Working Copy. Конверт `{kind, from, version, epoch}` не меняется никогда.
   - При несовпадении версий нет ни живой копии, ни смены: «Редактор открыт во вкладке с другой версией MergeMinds — закончите работу там и закройте её».
   - Старая вкладка предупреждает об уходе: совместимой копии нет.
   - Когда старая вкладка закроется, новая продолжит с сервера (TAB-05).
5. **User и выход из аккаунта.**
   - Cookie сессии общий для всех вкладок, поэтому выход в любой вкладке останавливает запись во всех.
   - Содержимое скрыто экраном «Вы вышли из аккаунта». Working Copy держится в памяти, закрытие вкладки предупреждает.
   - Вход тем же User продолжает работу. Lease прежней сессии берётся перехватом тем же User.
   - Вход другим User удаляет Working Copy прежнего. Вкладка другого User живёт в своём канале и чужих правок не видит (TAB-06).
6. **Живая копия.**
   - После каждого изменения уходит полная Working Copy, в той же задаче, что и изменение. Вместе с ней — статусы синхронизации, публикации и holder lease.
   - Изменения внутри одной задачи сливаются. Новая копия заменяет старую по `(epoch, seq)`, пропуски обнаруживать не нужно.
   - Вкладка, которая открылась, спрашивает состояние сообщением `hello`.
   - Следствие: замороженной пишущей вкладке нечего досылать, и силовая смена не теряет правок, сделанных в браузере.
   - На поблочные изменения переходим, только если замер покажет, что structured clone на каждое нажатие дорог.
7. **Своя вкладка, своя сессия, чужой Teacher (Q12/Q13 из mm-120).**
   - Свою вкладку этого браузера видно локально, без сервера: «Редактирование идёт во вкладке N этого браузера · Продолжить здесь».
   - `423` с holder — самим User — всегда означает другую сессию: «Открыт в другой сессии — на другом устройстве или в другом окне · Вернуть сюда», то есть перехват тем же User.
   - Чужой holder: «Редактирует Борис · Попробовать снова».
   - `interrupted` видят все вкладки браузера, потому что lease общий. Действовать можно из любой вкладки через «Продолжить здесь» (TAB-09).
8. **Что переходит при смене.**
   - Переходят Working Copy целиком и черновики полей ввода: root comment, ещё не добавленный в Working Copy, и reply.
   - Теряются история undo, выделение и курсор, scroll, открытые меню.
   - Первое нажатие в проснувшейся бывшей пишущей вкладке не применяется.
9. **bfcache и движки.**
   - `pagehide` означает уход: lock и канал отпускаются, копия продолжает.
   - При `pageshow` с `persisted` вкладка продолжает со своей Working Copy, только если запись о пишущей вкладке с тех пор не менялась. Иначе она выбрасывает её и подключается заново.
   - Поэтому протокол не зависит от того, как движок обращается с Web Locks и BroadcastChannel в bfcache.

### Факты о движках

- **[Web Locks](https://w3c.github.io/web-locks/).**
  - Один lock manager на storage bucket, общий для вкладок и workers origin.
  - Запросы выдаются по очереди FIFO. `ifAvailable` не встаёт в очередь.
  - `steal` освобождает удерживаемый lock, вытесняет очередь и отклоняет released promise прежнего держателя с `AbortError`. О самом перехвате прежний держатель не узнаёт.
  - При выгрузке документа его locks и запросы снимаются.
- **[Chrome Energy Saver](https://developer.chrome.com/blog/freezing-on-energy-saver)** не замораживает группу вкладок, которая держит Web Lock, блокирующий операции вне группы. Копии стоят в очереди к lock пишущей вкладки, поэтому по этому правилу Chrome её не заморозит. Остальные причины молчания: зависший главный поток, пауза в отладчике, заморозка в других движках.
- **Не проверено.**
  - Читается ли счётчик в localStorage синхронно и в актуальном значении сразу после разморозки вкладки. Это допущение о движках, его проверяет TAB-08 в Chromium, Firefox и WebKit. Страховка — проверка revision черновика на backend.
  - Заморозка отдельных фоновых вкладок в Firefox и Safari.
  - Блокирует ли удерживаемый Web Lock попадание страницы в bfcache.

### Backend

- **Проверено на [`mm-backend@ddd9849`](https://github.com/dsc-sgu/mm-backend/tree/ddd98496d1293a3cf9844201e70376b3364fdcc3).**
  - Course lease — пара `user_id + session_id` из cookie `SESSION_ID`, TTL `COURSE_LOCK_TTL_SECONDS` по умолчанию 60 с.
  - `423` несёт id User-держателя.
  - Logout не снимает `course_locks`: сессии лежат в Redis, `session_id` не ссылается на них внешним ключом.
  - `Logout` вызывает `sessionRepo.DeleteByID(userID)`, хотя сессии хранятся по ключу из id сессии. Похоже, сессия на сервере не удаляется, и выход только очищает cookie.
- **Рабочие допущения до ответа backend** — в mm-113 «Реестр frontend-вопросов к backend API»:
  - Перехват lease тем же User — для другой сессии и для повторного входа после выхода. Если перехвата не будет, повторный вход ждёт TTL прежней сессии, а «Вернуть сюда» превращается в «Попробовать снова».
  - Проверка revision черновика при записи (TAB-07). Без неё на силовом пути остаётся узкое окно молчаливой перезаписи, которое владелец принял в mm-120.
  - Новое: снимает ли выход из аккаунта lease сессии. Без этого другой Teacher на том же компьютере до 60 с видит «Редактирует Анна».

### Вход для матрицы и следующих тикетов

Строки TAB-01…TAB-09 остаются в силе. Решения добавляют к ним новые контракты-кандидаты, все уровня Stateful с fixture `tabs`:

- вкладка без живой копии не продолжает силой и становится копией, когда пишущая вкладка оживает;
- закрытие пишущей вкладки при живой копии: копия продолжает сама, предупреждения нет; без совместимой копии — предупреждение;
- выход из аккаунта скрывает и держит Working Copy; повторный вход тем же User продолжает, вход другим User удаляет Working Copy;
- возврат из bfcache продолжает со своей Working Copy, только если запись не менялась.

Решение уточняет:

- mm-116 «Спроектировать Review → Grade → Student result vertical»;
- mm-118 «Спроектировать lifecycle Course Page Working Copy».

Комментарии оставлены в обоих. Протокол вкладок становится частью общего lease module уровня course с адаптерами Review и черновика Course (slice 7 из mm-116, slice 4 из mm-118). Место этих slices в общем порядке определит mm-69 «Определить последовательность подготовки и выполнения рефакторинга».
