## Решение: последовательность рефакторинга — DAG этапов вертикалей

Последовательность собирает этапы из резолюций вертикалей в один граф зависимостей. Она опирается на:

- mm-67 «Ранжировать зоны рефакторинга по риску и отдаче»;
- mm-68 «Выбрать слоистую стратегию тестирования»;
- mm-120 «Спроектировать матрицу тестовых контрактов критических вертикалей».

Production/source code и тесты не изменялись.

### Правила

1. **Шаг — один этап.**
   - Один PR, замена за один шаг.
   - Тестовые контракты матрицы, чей уровень-владелец появляется в этапе, пишутся в том же PR.
   - Этап готов, когда проходят lint и build, а все его контракты зелёные в Chromium, Firefox и WebKit.
   - E2E-путь принадлежит этапу, после которого путь впервые проходит целиком.
   - Этап без контрактов матрицы проверяется lint, build и уже существующими тестами.
2. **DAG с параллельными дорожками.** После общей основы проверка, список попыток курса и редактирование курса идут параллельно. Порядок из mm-67 (проверка → список попыток → редактирование курса) решает только споры за людей и за конфликтующие файлы.
3. **Вопросы к бэкенду не блокируют этапы.**
   - Этапы идут против мок-бэкенда с рабочими допущениями из mm-113 «Реестр frontend-вопросов к backend API», помеченными в handlers.
   - Другой ответ бэкенда оформляется отдельным тикетом-исправлением.
   - Старые блокирующие связи на тикеты бэкенда убираются.
4. **Уровень тестирования появляется с первым настоящим потребителем.** PR «только инфраструктура» не бывает.
   - CI на GitHub Actions с lint и build — первый шаг (W0-1).
   - Vitest, RTL и MSW для Node — в K.
   - Playwright в трёх движках — в CH.
   - fast-check — в DOC1.
   - Каждый такой PR сразу добавляет свой job в CI.
5. **Обновления версий ставятся прямо перед этапом, чей код они задевают.**
   - TipTap, Axios и Immutable не обновляются: их удаляют.
   - Крупные обновления инструментов — в backlog mm-136 «Обновить крупные версии инструментов: ESLint, Vite, TypeScript, Globals, Lucide».
6. **Правило зон для продуктового backlog.** Продуктовый тикет, задевающий зону вертикали, берётся только после её этапов или переформулируется на новые швы. Тикеты в незатронутых зонах свободны.
7. **Передача.** Тикеты реализации создаются отдельным шагом после закрытия карты.
   - Epic на каждую группу: Основа, доступ к курсу, проверка, список попыток курса, редактирование курса, Хвост.
   - Этапы — sub-issues с нативной блокировкой по таблице ниже.
   - Тикет этапа берёт описание «Делает / Удаляет» из резолюции своей вертикали.
   - Контракты тикета — фильтр по этапу в матрице.
   - Уточнения из комментариев закрытых старых тикетов (см. ниже) переносятся в тикет этапа.

#### Почему так

- **Дорожка документа стартует сразу после Wave 0.** Характеризационные тесты должны зафиксировать текущий редактор раньше, чем его тронет кто-либо, включая обновление Plate. От DOC1 зависят REV4 и через READ — DRF2.
- **Доступ к курсу — три PR.**
  - Каждый оставляет единственный путь доступа.
  - ACC3 нельзя раздать по вертикалям: до их прихода кеш потерянного курса оставался бы видимым в непереведённых семействах (I2).
  - ACC2 поглощает переименование в `attemptNumber`.
- **Общий модуль брони рождается в REV7.**
  - DRF4 ждёт REV7, чтобы приоритетная дорожка не зависела от самой низкоприоритетной.
  - Простоя нет: у редактирования курса на это время есть DOC2–DOC5.
  - Между DRF2 и DRF4 бронь общая на все вкладки браузера. Две вкладки редактора страницы курса в одном браузере могут перезаписать правки друг друга. Риск такой же, как в текущем коде.
- **ATT1 ждёт REV2.** Иначе REV2 и ATT1 дважды проектируют проверки в состоянии мок-бэкенда.
- **UI из mm-121 разложен по этапам.** Закреплённый top bar — в ATT2, раскладки строки — в ATT4, поле общего отзыва, клавиши и диалог Esc — в ATT6. Так боковая панель и старая строка не переписываются дважды.
- **Механизмы из mm-72 без своей вертикали:**
  - keyboard — KB;
  - clipboard — DOC3;
  - кеш Shiki — V-PIERRE;
  - Reduce Motion — MOTION;
  - лимиты Worker pool — не этап, их подтверждают замером после REV3.
- **Вид страницы задания для преподавателя** и другие остатки RAM-моков подхватывает FINAL: список исключений ESLint показывает их явно.

Самая длинная цепочка по числу этапов — 14:

```
W0-1 → V-VAL → K → ACC1 → ACC2 → ACC3 → REV1 → REV2 → ATT1 → ATT2 → ATT3 → ATT4 → ATT5 → ATT6
```

Цепочка до DRF4 через REV7 — 13.

### 2026-10-14T06:47:35Z · t3m8ch

## Уточнение критериев готовности REV2: удалить временный адаптер «идентичность → локатор»

Зафиксировано при обсуждении PR #214 / ACC2.2 (mm-172).

В `src/features/course/features/attempt-review/api/mock.ts` временные `LegacyParams` и `resolveLegacyParams()` переводят уже разрешённые `CourseId + UserId + AttemptId` обратно в `courseSlug + taskId + studentUsername + attemptNumber` для прежнего in-memory источника попыток и проверок. Этот обратный переход не является целевой архитектурой.

**При создании тикета реализации REV2 перенести следующие пункты в его критерии готовности:**

- [ ] Операции чтения попыток и проверок используют стабильные идентичности и единое каноническое состояние попыток и проверок в мок-бэкенде; не обращаются к прежнему stateful RAM-источнику через локаторы маршрута.
- [ ] Удалены `LegacyParams` и `resolveLegacyParams()` из `attempt-review/api/mock.ts`, включая их эквивалент под другим именем. Нет fallback, восстанавливающего slug, username или номер попытки ради обращения к прежнему источнику содержимого.
- [ ] Временные реализации операций записи, перевод которых на HTTP принадлежит последующим этапам REV5/REV6, не удерживают этот адаптер: при необходимости они адресуют каноническое состояние прямо по стабильным ID. Этот критерий не переносит в REV2 сам перевод операций записи на HTTP.
- [ ] Нет второго независимого stateful источника попыток и проверок, поддерживаемого ради совместимости с прежней адресацией. Генераторы детерминированных фикстур могут оставаться — они не должны становиться альтернативным источником серверного состояния.

**Что остаётся:** разрешение локаторов маршрута `CourseId + Task + Username + AttemptNumber → AttemptId / UserId` на входе в маршрут — штатная часть ACC2. Отображение username и номера попытки, а также построение ссылок тоже остаются. Удаляется только обратная конверсия стабильных идентичностей в локаторы ради старого мок-источника.
