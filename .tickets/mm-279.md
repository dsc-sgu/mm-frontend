# Страница настроек и SSH-ключи для сдачи через git push

## Проблема

Попытки сдаются через `git push` по SSH. Сервер узнаёт студента по отпечатку SSH-ключа. Во фронтенде добавить ключ негде: пункт «Настройки» в меню пользователя (`src/app/header/ui/header.tsx`) вызывает `console.log('settings')`. Без ключа студент не может сдать ни одной попытки через git, и преподаватель не может работать с шаблоном, если шаблон наполняется через push.

Бэкенд (mm-backend PR #187, `internal/auth/sshkeys`): `POST /auth/ssh-keys` добавляет ключ, `DELETE /auth/ssh-keys/{fingerprint}` удаляет. На `main` то же самое лежит под `/git/add_key` и `/git/delete_key`. Получить список своих ключей бэкенд не позволяет.

## Что делает

Вертикаль: маршрут, операции на Fetch, MSW-handlers, тесты.

- Пункт «Настройки» открывает страницу настроек `/settings` с разделами. Первый раздел — «SSH-ключи». Сюда же позже встанет профиль (mm-4).
- Раздел «SSH-ключи»: список ключей (название, отпечаток, дата добавления), добавление ключа (название и текст публичного ключа), удаление с подтверждением.
- Неверный формат ключа и ключ, уже привязанный к другому пользователю, показываются у поля.
- Короткая подсказка: как создать ключ (`ssh-keygen -t ed25519`) и где взять публичную часть. Ссылка на страницу, где видны адрес репозитория и команда сдачи (mm-187).

## Что решить

- Список ключей: попросить у бэкенда `GET /auth/ssh-keys`. Внести в mm-113. До ответа MSW отдаёт список как рабочее допущение.
- Что возвращает добавление: сейчас пустое тело, без отпечатка.
- Ключ, который уже есть у другого пользователя: как бэкенд об этом сообщает.

## Интеграционные предпосылки и образцы

Блокеров на рефакторинг нет: новая вертикаль настроек и SSH-ключей может сразу вводить целевой HTTP-контракт, не копируя старый API и не ожидая перевода курсового редактора. mm-4 использует тот же /settings: сделать общий контейнер разделов и не создавать конкурирующие маршруты. mm-187 нужен для конечной ссылки на репозиторий, но проектирование всей страницы репозитория не должно задерживать добавление/удаление ключей; связанный переход включать лишь когда он действительно ведёт на реализованный сценарий.

Проверенные образцы origin/main: `src/features/auth/api/login.ts` и `src/app/remote-data/http.ts` — удалённая операция с явными исходами; `src/features/auth/api/mock.ts` и `src/app/mock-backend/state.ts` — MSW и данные текущего пользователя; `src/features/auth/ui/registration-form.tsx` — связка React Hook Form/Valibot; `src/features/auth/model/identity.ts` — стабильный UserId. В самой фиче определить чтение списка ключей, добавление с данными созданного ключа и удаление, схемы DTO, объявленные ошибки формата/чужого ключа и тесты доступа. Авторизация — по серверной сессии, а не по userId из формы.

Не хранить рабочий список ключей в отдельном RAM-моке компонента или localStorage. Не сохранять private key; форма принимает публичный ключ. Не копировать userID/avatarURL и ручной маппинг из старого check-session.ts. Чужие данные не должны оставаться видимыми при смене сессии: семейство ключей ограничить UserId и подключить отмену/очистку через политику владельца, не расширяя список чужих ключей внутри auth (направление mm-293). Готовой операции SSH-ключей в origin/main пока нет; frontend-first контракт создаётся этим тикетом.

Проверено по `origin/main` (`045ea6d`). Наличие решения в спецификации или рабочей ветке не означает, что его реализация уже доступна в `main`. Перед реализацией перечитать `docs/agents/remote-data.md` и проверить актуальность указанных путей.
