# Зафиксировать канонический доменный язык и состояния

## Question

Какие термины, идентичности, роли, права, инварианты и lifecycle-состояния канонически описывают реализованные course, task, attempt, review, grade, feedback/comment и content-editing потоки? Нужно разрешить обнаруженные неоднозначности кода, не проектируя ещё не реализованный продукт.

### 2026-09-11T12:40:36Z · t3m8ch

## Решение: канонический язык и состояния реализованного ядра

Решение отделяет фактическое ядро frontend от подтверждённых ограничений будущего Task Group UI. Оно не принимает transport/API schema и не проектирует ещё не реализованные экраны.

### Identity

- **User** имеет immutable internal ID. `username` — mutable public locator, а не identity.
- **Course** имеет immutable internal ID. `courseSlug` — mutable route locator. Текущий `courseId`, фактически используемый как slug, не является каноническим именем identity.
- **Task** — канонический термин. Это совпадает с backend (`tasks`, `task_id`, `block_type='task'`, `RepoID.TaskID`). `Assignment` не является второй доменной сущностью; на Course Page это только ссылочный content block на Task.
- **Task ID** стабилен. Текущий `Task.number` не является identity. Реальный execution position относится к Task Group и не выводится из визуального положения блока на Course Page.
- **Attempt** имеет immutable internal ID и отдельный `attemptNumber`. Номер монотонен в контексте Course + Task + Student и не является глобальной identity.

### Roles, membership и access

- Авторизация внутри Course определяется наличием **Course Membership** и её единственной course-local ролью `student | teacher`.
- Один User может быть Student в одном Course и Teacher в другом. Глобальный `session.role` не является источником course permissions.
- Student видит только собственные Attempts и опубликованные Reviews. Любой Teacher этого Course видит Attempts и Reviews всех Students.
- Teacher редактирует Course, создаёт/изменяет Review и создаёт корневые line comments. Student может отвечать в обсуждении собственной Review. Каждый автор редактирует и удаляет только собственные messages.
- Course имеет отдельный access lifecycle `draft → open`. `open → draft` допустим только пока нет ни одного Student membership; после присоединения первого Student возврат запрещён. Это access state, не состояние Course Snapshot.

### Course Page и content editing

- **Course Page** — визуально упорядоченный документ. Положение ссылки на Task в документе не определяет порядок выполнения Tasks.
- **Course Snapshot** — immutable опубликованная версия конфигурации Course. Student видит active published snapshot. Attempts, Grades, student progress и access facts в snapshot не входят, но могут ссылаться на него.
- **Course Draft Snapshot** — unpublished server snapshot, который готовят Teachers. Публикация создаёт immutable snapshot; последующие изменения идут в следующем draft.
- **Course Page Working Copy** — локальная редактируемая копия draft. Каноническое различие: synchronized vs unsynchronized local changes. Working Copy не является server source of truth.
- Уже согласованные server editing states `new | restored | stale_conflict`, lease loss и snapshot conflicts остаются частью snapshot integration, а не новой параллельной моделью этого ticket.
- Точные границы metadata/deadlines/task-only apply и пользовательские формулировки «сохранить / применить / опубликовать» остаются в связанных snapshot decisions; текущие mock labels не канонизируются здесь.

### Task Group и progression boundary

- **Student Group** — академическая группа участников. **Task Group** — отдельное понятие: линейная последовательность Tasks и один repository на Student; разные Task Groups могут выполняться параллельно.
- После explicit открытия Course студентам execution order и `maxGrade` фиксируются. Визуальная перестановка блоков Course Page их не меняет.
- Для locked Task Student видит summary и конкретный prerequisite, но не содержимое и не может отправить Attempt.
- Task Group/progression пока не реализованы во frontend, но должны проявиться в будущем UI настройки. Поэтому это extension constraint, а не заявление о текущем пользовательском поведении.
- Критерий завершения prerequisite намеренно не выбран за команду. Варианты submission / published Review / grade threshold / explicit Teacher approval вынесены в mm-110 «Согласовать критерий завершения задания и открытия следующего», дочерний ticket спецификации mm-100 «Спецификация: сократить путь преподавателя от курса к проверке попыток».

### Attempt lifecycle

- Attempt — immutable snapshot конкретной сдачи и применимого published Course context. Повторная сдача создаёт следующий Attempt; существующий не перезаписывается.
- Канонические состояния реализованного ядра: `submitted` без Review и `graded` с Review. Review меняется отдельно и не нарушает immutable Attempt.
- Предыдущие Attempts остаются addressable после новых сдач. Review текущей Attempt сравнивает её с явно выбранной baseline, а не с mutable repository HEAD.

### Review, Grade и feedback

- **Review** — опубликованный результат проверки одной Attempt. У Attempt не больше одной Review.
- Первая Review появляется атомарно вместе с обязательной **Grade**; Grade, Overall Feedback и teacher Line Comments становятся видимы Student одновременно. Persisted ReviewDraft сейчас не канонизируется; до save во frontend существует только local Review Working Copy.
- Review mutable: любой Course Teacher с exclusive Review Lease может изменить Grade и Overall Feedback. Review не закрепляется навсегда за создавшим её Teacher.
- **Review Lease** — временное exclusive право редактирования, не reviewer assignment. Остальные Teachers в это время читают Review.
- Quick grading создаёт или обновляет ту же Review. Она не захватывает lease, но backend должен атомарно отклонить конкретный grade mutation, если в момент записи действует чужой lease; UI pre-check сам по себе не является concurrency guarantee.
- **Grade** — numeric value, не отдельный Score object. Backend сегодня содержит только `tasks.max_grade` и `attempt_state='graded'`, поэтому полного backend result model пока нет. Канонические ограничения: `0 ≤ Grade ≤ Task.maxGrade`; существующую Grade нельзя очистить обратно в unreviewed; `maxGrade` фиксируется при открытии Course студентам.
- **Overall Feedback** — optional общий текст Review.
- **Line Comment Thread** — привязанное к строке или диапазону обсуждение: Teacher создаёт root comment, допустимые участники отвечают, каждый author управляет только своими messages.
- **Review Read State** — per-Student marker `unread | read`, а не lifecycle Attempt. Изменение Grade, Overall Feedback или teacher line comment создаёт новую видимую revision и снова делает Review unread; собственный reply Student не делает её unread для него самого.

### Разрешённые неоднозначности текущего кода

- `courseId` vs `courseSlug`: stable identity и mutable locator разделены.
- `username` vs User identity: stable ID и mutable locator разделены.
- `attemptId` vs `attemptNumber`: internal identity и course-local sequence number разделены.
- `Task` vs `Assignment`: доменная сущность одна — Task.
- global auth role vs course role: права даёт Course Membership.
- `Review` больше не означает одновременно страницу, режим редактирования и текстовый отзыв.
- `TaskAttemptAttention` уточняется до Review Read State.

Канонический glossary также записан в `CONTEXT.md`. Production/source code и тесты не изменялись.

### Уточнение границы после ответа команды

Команда подтвердила, что выбор стратегии открытия следующего Task сейчас не приоритетен: сначала нужно связать уже реализованный базовый frontend с backend. Поэтому mm-110 «Согласовать критерий завершения задания и открытия следующего» закрыт как `not planned` для текущего frontier.

Это уточняет, а не меняет каноническую модель выше: Task Group и линейный progression остаются подтверждёнными будущими concepts, но completion rule не входит в модель реализованного ядра и не блокирует это решение.
