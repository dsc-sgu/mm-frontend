# User hover card component

## Что это такое?

Карточка пользователя, отображаемая при наведении курсора на ссылку, ведущую на профиль пользователя. Например, при наведении на ФИО преподавателя.

Карточка содержит:

* аватар пользователя;
* ФИО;
* username;
* краткое описание;
* контактные данные, которые пользователь указал и которые доступны текущему пользователю;
* кнопку для перехода к диалогу с пользователем.

## Зачем это нужно?

Компонент нужен для улучшения UX.

Например, если студент хочет написать преподавателю, без такой карточки ему нужно:

1. перейти на страницу профиля преподавателя;
2. найти кнопку “написать сообщение”;
3. открыть чат.

С hover card это действие можно сократить до одного клика: студент наводит курсор на имя преподавателя и сразу нажимает кнопку для отправки сообщения.

## Как это реализовать?

### Как упаковать в виде сущностей React?

Я бы реализовал простой вариант с обёрткой для ссылки:

```tsx
<UserHoverCard user={user}>
  <Link to="...">
    Иванов Иван Иванович
  </Link>
</UserHoverCard>
```

Это кажется одним из самых простых вариантов. Не вижу смысла оверинжинирить что-то сложнее этого.

### В какой момент загружать данные для карточки пользователя.

#### Вариант 1: загружать все данные заранее

Можно загружать всю необходимую информацию сразу в тех местах, где мы получаем список пользователей.

Например, в карточке курса при получении списка преподавателей можно запрашивать не только ФИО и username, но и дополнительные данные для hover card.

##### Плюсы

* Улучшается UX: при наведении пользователю не нужно ждать загрузки данных.
* Не требуется делать дополнительные сетевые запросы с фронтенда: после основного запроса вся нужная информация уже доступна.

##### Минусы

* Основные API-ответы становятся тяжелее: придётся передавать больше данных, даже если пользователь никогда не откроет hover card.
* Одни и те же данные пользователя будут повторно передаваться в разных endpoint’ах, где этот пользователь встречается.
* Данные для карточки начинают размазываться по большому количеству endpoint’ов. Если изменится состав данных hover card, придётся менять много API-ответов.
* Данные карточки потенциально могут зависеть от прав доступа. Например, разные пользователи могут видеть разный набор контактных данных. В таком случае проверку прав доступа придётся корректно реализовывать во всех endpoint’ах, где возвращаются пользователи. Это размазывает authorization-логику и может усложнить backend.
* На первый взгляд может показаться, что такой подход добавляет лишние JOIN’ы, но это не главный аргумент: ФИО и username часто всё равно нужны вместе с ID пользователя, поэтому JOIN’ы в ряде случаев неизбежны.
* Сложность реализации с точки зрения backend/frontend пока неочевидна, утверждать ничего не буду.

#### Вариант 2: загружать данные лениво

Противоположный подход — загружать данные для hover card только при наведении на ссылку пользователя.

В этом случае можно сделать отдельный endpoint, например:

```http
GET /api/users/:id/hover-card
```

или в будущем batch-вариант:

```http
POST /api/users/hover-cards
```

##### Плюсы

* Основные API-ответы не раздуваются.
* Логика получения данных для hover card находится в одном месте.
* Проще централизованно учитывать права доступа.
* Изменение состава данных карточки затрагивает один endpoint, а не множество API-ответов.
* За счёт TanStack Query данные можно кэшировать по `userId`. Поэтому при повторном наведении на ту же ссылку или на другую ссылку того же пользователя повторный запрос не потребуется, пока данные остаются актуальными в кэше.

##### Минусы

* При первом наведении может быть задержка загрузки.
* Может увеличиться количество сетевых запросов, если пользователь быстро открывает много hover card.

Эти минусы можно частично смягчить за счёт:

* кэширования через TanStack Query;
* skeleton-лоадеров внутри карточки;
* batch prefetch в будущем, если это действительно понадобится.

#### Предлагаемое решение

На текущем этапе кажется более правильным выбрать подход с ленивой загрузкой данных для hover card.

Основная причина: он не приводит к размазыванию логики по большому количеству endpoint’ов. Данные карточки пользователя, особенно контактные данные и возможные права доступа, лучше получать через отдельный специализированный API.

Чтобы избежать лишней сложности на старте, batch prefetch пока можно не реализовывать. Это выглядит как преждевременная оптимизация. При этом стоит учитывать, что такая возможность есть, если в будущем появятся проблемы с latency или большим количеством запросов.

Пока backend API для получения подробной информации о пользователе нет, предлагаю:

1. реализовать компонент hover card на фронтенде;
2. замокать API получения данных пользователя;
3. сделать отдельный issue на подключение карточки к настоящему backend API.

### 2026-10-19T23:25:25Z · t3m8ch

Решение о данных пользователя в контрактах (#269): каждый человек в DTO передаётся как `UserRef` — `{ id, username, lastName, firstName, patronymic? }`, та же форма, что `UserSummary` у бэкенда.

Для карточки это значит:

- `<UserHoverCard user={userRef}>` подходит к любому месту, где показан человек: преподаватель курса, опубликовавший версию проверки (#270), автор ответа в треде.
- Текст ссылки — `formatFullName(user)`, адрес — `/@username`.
- Данные карточки (аватар, описание, контакты) списки не несут. Карточка загружает их лениво по `user.id`, как предлагает вариант 2 этого тикета, и кэширует по `id`. Поэтому в карточке username всегда свежий, даже если в списке он уже устарел.
