# Показывать карточку пользователя при наведении на ссылку на профиль

## Что это такое?

Карточка пользователя, которая появляется при наведении курсора на ссылку на профиль пользователя. Например, при наведении на ФИО преподавателя.

Карточка содержит:

* аватар пользователя;
* ФИО;
* username;
* краткое описание;
* контактные данные, которые пользователь указал и которые доступны текущему пользователю;
* кнопку для перехода к диалогу с пользователем.

## Зачем это нужно?

Карточка делает интерфейс удобнее.

Например, если студент хочет написать преподавателю, без такой карточки ему нужно:

1. перейти на страницу профиля преподавателя;
2. найти кнопку «Написать сообщение»;
3. открыть чат.

С карточкой это действие сокращается до одного клика: студент наводит курсор на ФИО преподавателя и сразу нажимает кнопку отправки сообщения.

## Как это реализовать?

### Как оформить в виде React-компонентов?

Я бы реализовал простой вариант — обёртку для ссылки:

```tsx
<UserHoverCard user={user}>
  <Link to="...">
    Иванов Иван Иванович
  </Link>
</UserHoverCard>
```

Это, кажется, один из самых простых вариантов. Не вижу смысла усложнять сильнее.

### Когда загружать данные для карточки пользователя?

#### Вариант 1: загружать все данные заранее

Можно загружать всю нужную информацию сразу там, где мы получаем список пользователей.

Например, в карточке курса при получении списка преподавателей запрашивать не только ФИО и username, но и дополнительные данные для карточки.

##### Плюсы

* Удобнее пользователю: при наведении не нужно ждать загрузки данных.
* Не нужны дополнительные сетевые запросы с фронтенда: после основного запроса вся нужная информация уже есть.

##### Минусы

* Основные ответы API становятся тяжелее: придётся передавать больше данных, даже если пользователь ни разу не откроет карточку.
* Одни и те же данные пользователя будут повторно передаваться в разных эндпоинтах, где этот пользователь встречается.
* Данные карточки расползаются по множеству эндпоинтов. Если изменится состав данных карточки, придётся менять много ответов API.
* Данные карточки могут зависеть от прав доступа. Например, разные пользователи могут видеть разный набор контактных данных. Тогда проверку прав придётся правильно реализовать во всех эндпоинтах, которые возвращают пользователей. Проверка прав расползается по коду и может усложнить бэкенд.
* На первый взгляд может показаться, что такой подход добавляет лишние `JOIN` в запросы, но это не главный аргумент: ФИО и username часто всё равно нужны вместе с ID пользователя, поэтому без `JOIN` во многих случаях не обойтись.
* Насколько это сложно реализовать на бэкенде и фронтенде, пока неочевидно, утверждать ничего не буду.

#### Вариант 2: загружать данные лениво

Противоположный подход — загружать данные для карточки только при наведении на ссылку на пользователя.

Для этого можно сделать отдельный эндпоинт, например:

```http
GET /api/users/:id/hover-card
```

или в будущем пакетный вариант:

```http
POST /api/users/hover-cards
```

##### Плюсы

* Основные ответы API не раздуваются.
* Логика получения данных для карточки находится в одном месте.
* Права доступа проще учитывать централизованно.
* Изменение состава данных карточки затрагивает один эндпоинт, а не множество ответов API.
* TanStack Query кэширует данные по `userId`. Поэтому при повторном наведении на ту же ссылку или на другую ссылку на того же пользователя повторный запрос не нужен, пока данные в кэше актуальны.

##### Минусы

* При первом наведении возможна задержка загрузки.
* Сетевых запросов может стать больше, если пользователь быстро открывает много карточек.

Эти минусы частично смягчают:

* кэширование через TanStack Query;
* скелетоны загрузки внутри карточки;
* пакетная предзагрузка в будущем, если она действительно понадобится.

#### Предлагаемое решение

Сейчас правильнее выбрать ленивую загрузку данных для карточки.

Главная причина: логика не расползается по множеству эндпоинтов. Данные карточки пользователя, особенно контактные данные и возможные права доступа, лучше получать через отдельный специализированный API.

Чтобы не усложнять на старте, пакетную предзагрузку пока можно не делать: это преждевременная оптимизация. Но стоит помнить, что такая возможность есть, если в будущем появятся проблемы с задержкой или с большим числом запросов.

Пока на бэкенде нет API для подробной информации о пользователе. Тикет всё равно делается вертикально: карточка, операция ленивой загрузки на Fetch, MSW-handler и тесты. Отдельного тикета на подключение к настоящему API не нужно. Аватар, описание и контакты пользователь заполняет в профиле (mm-289).

### 2026-10-19T23:25:25Z · t3m8ch

Решение о данных пользователя в контрактах (mm-269): каждый человек в DTO передаётся как `UserRef` — `{ id, username, lastName, firstName, patronymic? }`, та же форма, что `UserSummary` у бэкенда.

Для карточки это значит:

- `<UserHoverCard user={userRef}>` подходит к любому месту, где показан человек: преподаватель курса, опубликовавший версию проверки (mm-270), автор ответа в треде.
- Текст ссылки — `formatFullName(user)`, адрес — `/@username`.
- Данные карточки (аватар, описание, контакты) списки не несут. Карточка загружает их лениво по `user.id`, как предлагает вариант 2 этого тикета, и кэширует по `id`. Поэтому в карточке username всегда свежий, даже если в списке он уже устарел.
