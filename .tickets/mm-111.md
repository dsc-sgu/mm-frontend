# Выбрать явный UX для отказа в course-local доступе

## Question

Какой явный пользовательский и routing contract должен заменить временные молчаливые redirect при отказе в course-local доступе? Решение должно различить как минимум отсутствие Course Membership, недостаточную course-local роль и недоступный участнику ресурс; определить, когда показывать forbidden/not-found state, куда вести recovery action и какие случаи допустимо скрывать redirect или `404`. Текущий redirect Student с `/courses/:courseSlug/stats` на Course Page остаётся временным поведением до этого решения.

## Решение: явные fail-closed состояния вместо access redirects

### Матрица исходов

- Неизвестный Course и существующий Course без Course Membership внешне неразличимы: generic `404`, только общий authenticated shell, recovery action «К моим курсам».
- Course Member с недостаточной course-local ролью получает явный `403`: Course shell и разрешённая navigation остаются видимыми, текст называет требуемую роль, recovery action «На страницу курса».
- Отсутствующий participant-bound ресурс и существующий, но чужой ресурс внешне неразличимы: generic `404`; после подтверждения Membership сохраняется Course shell, recovery action «На страницу курса».
- Network/server failure при проверке доступа не подменяется `403` или `404`: защищённое содержимое не показывается, исходный URL сохраняется, UI предлагает «Повторить» и «К моим курсам».

Внутренние outcomes обязаны различать отсутствие Course, отсутствие Membership, role mismatch, отсутствие ресурса, ресурс вне разрешённой области и технический отказ, даже когда несколько outcomes намеренно сходятся в один внешний `404`.

### Routing и recovery contract

- При course-local access denial исходный URL сохраняется; автоматических redirects нет.
- Recovery выполняется только явным действием пользователя. Отдельная кнопка «Назад» не нужна: browser navigation уже предоставляет это действие.
- Недоступные по роли navigation items скрыты; `403` обслуживает direct, stale и shared links.
- До подтверждения Membership показывается нейтральное loading state без Course metadata, breadcrumbs, navigation, предыдущего или cached protected content.
- Если authoritative revalidation подтверждает потерю Membership, защищённое содержимое немедленно заменяется course-level `404`; если роль больше не подходит текущему разделу — `403`. Действия блокируются, URL не меняется.
- Синтаксически некорректные и корректные, но отсутствующие locators дают generic `404`, а не redirect; frontend не угадывает исправленный locator.
- Unauthenticated → login остаётся отдельным auth redirect и не считается course-local denial.

### Тексты

- `404`: «Страница не найдена» — «Возможно, ссылка устарела или страница больше недоступна.» Текст не сообщает, существует ли Course или ресурс и сработало ли ограничение доступа.
- `403`: «Нет доступа» — для текущих teacher-only routes: «Этот раздел доступен только преподавателям курса.»
- Ошибка проверки: «Не удалось проверить доступ».

В текущем client-rendered приложении `403` и `404` являются категориями route state и UX. При появлении server rendering те же категории должны отображаться в соответствующие HTTP status codes.

### Смена `courseSlug`

Frontend не предполагает сохранение aliases после смены slug. Неизвестный или устаревший slug даёт generic `404`, пока backend явно не предоставит canonicalization contract. Вопрос об alias/history, lifetime и collision semantics, порядке access check и возврате canonical URL добавлен в mm-113 «Реестр frontend-вопросов к backend API»; существующая строка расширена без создания дубликата.

Production/source code и тесты не изменялись.

### 2026-10-19T22:16:43Z · t3m8ch

Часть решения заменена [ADR 0006](https://github.com/dsc-sgu/mm-frontend/pull/265) «Отказ в доступе не раскрывает существования ни на экране, ни по сети».

**Заменено.** Требование «Внутренние outcomes обязаны различать отсутствие Course, отсутствие Membership, role mismatch, отсутствие ресурса, ресурс вне разрешённой области и технический отказ, даже когда несколько outcomes намеренно сходятся в один внешний `404`».

Различать «ресурса нет» и «ресурс чужой» может только бэкенд. Чтобы фронтенд знал разницу внутри, бэкенд должен передать её по сети: статусом (`403` против `404`) или телом (`404` + `not-member` против `404` + `course-not-found`). Тогда разницу видно во вкладке Network, и одинаковый экран ничего не скрывает.

**Теперь.** Чужое и несуществующее неразличимы и во внутренних исходах фронтенда:
- нет курса или нет участия — один исход `not-found`, по сети `404` без тела;
- ресурса участника нет или он чужой — один исход `not-found`, `404` без тела, для локаторов и для чтений по идентичности;
- курс перепроверяется после любого отказа на ресурсе, а не только после `forbidden`.

**Без изменений.** Всё, что видит пользователь: generic `404` курса, `403` раздела по роли, generic `404` ресурса в оболочке курса, «Не удалось проверить доступ» при сбое, тексты и действия восстановления.

Позиция для бэкенда — mm-113, пункт «Forbidden или not-found». Реализация — mm-266.
