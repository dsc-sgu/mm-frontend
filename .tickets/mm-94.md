# Публиковать и отменять server-backed course draft

## Parent

[Перевести course dashboard и редактирование курса на общий mock backend](https://github.com/dsc-sgu/mm-frontend/issues/78)

## What to build

Завершать editing session явными publish и cancel flows. Publish атомарно делает draft активной версией и обновляет read-side; cancel безопасно отбрасывает draft текущей session и возвращает published state.

## Acceptance criteria

- [ ] Publish недоступен при unsynced или failed local operations.
- [ ] Успешный publish делает draft active published snapshot и завершает lease.
- [ ] Course page, dashboard и deadlines получают согласованное обновление.
- [ ] Cancel требует подтверждения при наличии работы и следует session-bound semantics.
- [ ] После cancel editor возвращается к published state без stale working copy.
- [ ] Student не видит промежуточные draft changes до publish.
- [ ] Lint и build проходят.

## Уточнения из [«Спроектировать lifecycle Course Page Working Copy»](https://github.com/dsc-sgu/mm-frontend/issues/118#issuecomment-6090347912)

Покрывается slice 2 «Сессия черновика».

- «Опубликовать» и `Mod+S` открывают один диалог подтверждения. Повторный `Mod+S` в диалоге подтверждает публикацию, подтверждение заблокировано ~0,5–1 с после открытия, `Esc` закрывает диалог без публикации.
- Если публикация заблокирована (lease не мой, ошибки валидации, нет отличий от опубликованной версии, `sync-rejected`, публикация идёт или не подтверждена), диалог не открывается: toast с причинами и фокус на первом невалидном поле. Несинхронизированные правки не блокируют: подтверждение сначала дожидается синхронизации.
- Неизвестный исход → `publishing { unconfirmed }` с замороженной Working Copy и сверкой по id активного snapshot Course. Idempotency key не нужен.
- После публикации — инвалидация Course Page, списка курсов и дедлайнов, затем переход на Course Page.
- «Удалить черновик» заменяет «Сбросить»: подтверждение, `discarding`, переход на Course Page. Простой уход из редактора черновик не удаляет.

Каноническим источником является решение по ссылке выше. Окончательную нарезку на implementation-тикеты определит [«Определить последовательность подготовки и выполнения рефакторинга»](https://github.com/dsc-sgu/mm-frontend/issues/69).
