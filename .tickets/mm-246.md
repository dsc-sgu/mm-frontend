# Спроектировать PWA с офлайн-кэшем для просмотра без сети

## Проблема

Мобильный интернет у студентов регулярно пропадает. Сейчас без сети приложение не открывается совсем, хотя нужное студент часто уже успел загрузить: страницу курса, условие задания, свои попытки и проверки.

Идея: сделать MergeMinds PWA с постоянным резервным кэшем, который включается при потере сети и позволяет **только читать** то, что уже было загружено.

## Что известно сейчас

- В коде нет ни service worker, ни постоянного кэша данных. `localStorage` используется только для мелких настроек интерфейса (например, режим отображения diff).
- Данные страниц читаются через TanStack Query, правила работы с удалёнными данными описаны в `docs/agents/remote-data.md`.
- Часть доменных данных неизменяема по определению в `CONTEXT.md`: опубликованная версия страницы курса и попытка. Сейчас в `CONTEXT.md` это снапшот курса; в модели mm-backend PR #187 (не влит) — версия блока `(id, version)` и чекпоинт. Сама опубликованная страница меняется поблочно. Такие данные можно кэшировать по идентичности без инвалидации. Остальные сущности нужно проверить отдельно.
- Изменяемое и при этом важное для студента: действующий дедлайн, переопределения дедлайнов, состояние доступа к заданию, новые версии проверки, прочитанность проверки.

## Что нужно решить

1. **Минимальный объём офлайн-просмотра.** Только уже открытые страницы курса и саммари заданий, или ещё и свои попытки с проверками? Что из этого студент действительно ждёт без сети?
2. **Холодный запуск без сети.** Должно ли приложение открываться, если его закрыли и открыли заново уже офлайн? Тогда нужно решить, как хранится сессия входа и что с ней делать, когда срок её жизни истёк, а сети нет.
3. **Политика кэша по видам данных.**
   - неизменяемые данные (версия блока или снапшот курса — по итогу mm-34k14, попытка): кэшируются навсегда по идентичности;
   - изменяемые (дедлайны, доступ, проверки): показывать из кэша с явной пометкой «данные на такое-то время». Показывать устаревший дедлайн без пометки опаснее, чем не показывать его вовсе.
4. **Что считается «загруженным».** Кэшируем всё, что студент видел, или заранее подгружаем нужное (например, текущую цепочку заданий)?
5. **Личные данные на устройстве.** Кэш содержит оценки и комментарии проверки. Что его стирает: выход из системы, смена пользователя, срок давности? Что будет на общем устройстве?
6. **Что делает интерфейс офлайн.** Какие действия блокируются, как это показано, как приложение узнаёт, что сеть вернулась, и когда обновляет данные.
7. **Где хранить.** Service worker для оболочки приложения и запросов, плюс IndexedDB или сохранение состояния TanStack Query для данных. Нужно проверить, что подходит под правила из `docs/agents/remote-data.md` (отмена запросов, повторы, ошибки).
8. **Рабочие копии преподавателя.** Офлайн-редактирование курса и проверок явно **не входит** в этот тикет. Но стоит убедиться, что кэш не конфликтует с черновиками страницы курса и бронью проверки (см. `docs/adr/0004-browser-shared-editor-lease.md` и mm-34k14).

## Заготовка выводов (интерпретация, не решение)

- Чем больше данных адресуется неизменяемой идентичностью, тем проще кэш. Поэтому ответ на вопрос 3 стоит начать с перечня сущностей и признака «изменяется или нет».
- Дедлайн и состояние доступа: единственное, где устаревший кэш может ввести студента в заблуждение. Для них нужна пометка времени, а не молчаливый показ.

## Связанное и ограничения

- Контракт ссылочных блоков и точка расширения под будущие плагины обсуждаются в mm-129. Офлайн-кэш не должен их закрывать: ключи кэша строятся на неизменяемых идентичностях, а не на формате конкретных блоков. Сами плагины в этот тикет не входят: у них своя модель доверия к чужому коду.
- Вопросы к бэкенду (заголовки кэширования, версии сущностей, срок жизни сессии) складываем в mm-113 — реестр вопросов фронтенда к API бэкенда, — когда они станут понятны.

## Результат тикета

Решения по пунктам 1–7 в виде комментария или ADR, список сущностей с признаком «изменяется или нет» и, если решено делать, набор тикетов на реализацию. Реализации в этом тикете нет.
