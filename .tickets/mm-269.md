# Передавать людей в контрактах как UserRef: id, username и части ФИО

## Зачем

Карточка пользователя при наведении (mm-3) загружает свои данные лениво, по `id`. Сами списки должны нести ровно то, что нужно для ссылки на пользователя:

- ФИО — текст ссылки (`formatFullName()`);
- `username` — показ рядом с ФИО (студенты должны запоминать ники) и адрес профиля `/@username`;
- `id` — сравнение, ключ кэша карточки и её загрузка.

Сейчас правило «People in contracts» определяет человека в контракте как `{ id, lastName, firstName, patronymic? }`, без `username`. Новые DTO следуют ему: автор в `load-review` и студент в `load-attempt-summary` приходят без `username`, и показать ник или построить ссылку на профиль там нельзя. Отдельного типа для этой формы нет: каждый DTO собирает `id` и `FullNameSchema` сам.

Бэкенд уже передаёт людей в ответах курсов как `UserSummary { id, firstName, lastName, patronymic, username }` (mm-backend@ddd9849, `internal/courses/response.go:20`). `UserRef` повторяет эту форму.

`username` при этом не становится идентичностью: он изменяемый (`CONTEXT.md`, User). В списке он может устареть до обновления данных — ADR-0005 это допускает: списки показывают username, но адрес по нему не правят. Карточка загружается по `id`, поэтому в ней username всегда свежий.

## Делает

- `features/auth/model/user-ref.ts`: `UserRefSchema` — `{ id: UserIdSchema, username: UsernameSchema, ...FullNameSchema.entries }` и `type UserRef = v.InferOutput<typeof UserRefSchema>`.
- `AGENTS.md`, раздел «People in contracts»: человек в DTO или доменном типе — `UserRef` (`{ id, username, lastName, firstName, patronymic? }`). `username` — только для показа и как локатор в ссылках; сравнение и ключи — только по `id`. Данные сверх `UserRef` (аватар, контакты) приходят из отдельного чтения по `id` (mm-3), а не с каждым списком.
- `review/api/load-review.ts`: `AuthorSchema` заменяется на `UserRefSchema`; `ReviewAuthor` в `review/model/types.ts` — это `UserRef`.
- `attempt-review/api/load-summary.ts`: студент — `UserRefSchema`; тип студента в `attempt-review/model/types.ts` — `UserRef`.
- Моки бэкенда отдают `username` во всех этих ответах.
- Тесты операций: ответ, где у человека нет `username`, — отказ `invalid-response`.

## Не входит

- Преподаватель курса в `loadCourses` — это mm-259. Если этот тикет сделан раньше, mm-259 берёт `UserRefSchema` вместо своей формы `{ id, username } & FullName`.
- Формат ФИО в шапке и у преподавателей курса — mm-258.
- Кто опубликовал версию проверки в селекторе попыток — отдельный тикет, который зависит от этого.
- Сама карточка пользователя — mm-3.
- Старые агрегаты со строкой имени в `features/attempts`.

## Готово, когда

- [ ] `UserRefSchema` и `UserRef` есть в `features/auth/model/user-ref.ts`.
- [ ] Ни один новый DTO не собирает `id` и `FullNameSchema` вручную.
- [ ] Правило «People in contracts» описывает `UserRef` и роль `username`.
- [ ] `bun run lint`, `bun run build` и тесты проходят.
