# Выбрать слоистую стратегию тестирования

## Question

Какая стратегия тестирования нужна реализованной системе: какие гарантии обеспечивают static, pure-model, stateful-model, boundary integration, component interaction и E2E слои; какой стек выбрать; где нужны characterization tests; как контролировать fixtures, browser behavior, coverage и flaky tests?

## Решение: слоистая стратегия behavioral testing

### Основной принцип

Тесты организуются не как механическая пирамида и не ради процента покрытия, а вокруг наблюдаемых контрактов и устойчивых seams.

Каждый контракт подробно проверяется на самом дешёвом уровне, который способен достоверно его доказать. Сквозные E2E-сценарии подтверждают, что уровни действительно соединены, но не повторяют всю комбинационную матрицу нижних тестов. Наиболее опасные fail-closed инварианты identity, course-local access, сохранности данных и целостности Review дополнительно получают независимые отрицательные проверки на нескольких уровнях, включая настоящий браузер.

### Ответственность слоёв

1. **Static gates** — TypeScript build, ESLint и целевые статические архитектурные правила. Они доказывают типовую и структурную корректность, но не пользовательское поведение.
2. **Pure-model tests** — чистые функции, decision tables, guards, validation, normalization, serialization и FSM transitions без React, DOM и transport. Здесь исчерпывающе проверяются комбинации, границы и доменные инварианты.
3. **Stateful-model tests** — reducers и свежие Zustand store instances. Они проверяют последовательности событий, lifecycle, concurrency/pending/error transitions и отсутствие утечки состояния между сценариями.
4. **Boundary integration tests** — реальная связка Fetch/MSW, Valibot validation/mapping, operation-specific outcomes, TanStack Query keys/cache и Router boundaries без полного браузерного пути. Они защищают trust boundary, identity, cancellation, invalidation и atomic/authoritative projections.
5. **Component interaction tests** — React Testing Library + `user-event` в `jsdom`, с новым Router, QueryClient и feature state на сценарий. Они проверяют наблюдаемые loading/error/denied/pending states, формы, доступные роли и пользовательские действия; внутреннее состояние компонентов не является контрактом.
6. **Real-browser integration tests** — Playwright для `contenteditable`, native selection, clipboard, focus, keyboard, DnD, layout/geometry, Worker/WASM и lifecycle-safe scheduling. Проверяется наблюдаемый outcome, а не `queueMicrotask`, число animation frames или другие workaround.
7. **E2E tests** — тонкий набор завершённых критических путей через приложение целиком. Они доказывают соединение route, UI, transport, cache и domain rules; комбинационные ошибки остаются на более дешёвых слоях.

### Стек

- Vitest — runner для Node и `jsdom`.
- React Testing Library + `@testing-library/user-event` — component interaction.
- MSW — единый network-level mock seam после Fetch cutover; mock и real responses проходят один production validation path.
- Playwright Test и официальные Plate Playwright utilities — вся real-browser integration и E2E поверхность.
- Vitest Browser Mode сейчас не вводится, чтобы не поддерживать третью инфраструктуру. Его можно рассмотреть только по фактическим данным, если isolated browser-component suite станет большим и Playwright окажется чрезмерно тяжёлым.

### Characterization policy

Characterization tests добавляются выборочно перед рискованным рефакторингом, когда иначе можно незаметно изменить значимый фактический outcome. Они не канонизируют весь текущий implementation.

Известно неверное или временное поведение, включая молчаливые access redirects, допускается фиксировать только как явно временную characterization-защиту с известным целевым контрактом и условием удаления. После реализации продуктового решения такой тест заменяется behavioral contract test; дефект не сохраняется ради прохождения старого теста.

### Fixtures и изоляция

- Feature-owned минимальные factories/builders с явными overrides.
- Небольшой каталог именованных relationship-safe сценариев Course/Task/Attempt/Review для boundary и E2E.
- Каждый тест получает свежие Router, QueryClient, local store и resettable MSW state; singleton/mock stores явно сбрасываются.
- Большие application mock aggregates не копируются как неявный canonical fixture.
- Generated IDs проверяются по свойствам, уникальности и связям, а не по конкретным значениям; clock/randomness контролируются только там, где влияют на контракт.
- Failure profiles описывают значимые исходы операции, а не случайные задержки текущих RAM-моков.

### Browser matrix и merge gates

Chromium, Firefox и WebKit равноправны. Chromium не является основным или более авторитетным браузером.

Перед каждым merge запускаются:

- lint и build;
- все Node, stateful-model, boundary и `jsdom` suites;
- вся Playwright real-browser/E2E поверхность в Chromium, Firefox и WebKit.

Browser-specific capability contracts проверяются по их собственным ожидаемым исходам: например, clipboard auto-read может быть Chromium-only, но manual input/paste остаются обязательны в Firefox и WebKit. Ослаблять matrix заранее нельзя. Разделение suites или изменение частоты допускается только после фактических измерений duration/resource cost, а не из предположения, что полный matrix медленный.

### Coverage

Основной критерий достаточности — risk-weighted critical-contract matrix: пользовательский путь × outcome × отказ × слой-владелец. Coverage report служит диагностикой пропущенных ветвей, но глобальный line/branch threshold не является release gate.

Высокий локальный branch coverage допустим для компактных pure-model decision tables/FSM, где каждая ветвь соответствует содержательному исходу. UI и E2E не оцениваются процентом покрытия.

### Flaky policy

- Один автоматический retry допустим только для trace/диагностики и классификации; прохождение со второй попытки не считается чистым результатом.
- Flaky test получает владельца и issue, а не дополнительные бессрочные retries.
- Временный quarantine допустим только для некритичного сценария, с причиной и условием возврата.
- Identity/access, data-loss и atomic Review publication tests нельзя quarantine-ить; их нестабильность блокирует merge до исправления теста или недетерминированной seam.
- Числовой допустимый flaky-rate не выдумывается заранее: он может быть установлен по истории запусков, не ослабляя запрет на нестабильность критичных гарантий.

### Accessibility и visual checks

- Component tests проверяют accessible role/name/state, focus order и keyboard outcome там, где это часть поведения.
- Playwright + axe проверяет ключевые устойчивые состояния критических экранов.
- ARIA snapshots используются точечно только для небольшой стабильной структуры.
- Pixel screenshot assertions не используются. Screenshots и traces сохраняются как диагностические artifacts.
- Автоматика не объявляется полной гарантией accessibility; ручной аудит остаётся отдельной release-практикой за пределами этой planning-карты.

### Следствие для карты

После спецификации критических вертикалей нужен отдельный конкретный каталог тестовых контрактов: именованные scenarios, fixtures, слой-владелец каждого контракта и минимальные cross-browser/E2E proofs. Он должен следовать этой стратегии и не проектировать тесты раньше поведения.

Production/source code, test runner и тесты в рамках решения не изменялись.
