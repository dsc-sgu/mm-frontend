# Выбрать критические пользовательские пути и гарантии

## Question

Какие из уже реализованных пользовательских путей являются критическими для MergeMinds, какие результаты и отказные сценарии в них недопустимы, и по каким критериям дальше приоритизировать спецификации, рефакторинг и тесты?

## Решение: критические пути, недопустимые отказы и порядок защиты

### Критические пользовательские пути

Все реализованные end-to-end пути считаются бизнес-критичными:

1. вход и доступ к Course;
2. Student открывает собственную Attempt и читает опубликованную Review;
3. Teacher находит Attempt через Course Attempts и переходит ровно к выбранной работе;
4. Teacher проверяет immutable Attempt и публикует Review с Grade;
5. Teacher редактирует и публикует Course content.

Бизнес-критичность отделяется от текущего engineering priority. Login/register flow пока не следует закреплять подробными тестами: frontend использует mock-авторизацию, а целевой flow может измениться при внедрении OpenID. Стабильный course-local authorization contract защищается уже сейчас независимо от identity provider.

### Недопустимые отказы

Система не должна показывать правдоподобный успех или результат, если не может гарантировать:

- точную identity Course + Task + Student + Attempt;
- отсутствие доступа к чужому Course, Attempt или teacher-only действию;
- полную загрузку материала Attempt, на основании которого публикуется Review;
- атомарную первую публикацию Review вместе с обязательной Grade;
- отсутствие скрытой потери Review Working Copy или Course Working Copy;
- единую authoritative Grade в Teacher review, attempts list, task history и Student result;
- целостность Grade, Overall Feedback и teacher Line Comments одной Review revision.

При риске несправедливой оценки, потери данных или нарушения доступа действие блокируется. Предпочтителен явный отказ вместо частичного или недостоверного результата.

### Course Membership и authorization

Identity provider отвечает на вопрос «кто пользователь», а Course Membership — «что ему разрешено». Поэтому независимо от будущего OpenID-flow нужно защищать следующие правила:

- Course Membership и единственная course-local роль являются источником permissions;
- Student видит только собственные Attempts и опубликованные Reviews;
- только Teacher Course редактирует Course и Review;
- глобальная session role не подменяет course-local authorization.

### Полнота Attempt и Review

Authoritative changed-files manifest определяет полный состав Attempt.

В текущем one-shot flow редактирование и публикация Review доступны только после успешной полной загрузки обязательных данных. Если файл или diff не загрузился после ограниченных automatic retries:

- публикация блокируется;
- UI перечисляет проблемные файлы и показывает terminal error;
- Teacher может повторить загрузку вручную;
- Review Working Copy не теряется.

Известный binary, oversized или unsupported файл не считается скрытой ошибкой, если UI явно показывает его наличие и даёт предусмотренный способ проверить содержимое.

Будущая streaming/lazy-loading реализация может сразу отображать полученные части, но публикация разблокируется только после успешного terminal marker всех обязательных streams. До появления streaming тестируется обычная полная загрузка; streaming lifecycle нельзя преждевременно закреплять тестами.

Review Lease можно выдать и поддерживать до завершения загрузки: lease означает исключительное право редактирования, а не полноту данных. Сами поля нельзя изменять и новую revision нельзя публиковать до полной загрузки immutable Attempt и latest Review. При будущей потоковой загрузке части существующей Review можно показывать с явным incomplete/loading state.

Teacher не обязан открывать каждый changed file перед публикацией: `viewed` не доказывает прочтение. Индикаторы viewed/unviewed в file tree считаются полезной неблокирующей защитой от человеческой ошибки, но не publication gate и не текущим приоритетом.

### Публикация и согласованность Review

Канонический lifecycle остаётся решением из [«Зафиксировать канонический доменный язык и состояния»](https://github.com/dsc-sgu/mm-frontend/issues/65): до первой публикации существует local Review Working Copy, но persisted ReviewDraft не требуется; первая Review появляется атомарно вместе с Grade.

Если запрос публикации мог быть принят, но frontend не получил ответ:

- состояние остаётся `pending`;
- frontend читает authoritative Review revision и выполняет reconciliation;
- нельзя сообщать ложный успех, немедленно считать операцию неуспешной или слепо создавать повторную Review.

Публикация Review требует документированного idempotency key и backend deduplication semantics. Внешний вопрос добавлен в [«Реестр frontend-вопросов к backend API»](https://github.com/dsc-sgu/mm-frontend/issues/113).

После принятия новой revision временное расхождение read models допустимо только как явный `pending`. Student продолжает видеть предыдущую целостную Review с сообщением о синхронизации; новая Grade, Overall Feedback и teacher Line Comments появляются вместе, а не частями.

Browser-local recovery Review Working Copy желателен в будущем, но не входит в первый implementation priority. Его lifetime, logout cleanup, isolation и UX конфликта с новой server revision определяются тогда, когда эта возможность будет проектироваться; сейчас они не блокируют критические спецификации.

### Course editing

При network failure, lease loss или snapshot conflict публикация Course блокируется, а несинхронизированная Course Working Copy сохраняется до явного решения Teacher. Ложный save и потеря working copy после одного сообщения об ошибке недопустимы. Automatic merge, browser-crash recovery и точный conflict-resolution UX не фиксируются до соответствующей implementation-задачи.

### Course Attempts и quick grading

Обязательный контракт Course Attempts:

- полный корректный список доступных Teacher Attempts либо явное incomplete/error state;
- корректные фильтры;
- переход ровно к выбранной Attempt;
- надёжный individual review и individual grading.

Bulk selection и quick grading — productivity accelerator, а не минимальное ядро. Их текущий UI не нужно цементировать спецификациями и тестами: форма может измениться, упроститься или исчезнуть. Это отдельное продуктовое решение.

### Допустимые деградации

Если integrity и access сохранены и состояние показано честно, временно допустимы:

- медленный, но корректный путь;
- блокировка редактирования при конфликте или transport failure;
- поломка prefilter, selection persistence или другого навигационного удобства, если данные достижимы вручную;
- потеря темы, diff layout и других visual preferences;
- отсутствие bulk/quick grading при доступном individual workflow.

### Правило и порядок приоритета

Критерии применяются лексикографически:

1. риск необратимого вреда;
2. стабильность требования;
3. частота использования;
4. центральность Git-like review как tie-breaker.

Отсюда порядок дальнейших спецификаций, refactoring seams и защитных тестов:

1. identity, integrity и course-local access;
2. Review → Grade → Student result;
3. Course editing без потери данных;
4. Attempts list, filters и точная навигация;
5. deferred/volatile surfaces: OpenID UI, конкретная форма bulk/quick grading, browser-local draft recovery и viewed indicators.

Production/source code и тесты в рамках решения не изменялись.

## Уточнения из [«Спроектировать Review → Grade → Student result vertical»](https://github.com/dsc-sgu/mm-frontend/issues/116)

Решение Review vertical уточняет три формулировки этого решения. Остальные гарантии остаются в силе.

1. **Нетекстовые файлы.** Записи manifest вида `binary`, `too-large` или `unsupported` не блокируют публикацию, если UI явно показывает их с пометкой «не отображается». Отдельный способ проверить их содержимое (например, скачивание) больше не обязателен. Это сознательное ослабление прежнего требования, принятое владельцем.
2. **Неизвестный исход публикации.** Сверка выполняется повтором той же логической команды с тем же idempotency key: ответ backend на повтор и есть авторитетный исход. Пока исход неизвестен, Review Working Copy заморожена. Ложный success, немедленный провал и вторая Review по-прежнему исключены.
3. **Pending для Student'а.** Frontend не выводит состояние синхронизации сам. Сообщение «идёт синхронизация» показывается только при явном сигнале backend, а каждый ответ backend обязан содержать ровно одну целостную Review Revision. Расхождения между экранами устраняются номерами revision и инвалидацией проекций.
