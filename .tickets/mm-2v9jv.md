# Определить единый формат тела ошибок API

## Проблема

Сейчас нет единого формата тела ошибки API: конкретные операции определяют ответы независимо. Отказы доступа используют пустое тело, некоторые ожидаемые отрицательные исходы требуют структурированных данных, а неожиданные HTTP-статусы превращаются во фронтендовый `OperationFailure` без чтения тела.

Нужен общий контракт, чтобы бэкенд возвращал ошибки предсказуемо, а фронтенд мог проверять их и выбирать поведение по стабильным признакам, не разбирая текст сообщения.

## Цель

Определить и зафиксировать единый формат тела ошибок API и правила его использования. Согласовать контракт между фронтендом и бэкендом; явно описать допустимые исключения и переход от текущих ответов.

## Что решить

- Выбрать форму JSON и обязательные/необязательные поля: стабильный машинный код, диагностическое описание, дополнительные данные конкретной операции, ошибки полей формы и идентификатор для диагностики. Наличие и назначение каждого поля обосновать; этот перечень — вопросы проектирования, а не заранее утверждённая форма.
- Определить связь HTTP-статуса, машинного кода и специфичных для операции исходов. Общий формат не должен превращать каждый `4xx` в технический отказ: ожидаемый отрицательный исход остаётся частью контракта операции.
- Определить, когда тело отсутствует: в том числе для `401`, отказов доступа `403`/`404`, ответов инфраструктуры и прокси. Сохранить неразличимость чужого и несуществующего ресурса по ADR 0006; любые изменения текущих контрактов пустого тела описать явно.
- Разделить диагностический текст и пользовательские сообщения: определить правила локализации, обработки ошибок полей и безопасного отображения. Не показывать произвольный текст сервера напрямую пользователю.
- Описать поведение при неизвестном коде, некорректном JSON, неправильной форме и ответах без тела. Неизвестный или невалидный ответ не изображается успехом.
- Определить место общей схемы проверки и обработки на фронтенде, композицию со схемами дополнительных данных операций и соотношение с `OperationFailure`. Не смешивать формат HTTP-ответа с внутренним объектом ошибки фронтенда.
- Определить правила расширения формата и совместимости, затем перечень затронутых операций и порядок перехода без второго временного пути данных.

## Готово, когда

- Зафиксированы выбранный формат, значения полей, связь со статусами и явные исключения.
- Есть примеры обычного отказа, ошибок полей, ожидаемого конфликта и отказа доступа; для каждого указан HTTP-статус, заголовки, тело либо его отсутствие и поведение фронтенда.
- Описаны сценарии неизвестного кода, невалидного/пустого тела и технического ответа прокси.
- Решение согласовано с правилами `docs/agents/remote-data.md` и ADR 0006; необходимые изменения документации перечислены или внесены.
- В mm-113 зафиксировано решение для бэкенда; оставшаяся реализация разложена на конкретные тикеты фронтенда и бэкенда с проверяемыми критериями.

## Границы

Это тикет на определение общего контракта и плана внедрения. Массовое изменение всех операций API и реализация бэкенда не входят автоматически: их объём определяется после решения. Приоритет P1 по запросу владельца.
