# Спроектировать Course access vertical и identity seam

## Question

Какая целевая форма законченного Course access vertical должна провести User от route identity до разрешённого Course или явного отказа: где живут interfaces стабильной Course/User identity, mutable route slug, Course Membership, course-local permissions, existence lookup и denied/not-found outcomes; как Router, feature operations и Query cache используют их без дублирования authorization logic? Решение должно опереться на канонический доменный язык и выбранный Fetch/MSW contract, включить только реализованные Course routes и подготовить конкретные seams для первого refactoring slice. Конкретный UX отказа берётся из mm-111 «Выбрать явный UX для отказа в course-local доступе»; production/source code и тесты не менять.

## Решение: Course lookup как единый access spine

Решение задаёт целевую форму первого refactoring vertical без compatibility layers и без изменения production/source code в рамках wayfinding.

### Identity и locators

- `UserId` — immutable identity текущего User и входит в session projection. `username` остаётся mutable display/route locator и не используется как доказательство ownership или authorization.
- `CourseSlug` — mutable route locator. `CourseId` — стабильная identity для feature operations и cache.
- `UserId`, `CourseId`, `CourseSlug`, `Username`, `AttemptId` и `AttemptNumber` должны быть статически различимыми типами.
- Полная `CourseMembership` имеет смысл в проекциях нескольких участников как `CourseId + UserId + CourseRole`. В результате входа текущего User она не возвращается: User уже задан session, Course — результатом lookup, поэтому достаточно `role` без однословной обёртки `CurrentCourseAccess`.

### Course и Course Page — разные проекции

Вход в любой реализованный Course route начинается одной access-aware операцией `loadCourseBySlug(courseSlug, signal)`. Это загрузка самого Course по locator, а не отдельный permission-check endpoint:

```ts
type LoadCourseResult =
  | {
      status: 'found';
      course: {
        id: CourseId;
        title: string;
        shortTitle: string;
        iconName: CourseIconName;
        color: CourseColor;
      };
      role: CourseRole;
    }
  | { status: 'course-not-found' }
  | { status: 'not-member' };
```

- `slug` не дублируется в response: Router уже владеет locator, а aliases/canonicalization не предполагаются.
- Отдельный `fetchCourseAccess` и поиск Course в общей list projection удаляются.
- `CourseId` из успешного lookup становится identity для дочерних operations и query keys.
- `Course Page` остаётся отдельным документом и загружается через `loadCoursePage(courseId)` только для маршрута, которому нужен этот документ. Вложенные routes не загружают Course Page ради identity или роли.

### Section-level policy

Одна небольшая таблица является источником правил для navigation и route authorization реализованных Course sections:

```ts
const courseSectionAccess = {
  page: 'member',
  journal: 'member',
  attempts: 'teacher',
  repositories: 'teacher',
  files: 'teacher',
  analytics: 'teacher',
  edit: 'teacher',
} as const;
```

Она не становится универсальной permission framework и не владеет resource ownership или mutation permissions.

- Course Page и Task Page доступны любому Course Member.
- Journal доступен обоим ролям: Student получает только персональную projection, Teacher — общую.
- Course Attempts, repositories index, Course files, analytics, Course/Task editing и Review editing требуют Teacher.
- Student может читать только собственные participant-bound Repository, Attempts и опубликованные Reviews; Teacher — ресурсы Students этого Course.
- Недоступные navigation items скрыты, но direct/stale/shared link обрабатывается route policy.

### Participant-bound resources

Текущая форма URL сохраняется в первом slice, но route values считаются только locators:

- `$studentUsername` остаётся `Username` locator;
- числовой `$attemptId` переименовывается в `$attemptNumber`;
- feature-owned operation разрешает route locators в стабильные `UserId` и `AttemptId`;
- после разрешения operations и cache используют стабильные IDs.

Course context больше не содержит `studentUsernames`. Backend авторитетно проверяет existence и доступ. Каждая remote operation имеет собственный operation-specific union; общий `LoadResourceResult<T>` не вводится. Например:

```ts
type LoadAttemptResult =
  | { status: 'found'; attempt: Attempt }
  | { status: 'not-found' }
  | { status: 'forbidden' };
```

`forbidden` — понятная внутренняя причина: ресурс существует, но недоступен текущему User. Отображение зависит от вида отказа:

- section-level `forbidden` → явный `403`;
- participant-bound resource `forbidden` → generic `404`;
- resource `not-found` → тот же generic `404`.

Так frontend сохраняет внутреннее различие, но не раскрывает существование чужого ресурса. Сравнения `session.username === routeUsername` и client-side roster checks удаляются; backend повторно авторизует каждую защищённую operation.

### Route outcomes

- `course-not-found` и `not-member` внешне неразличимы и дают course-level generic `404`.
- Section role mismatch даёт `403` с сохранением разрешённого Course shell.
- Resource `not-found` и `forbidden` дают resource-level generic `404` с Course shell после уже подтверждённой Membership.
- Network, неожиданный response и invalid DTO не маскируются под access denial: route показывает явное retryable «Не удалось проверить доступ» и сохраняет URL.
- До подтверждения Membership защищённые metadata, navigation и cached content не показываются.
- Единственный автоматический redirect в этой цепочке — unauthenticated → login.

### Query cache и session consistency

Query keys принадлежат своим projections:

```ts
const courseContextKeys = {
  all: ['course-context'] as const,
  bySlug: (userId: UserId, courseSlug: CourseSlug) =>
    [...courseContextKeys.all, userId, courseSlug] as const,
};

const coursePageKeys = {
  all: ['course-pages'] as const,
  detail: (courseId: CourseId) =>
    [...coursePageKeys.all, courseId] as const,
};
```

- `UserId` входит в Course context key, потому что authenticated session — неявный вход lookup и разные Users получают разные роли или denial для одного slug.
- Course Page key содержит только `CourseId`, пока документ действительно одинаков для всех Course Members. User-specific projections получают отдельные families с `UserId`.
- Login, logout и session replacement очищают session-bound protected cache.
- Course context revalidate-ится при новом входе в Course, reconnect/focus и после access-related отказа защищённой operation. Подтверждённая потеря Membership закрывает subtree как `404`, смена роли пересчитывает navigation и текущий section state.
- Route context является frontend UX gate, но не security boundary: backend проверяет доступ каждой operation.

Если будущая profile mutation меняет `username`, стабильный `UserId` остаётся прежним, но session projection должна быть согласована до завершения success-flow: полный авторитетный response записывается в точный session cache, иначе session query инвалидируется и ожидается refetch. Повторный login не нужен без отдельного backend security requirement. Если текущий URL содержит старый username, Router заменяет locator на новый; старый username не считается alias.

### Первый refactoring slice

Выполняется один архитектурно чистый cutover всех реализованных Course routes:

1. Ввести стабильные identity-типы и `session.userId`; убрать global session role из course-local решений.
2. Реализовать `loadCourseBySlug` через выбранный Fetch/Valibot/MSW path и `courseContextKeys`.
3. Перевести Course root на новый lookup, явные route states и context с `CourseId`, shell metadata и `CourseRole`.
4. Подключить единую section policy к navigation и всем реализованным Course routes.
5. Перевести participant-bound routes на feature-owned resource operations и стабильные identities.
6. Перевести дочерние query families с slug/username locators на `CourseId`/`UserId`/resource IDs там, где lookup уже выполнен.
7. Удалить `fetchCourseAccess`, `COURSE_ACCESS_QUERY_KEY`, `studentUsernames`, старые redirect guards, username-based ownership и obsolete cache paths.

Переходных adapters, aliases и параллельного старого access path не создаётся. Точные backend statuses/payloads остаются внешней предпосылкой из реестра frontend-вопросов к backend API; frontend operation contracts выше не должны молча определять backend wire format.

Production/source code и тесты не изменялись.

### 2026-10-19T22:16:45Z · t3m8ch

Часть решения заменена [ADR 0006](https://github.com/dsc-sgu/mm-frontend/pull/265) «Отказ в доступе не раскрывает существования ни на экране, ни по сети».

**Заменено.** Внутренние исходы отказа:
- курс: `course-not-found` и `not-member`;
- ресурс участника: `not-found` и `forbidden` («ресурс существует, но недоступен текущему User»).

Различие держалось на ответе бэкенда (`404` + `not-member` против `404` + `course-not-found`; `403` против `404`), поэтому раскрывало по сети то, что экран намеренно скрывает.

**Теперь.**
- Курс: исходы `found` и `not-found`; нет курса и нет участия неразличимы.
- Ресурс участника: исходы `found` и `not-found`; нет и чужой неразличимы. По сети в обоих случаях `404` без тела.
- Перепроверка контекста курса — после любого отказа на ресурсе, а не после `forbidden`.
- Отказ после `found` считается потерей доступа: кэш данных курса удаляется. Смена slug того же курса обрабатывается только через ответ `found` с новым slug (ADR 0005, mm-254).

**Без изменений.** Отображение: course-level generic `404`, section `403` по роли с оболочкой курса, resource-level generic `404` с оболочкой курса. Seam идентичностей, revalidation при входе, reconnect и focus.

Позиция для бэкенда — mm-113, пункт «Forbidden или not-found». Реализация — mm-266.
