# Флаки E2E редактора Course Page: нумерация списков и каретка после перетаскивания

Тесты редактора Course Page из [#148](https://github.com/dsc-sgu/mm-frontend/issues/148) зависят от порядка запуска и от нагрузки. Каждый проходит по отдельности, но при прогоне файла целиком или под нагрузкой падает. CI на `main` пока зелёный, однако локальный полный прогон Playwright всегда красный. Из-за этого по нему нельзя судить, сломал ли изменение что-то.

### Наблюдения

Всё проверено 2026-10-14 на `main` @ 29fcd78 (поведение совпадает с веткой #235).

**Стабильно падают в WebKit при прогоне `lists.spec.ts` целиком, в том числе с `--workers=1`:**
- `lists.spec.ts:189` «смена ordered → unordered завершает серию: 1 / • / 1»
- `lists.spec.ts:265` «перетаскивание выделенных items переносит их группой»
- `lists.spec.ts:296` «после Apply и повторного открытия номера те же: items из отдельных команд»
- `lists.spec.ts:314` «read-only показывает те же номера, что редактор: items из отдельных команд»

Поведение одинаковое в нативном WebKit на ALT Linux и в официальном образе `mcr.microsoft.com/playwright:v1.64.0-noble` (Ubuntu noble, как в CI), то есть дело не в ОС. При запуске по одному, например `lists.spec.ts:189 --project=webkit`, все проходят.

**Падают под нагрузкой.** Полный параллельный прогон, load average около 10:
- `focus.spec.ts:147` «перетаскивание оставляет каретку в перемещённом блоке» и `focus.spec.ts:165` «undo возвращает каретку в затронутый блок» — в Chromium и Firefox;
- в Firefox: `lists.spec.ts` 240, 250, 296 и `course-access/participants.spec.ts:9`.

По отдельности тоже проходят.

**Открытый вопрос:** почему CI зелёный. Возможные отличия CI: число воркеров на 2-ядерном runner, порядок тестов, `CI=true`, retries.

### Гипотезы (не проверены)

1. Тесты одного файла делят состояние: in-memory mock backend, MSW, контрольный канал dev server, storage. Тогда исход теста зависит от того, какой тест шёл перед ним.
2. Перетаскивание через dnd-kit и проверки каретки ждут таймингов или анимаций, а не видимого состояния. Под нагрузкой или в WebKit они не успевают.

### Делает

- Находит минимальное воспроизведение: какой тест или какая комбинация в каком порядке ломает перечисленные тесты. Подойдут `--grep`, бисекция набора и `--trace on`.
- Устанавливает первопричину и подтверждает её экспериментом.
- Исправляет причину: изоляцию состояния между тестами, ожидание видимого состояния вместо таймингов или баг приложения, если он реальный.
- Если причина в коде приложения, а не в тестах, сначала описывает её в issue и только потом исправляет.

### Не входит

- Увеличение таймаутов, retries, `test.skip` и `test.fixme`. По политике [#68](https://github.com/dsc-sgu/mm-frontend/issues/68) тест, который прошёл только при повторе, всё равно валит прогон.

### Готово, когда

- `lists.spec.ts` и `focus.spec.ts` целиком проходят 3 раза подряд в Chromium, Firefox и WebKit.
- Полный `bunx playwright test` зелёный локально.
- `bun run lint` и `bun run test` проходят.
- В PR описаны первопричина и способ, которым она подтверждена.

### Локальный запуск

На ALT Linux браузеры берутся из podman-контейнера `run-server`, а тесты и vite работают на хосте:

```bash
podman run --rm --init -d --name playwright-server --network host --ipc host \
  mcr.microsoft.com/playwright:v1.64.0-noble \
  npx -y playwright@1.64.0 run-server --port 3000 --host 127.0.0.1

PW_TEST_CONNECT_WS_ENDPOINT=ws://127.0.0.1:3000/ PLAYWRIGHT_PORT=<уникальный порт> \
  bunx playwright test playwright/course-page-editor/lists.spec.ts --project=webkit --workers=1
```

Версия образа должна совпадать с `@playwright/test` в `package.json`.
