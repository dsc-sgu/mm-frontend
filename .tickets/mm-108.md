# Выбрать frontend transport/API seam и правила cache invalidation

## Question

Какой единый контракт должен отделять feature-модули реализованного frontend от транспорта и mock/real implementations: оставить Axios или принять Fetch, где выполнять runtime validation DTO, как владеть query keys и cache invalidation, и как переключать mock/real backend без рассыпания условий по features? Решение должно опираться на фактическую локальность Axios в auth, текущие mock-only API остальных features и выбранный канонический доменный язык; реальный backend API и сама миграция остаются вне этой карты.

## Comments

### 2026-09-11T08:16:22Z · t3m8ch

## Вход от владельца: явный Result-like error API

Предпочтение для transport seam: не строить прикладной API вокруг исключений. Использовать Rust/Haskell-подобный явный результат — discriminated union `Result<T, E>` — где HTTP failures, network failures, abort и invalid response представлены типизированными вариантами.

Уточнение для будущего решения:

- ожидаемые доменные исходы не считать transport errors: например, `401` при проверке session остаётся вариантом `not-authorized`;
- `fetch` всё ещё reject-ит promise при network/CORS/abort failures и JSON parsing может бросить, поэтому transport boundary должен перехватить их и преобразовать в `Err`;
- TanStack Query использует rejected promise для `isError`, retries и error boundaries. Нужен явный adapter, который unwrap-ит `Result` и бросает только на границе TanStack Query; domain/model code продолжает работать с ADT;
- не добавлять Result-библиотеку по умолчанию: локального discriminated union достаточно, пока combinator complexity не докажет обратное.

### 2026-09-11T08:17:57Z · t3m8ch

## Решение владельца: Fetch вместо Axios

Для frontend transport выбран нативный `fetch`. Axios не является проектным стандартом и должен быть удалён после clean cutover существующего auth client.

Зафиксированные ограничения для оставшейся части решения:

- transport API возвращает явный Result-like discriminated union, а не использует исключения как прикладной error channel;
- network/CORS/abort/body parsing exceptions перехватываются на transport boundary и переводятся в типизированные ошибки;
- ожидаемые доменные исходы, включая `not-authorized` при session check, остаются отдельными вариантами результата;
- исключение допустимо только в adapter к TanStack Query, где rejected promise требуется для retries, `isError` и error boundaries;
- после миграции всех imports зависимость `axios` удаляется из manifest/lockfile.

Этот выбор закрывает часть вопроса о transport implementation. DTO validation, mock/real seam, query-key ownership и cache invalidation остаются открытыми в этом тикете.

### 2026-09-13T21:59:50Z · t3m8ch

## Решение: Fetch/MSW transport, явные исходы и feature-owned cache

### Transport и mocks

- Нативный `fetch` является единым HTTP transport; Axios удаляется после полного cutover существующего auth client.
- Feature-модули предоставляют operation-specific функции, скрывающие URL, HTTP statuses, parsing, runtime validation и DTO mapping от UI/domain-кода.
- Одни и те же Fetch-based функции работают с реальным backend и MSW. Feature-код не выбирает mock/real implementation.
- MSW является network-level mock seam. TypeScript interfaces и dependency injection не вводятся только ради HTTP mocks.
- Stateful MSW backend остаётся единым resettable состоянием с feature-local handlers/operations, как принято в [«Согласовать карту реализованной frontend-системы»](https://github.com/dsc-sgu/mm-frontend/issues/63).

### Исходы, отказы и TanStack Query

- Формальный критерий: если операция получила один из объявленных корректных ответов, Promise завершается operation-specific discriminated union; если ни один объявленный исход получить нельзя, Promise отклоняется типизированным `Error`.
- Ожидаемые отрицательные исходы, например `not-authorized` при session check, остаются данными. HTTP status сам по себе не определяет канал.
- Network, неожиданный HTTP response, malformed body и invalid DTO являются отказами операции.
- Cancellation является отдельным управляющим исходом: `AbortSignal` TanStack Query передаётся в `fetch`, abort не преобразуется в user-visible network failure.
- Универсальный `Result<T, E>` на transport/TanStack seam отвергнут: при корректном unwrap он добавляет цикл `Err → throw`, а без unwrap ломает `isError`, retries и error boundaries.
- Retry policy определяется после классификации исхода одновременно по виду отказа и контракту операции. Mutation retries запрещены без документированной backend idempotency; одна логическая команда переиспользует один idempotency key во всех попытках.

### Runtime validation

- Непроверенный structured payload не получает DTO/domain type через `any`, assertion или unchecked generic.
- Внешние данные входят как `unknown` и проходят Valibot validation до чтения полей, DTO mapping и помещения в state/cache.
- Проверяются successful payloads и structured error payloads, поля которых использует frontend.
- MSW responses проходят тот же production parsing/validation path, что и реальные ответы.

### Query keys

- Единый проектный стиль распространяется на все query families, включая семейства с одним key: каждый владелец предоставляет readonly typed `<область>Keys` factory.
- Параметризованные factories выражают иерархию от общего scope к точным entries и включают все входы, меняющие результат `queryFn`.
- Raw root constants и вручную собранные tuples не являются cross-feature interface. Другой feature использует factory владельца.
- Общего registry ключей нет. Semantic helper создаётся только для повторяемого, многосоставного или инвариантного cache behavior, а не как однострочная обёртка над TanStack Query.
- Существующий `taskPageKeys` признан удачным началом этой конвенции.

### Cache consistency после mutation

- `setQueryData` используется для точного entry, когда mutation вернула его полное провалидированное авторитетное представление.
- Filtered, sorted, paginated, derived и неполные representations инвалидируются минимальным корректным prefix; frontend не воспроизводит backend business logic ради ручной нормализации cache.
- Broad invalidation допустима только при фактическом изменении всего scope либо невозможности выразить полный stale scope уже известным более узким prefix. Гипотетические будущие projections не являются основанием инвалидировать весь Course.
- Cross-feature cache effects остаются явными в mutation orchestration и используют factories либо содержательные helpers владельцев caches.
- Все cache updates immutable. Mutation ожидает required invalidations, если следующий UI transition предполагает согласованные данные.

### Optimistic updates

- Optimistic update не является default. Он нужен только когда ожидание server response заметно нарушает непрерывность действия, а speculative outcome однозначен, понятен и безопасно обратим.
- Для одного UI surface предпочтителен pending UI из mutation state/variables без изменения cache.
- Cache-level optimism допустим только нескольким consumers или дальнейшим локальным операциям и требует concurrency model, cancel конфликтующего refetch, snapshot, immutable update, rollback и authoritative reconciliation.
- Для создания/изменения комментариев optimistic cache update сейчас не нужен.
- Существующий переход Review Read State в `seen` является обоснованным optimistic cache update.
