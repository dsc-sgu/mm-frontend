# Отправлять попытку загрузкой файлов через сайт

## Проблема

Сейчас попытку можно сдать только через `git push`. Студенту без опыта с git это закрывает путь в систему. Бэкенд уже принимает отправку через сайт: `POST /attempts?taskID=…` с ZIP в теле, в ответе `commitHash` (mm-backend PR #187, `internal/attempts/handler.go`). Во фронтенде нет ни кнопки, ни формы, а в тикетах эта возможность упоминается только мимоходом (mm-181, mm-268).

## Что делает

Вертикаль: форма на странице задания, операция на Fetch, MSW-handler, тесты.

- На странице задания у студента есть кнопка «Отправить попытку» и область выбора файлов или папки (drag-and-drop). Фронтенд упаковывает файлы в ZIP.
- До отправки видно, какие файлы попадут в попытку по маскам путей задания, если маски известны фронтенду.
- После отправки новая попытка появляется в истории попыток (mm-222-REV2.2), кэш сбрасывается.
- Отказы называются явно: попытки кончились (`409 attempts-exhausted`), ни один файл не подошёл под маски, архив слишком большой (`MaxZipTotalSize`), задание ещё не открыто.

## Что решить

- Что такое отправка через сайт для репозитория: новый коммит поверх репозитория цепочки или полная замена содержимого. От этого зависит, что студент увидит потом в `git pull`.
- Лимит размера и как о нём сказать до загрузки.
- Связь с правилом mm-268 (новая попытка до проверки предыдущей).
- Нужна ли загрузка уже в первом семестре. Пока решено: priority 1, основной путь сдачи — `git push`. Если выяснится, что первокурсники не справляются с git, поднять до priority 0.

## Интеграционные предпосылки и образцы

Добавить блокер mm-222: новая попытка после загрузки должна появляться в канонической истории, которую этот этап переводит с локального RAM-агрегата на HTTP/MSW. Иначе фича будет вынуждена расширять удаляемый fetchTaskPage и локальное создание истории. mm-227 не нужен для самого создания попытки: публикация проверки здесь не выполняется. Весь эпик mm-218 и полнота diff не являются предпосылкой отправки.

Проверенные готовые образцы origin/main: `src/features/course/features/attempt-review/api/load-attempt.ts` — разрешение локатора в AttemptId; `attempt-review/api/load-student-attempts.ts` и `attempt-review/api/queries.ts` — операции и фабрики ключей по CourseId/TaskId/UserId; `src/app/mock-backend/state.ts` — каноническая неизменяемая попытка. История и её фабрика ключей из mm-222 доступны пока лишь в незавершённой ветке mm-218-wave1, не копировать их как уже влитый API.

Загрузку архива, результат отправки и ожидаемые отрицательные исходы реализовать отдельной операцией владельца task через runHttpOperation/Fetch, MSW и проверку DTO. Ответ должен однозначно разрешать принятую попытку; один commitHash старого бэкенда не навязывает форму нового API. После подтверждённой отправки инвалидировать историю task и селектор попыток через их публичные фабрики, не добавлять строку вручную в отфильтрованный кэш. Не импортировать `task/api/mock.ts` и не копировать optimistic map по attemptNumber из старого `task/api/queries.ts`. Правило повторной отправки до проверки из mm-268, поведение репозитория и лимиты определить до реализации операции в рамках этого сценария; это вопросы контракта, не зависимость от всего списка попыток ATT1 или настроек редактора.

Проверено по `origin/main` (`045ea6d`). Наличие решения в спецификации или рабочей ветке не означает, что его реализация уже доступна в `main`. Перед реализацией перечитать `docs/agents/remote-data.md` и проверить актуальность указанных путей.
