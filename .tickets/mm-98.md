# Согласовать протокол SSE для обновлений проверки и брони проверки в реальном времени

## Делает

Согласовывает протокол событий в реальном времени между фронтендом и бэкендом (предпочтение — SSE, см. комментарий 2026-10-09) для проверки и брони проверки до тикетов реализации. Контракт должен безопасно поддерживать проекцию в TanStack Query при переподключении и пропущенных событиях.

Контекст попыток на бэкенде: [mm-backend PR #159 «Attempt, Task, Git API»](https://github.com/dsc-sgu/mm-backend/pull/159) и [mm-backend PR #164 «refactor: reworked based on design doc»](https://github.com/dsc-sgu/mm-backend/pull/164).

## Готово, когда

- [ ] Определена область подписки.
- [ ] Записаны типы событий и их тела для взятия, продления, снятия и истечения брони.
- [ ] У событий есть ревизия или порядковый номер, чтобы замечать пропуски и доставку не по порядку.
- [ ] Определены аутентификация, авторизация и потеря участия в курсе.
- [ ] Определены переподключение с нарастающей задержкой и эндпоинт полной сверки с сервером.
- [ ] Согласовано, когда фронтенд обновляет кэш, а когда инвалидирует его и перечитывает.
- [ ] Контракт согласован командами фронтенда и бэкенда и записан в устойчивом документе или ADR.
- [ ] После решения отдельно составлена нарезка реализации на фронтенде, готовая для агентов.

## Зависит от

- Согласованная модель попыток и проверки на бэкенде: текущие открытые PR ещё не задают протокол брони проверки.

### 2026-10-09T21:49:08Z · t3m8ch

## Уточнение из «Спроектировать Review → Grade → Student result vertical»

Решение mm-116 «Спроектировать Review → Grade → Student result vertical» расширяет этот тикет. Название изменено с «Согласовать WebSocket protocol для review-lock updates».

### Факты

- Ни на `main`, ни в ветках и PR backend нет realtime: ни WebSocket, ни SSE, ни уведомлений. Course lease сообщает о занятости только ответом `423`.
- Frontend-vertical Review не зависит от realtime. Lease, публикация и согласованность корректны через heartbeat, вход, фокус и reconnect, а realtime подключится к тому же источнику состояния lease и Review без переделки модели.

### Предпочтение владельца frontend: SSE

Все нужные события идут от сервера к клиенту, а команды уже идут через REST. Поэтому предпочтительный транспорт — Server-Sent Events. Окончательный выбор протокола остаётся за этим тикетом вместе с backend.

### Охват событий

Не только Review Lease:

- lease взят, продлён, снят или истёк;
- опубликована новая Review Revision;
- создан, изменён или удалён reply;
- изменилась Review Read State.

### Что учесть

1. **Лимит соединений HTTP/1.1** (6 на origin): нужен HTTP/2 между браузером и reverse proxy либо общий поток на все вкладки.
2. **Один поток на User с фильтрацией по Course Membership и роли**, а не поток на Course: `EventSource` нельзя перенастроить без переподключения при навигации.
3. **События — подсказки для инвалидации.** Frontend по событию вызывает `observeReviewRevision` либо инвалидирует нужную проекцию и перечитывает авторитетные данные. Исключение — небольшое полное состояние lease, его можно класть в cache прямо из события.
4. **`Last-Event-ID`, номера revision или sequence** для обнаружения пропусков и авторитетного resync. Нужны keepalive-комментарии, отключение буферизации в proxy и рассылка через Valkey pub/sub при нескольких экземплярах backend.
5. **Потеря Membership** закрывает поток или прекращает события по этому Course.

### Идея для протокола

Lease можно привязать к открытому SSE-соединению: пока поток жив, сервер сам продлевает lease. Это снимает проблему замедления таймеров heartbeat в фоновых вкладках, но требует решить поведение при обрыве соединения и нескольких экземплярах backend.

## Бронь редактирования курса уходит, бронь проверки остаётся

Если [mm-backend PR #187](https://github.com/dsc-sgu/mm-backend/pull/187) вольют или согласуют, брони редактирования курса и `heartbeat` курса не будет: черновик заводится на каждый изменённый блок, конфликты ловит публикация. Из охвата событий этого тикета выпадают события брони курса и `423` курса. События брони проверки (взята, продлена, снята, истекла), новой версии проверки, ответов и прочитанности остаются как были.

Возможное новое событие — «у коллеги черновик этого блока» — не входит сюда: оно в бэклоге, в mm-287. Если до него дойдёт, события добавляются к этому же потоку на пользователя. Модель — mm-286.
